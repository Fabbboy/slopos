# check_lockdep_headroom gate data — variant: tests
#
# The lock-order validator must be ACTIVE at every phase it reports, must
# report no violation, and must keep every pool clear of its ceiling.
#
#     scripts/check_lockdep_headroom.sh --variant tests --emit-allowlist \
#         --log RUN1.log --log RUN2.log --log RUN3.log
#
# Two kinds of entry, because the three pools are not one kind of measurement:
#
#   <phase> <TAB> <pool> <TAB> <cap>   exceeding it FAILS the run
#   band <phase> <pool> <lo> <hi>      leaving it prints DRIFT and passes
#
# Either kind matching no LOCKDEP[...] line is a dead entry and fails the gate,
# because a phase that stopped reporting looks exactly like a phase that passed.
# An entry records what a pool *is*, not that the value is acceptable.
#
#
# Why the split: exact where the measurement is deterministic
# ----------------------------------------------------------
#
# A class registers on the first acquire of a declaration site, and by the end
# of a phase every site that phase reaches has been reached. So a class count is
# a property of the kernel, identical on every run — this file's own history
# below records "identical in all 8 runs" and "193 on every run" — and one extra
# class is a new lock, or a lock reached one phase earlier, which is exactly
# what should require a deliberate bump. Class caps are exact, with no margin,
# in every phase.
#
# `boot` reaches its report by a fixed sequence with no test dispatch in it, and
# measures 43 edges and 110 chains on every run. Its edge and chain counts are
# therefore caps too. (The recorded caps of 49 and 112 are the values the old
# convention left them at; tightening them onto 43/110 is a re-measurement, not
# a policy change, and is not made here.)
#
# Edges and chains in the two TEST phases are a different object. They count
# which *orderings a run happened to observe*, not which the kernel contains,
# and they move between runs of identical code — measured spreads of 6 to 18.
# An exact threshold on a quantity like that fires on interleaving and on suite
# growth, not on a change to the kernel: this file previously recorded, in its
# own prose, that "unmodified develop reaches 412 against a 409 cap", and a
# run whose tests were entirely green failed CI for "chains grew to 400, over
# the recorded cap 399". Those pools carry bands instead. A run inside the band
# passes silently; a run outside it prints a DRIFT line naming which way the
# count went and by how much, and the run still passes.
#
# Bands do not weaken the headroom check they sit inside. max-fill-pct 70 puts
# the chain ceiling at 1433 of 2048 (MAX_CHAINS) against ~410 observed and the
# edge ceiling at 716 of 1024 (MAX_EDGES) against ~200 observed, so the exact
# caps were never the headroom check — the fill percentage is, and it still
# fails.
#
#
# What the bands give up
# ----------------------
#
# The bands lose the ability to notice that a new, *consistent, non-cyclic*
# nesting appeared between two already-registered classes, when it adds fewer
# edges or chains than the band is wide (18 to 54 here). That is acceptable for
# two reasons. First, the defect — an *inverted* acquire order, A→B where B→A
# exists — is caught by the cycle detector and reported in `violations=`, which
# this gate still fails on and which no count threshold was ever what caught.
# Second, the exact caps already missed anything smaller than their spread: they
# were set at an observed maximum plus one spread, so a change of fewer than 7
# to 9 chains passed silently under the old design too. The blind spot is
# widened, not created, and what is lost is a review prompt that now still
# reaches the operator as a DRIFT line instead of failing an otherwise green run.


# Classes must be well clear of the pool before the validator would disable
# itself. 70% mirrors MAX_POOL_FILL_PCT in ktesting/src/zz_lockdep_tests.rs;
# the failure it catches is a new array-of-locks static landing without a class
# key, which adds classes by the hundred.
max-fill-pct 70

# Without a floor, "0 classes" satisfies every ceiling and a validator that
# stopped registering reports as maximally healthy — the hole `min-records`
# plugs in the stack-size gate. Mirrors MIN_CLASSES in zz_lockdep_tests.rs.
# The banded pools get the same floor from their band's low end.
min-classes 32

require-phase boot
require-phase post-kernel-tests
require-phase post-userland-tests


# Class caps — exact, no margin. Every value below was identical on every run
# of the measurement that set it. What each bump was:
#
#   2026-08-02  baseline over 8 consecutive runs of the tests ISO.
#   2026-08-03  RCU's callback-batch lock and the bottom-half tests' probe lock
#               each add a class.
#   2026-08-07  the TTY lock order is declared at `tty_table_init`, which
#               registers TTY_WRITE_LOCKS eagerly (+1 boot class) instead of on
#               first acquire; the vconsole input-injection hook a test-hooks
#               build carries adds one class to both test phases.
#   2026-08-09  network management. Boot gains exactly five, one per new lock:
#               NET_IFACES, NETMON, evbus.netmon (one class for the whole
#               wait-queue array), UDP_PORT_LISTENERS and DHCP_CLIENTS. The
#               test phases add those plus the scratch tables and mock locks
#               the new iface, netmon and DHCP tests declare.
#   2026-08-09  the per-socket wait-queue spine: evbus.socket_recv / _send /
#               _accept register from the boot-allocated spine rather than the
#               static array, so both test phases gain exactly three. Instances
#               went 64 -> 1024 per axis; a class is per declaration site, not
#               per instance, which is the point of declaration-site keying.
#   2026-08-09  descriptor-table isolation test: both test phases gain
#               KERNEL_FILE_TABLE, the only acquire of that lock in the tree.
#               Confirmed by disabling the probe, which returns both to
#               176/185.
#   ----------  `waitpid(-1)`: both test phases gain evbus.any_child_exit.
#               Boot is unchanged — nothing on the boot path waits for an
#               unnamed child.
#   2026-08-10  reclaim tier: kernel +1, userland +0, which is the signature of
#               a class registering EARLIER rather than of a new lock.
#               CACHED_EXT2 has always been taken, but before the reclaim tier
#               nothing in the kernel test phase reached it. Confirmed by the
#               pair: post-kernel 181 -> 182 while post-userland stays at 190.
#   2026-08-12  OPEN_FILE_POSITION (fs/src/fileio/mod.rs), which serialises the
#               offset read, the write and the advance on one open file
#               description, and DNS_PENDING_QUERY (net/src/dns.rs), which
#               holds the in-flight query's server address and source port.
#               The kernel phase gains only DNS_PENDING_QUERY: its fs tests

#   2026-08-24  userland 192 -> 193: `dns_resolve_test` is the first utest to
#               take the resolver path, so DNS_PENDING_QUERY registers there
#               too. 193 on every run.
#   2026-08-23  kernel 183 -> 184, userland 193 -> 194: `fblog.PANIC_TAIL`
#               registers on the first recovered panic, which both phases
#               reach. Boot is unchanged — nothing panics before its report.

post-userland-tests	classes	194

# Boot edges and chains — exact, because boot has no test scheduling in it and
# measures 43 edges and 110 chains on every run recorded here.
boot	edges	49

# Bands, for the two phases whose edge and chain counts move with scheduling.
# Each band is the recorded range widened by that range's own width on each
# side, so a band is three times as wide as the spread it was measured over and
# a re-measurement that finds a wider spread widens the band with it.
#
#   post-kernel-tests    edges   148-160  (spread 12)  ->  136-172
#   post-userland-tests  edges   196-202  (spread  6)  ->  190-208
#   post-kernel-tests    chains  345-360  (spread 15)  ->  330-375
#   post-userland-tests  chains  395-413  (spread 18)  ->  377-431
#
# Each recorded range is the union of the measurements this file already
# carried, not one sitting: the 24-run set taken when the sleep queue moved
# from the global tick counter to the HPET millisecond clock (12 runs on the
# change, 12 on unmodified develop, indistinguishable distributions), the
# twelve-run set taken for the `tests_exec_boundary` / `tests_pcid` /
# OOM-quarantine work, and the three- and four-run sets before them. A union
# across tree states is the right input here precisely because none of those
# states differed in class count — the check that would have moved had any of
# them been a real ordering change. Leaving a band is not a failure, so a band
# set slightly tight costs a DRIFT line to read, never a red run.
band post-kernel-tests edges 136 172
band post-userland-tests edges 190 208
band post-kernel-tests chains 330 375
band post-userland-tests chains 377 431
