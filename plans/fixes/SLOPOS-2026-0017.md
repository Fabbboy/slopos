## 1. Evidence: what is actually in the tree

The ledger entry is materially correct in its conclusion and wrong in almost
every line number and in one quoted comment. Corrections first.

### 1.1 The counter

`slopos-ostd/src/mm/vm_space.rs:217-230` (ledger said `:287-298`):

```rust
static NEXT_PCID: AtomicU64 = AtomicU64::new(1);

// TODO(tech-debt): a monotonic counter masked to the architectural 12
// bits aliases PCIDs after 4096 address spaces — needs a real ASID slot
// scheduler.
fn alloc_pcid() -> Pcid {
    let raw = NEXT_PCID.fetch_add(1, Ordering::Relaxed);
    Pcid::new((raw & 0x0FFF) as u16)
}

#[cfg(any(test, feature = "test-helpers"))]
pub fn reset_pcid_counter_for_test() {
    NEXT_PCID.store(1, Ordering::Release);
}
```

**Ledger correction 1.** The ledger quotes a comment claiming PCIDs are
"**never reused**". No such comment exists. The current comment is a
`TODO(tech-debt)` that correctly describes the aliasing. Someone already fixed
the *comment* and not the code. The ledger's evidence bullet should be
rewritten to quote what is there, because a reviewer chasing the quoted string
will not find it and may conclude the finding is stale.

**Ledger correction 2.** Line numbers. `alloc_pcid` is at `:222`, not `:287`.
`pcid: alloc_pcid()` in `VmSpace::new` is at `:259`, not `:336`. `activate` is
at `:386-404`, not `:539-551`.

### 1.2 The PCID newtype

`slopos-ostd/src/arch/x86_64/cr3.rs:13-28` (ledger said `:20-28` — close):

```rust
impl Pcid {
    /// PCID 0 — kernel-only address space (the kernel page-dir).
    pub const KERNEL: Pcid = Pcid(0);

    /// Construct a `Pcid`. Mask to 12 bits.
    #[inline]
    pub const fn new(raw: u16) -> Self {
        Pcid(raw & 0x0FFF)
    }
```

`NEXT_PCID` starts at 1, so the 4096th `VmSpace::new` computes
`4096 & 0x0FFF == 0` and hands a user address space `Pcid::KERNEL`. The ledger
is right about this.

Note there are **two** unrelated `Pcid` types in the tree — this one, and
`mm/src/mmu/cr3.rs:31` — and they do not interoperate. That duplication is part
of what this proposal removes.

### 1.3 The NOFLUSH bit

`slopos-ostd/src/arch/x86_64/cr3.rs:50-55` (ledger said `:58-63`):

```rust
pub unsafe fn write_cr3_pcid(pml4_phys: PhysAddr, pcid: Pcid, no_flush: bool) {
    let mut value = pml4_phys.as_u64() & !0xFFF_u64;
    value |= pcid.raw() as u64;
    if no_flush {
        value |= 1u64 << 63;
    }
```

`slopos-ostd/src/mm/vm_space.rs:389-404`:

```rust
pub unsafe fn activate(&self) {
    if let Some(hook) = current_cursor_unmap_hook() {
        hook.on_activate(self.mm_ctx_handle.load(Ordering::Acquire));
    }
    // NOFLUSH is architecturally legal only when `CR4.PCIDE` is
    // enabled; setting it on a platform that never enabled PCIDE
    // yields a #GP.
    let pcide_enabled = (crate::cpu::x86_64::control_regs::read_cr4()
        & crate::cpu::x86_64::control_regs::Cr4Flags::PCIDE.bits())
        != 0;
    unsafe { write_cr3_pcid(self.pml4_paddr(), self.pcid, pcide_enabled) };
}
```

`no_flush` is *literally* "did anyone turn PCIDE on". There is no flush
decision anywhere in the kernel. Every CR3 write on PCID-capable hardware —
process→process, process→kernel master, kernel master→process — is NOFLUSH.

`CR4.PCIDE` really is set: `boot/src/boot_memory.rs:22-25` runs
`boot_step_mmu_asid_init_fn` at `boot_init_priority(30)`, which calls
`slopos_mm::mmu::init_bsp()` → `mm/src/mmu/asid.rs:111-146`, which does
`set_cr4_pcide_local()` on any Intel/AMD CPU with the CPUID PCID bit that is
not on the Alder/Raptor Lake errata list. `boot/src/smp.rs:48` does the same
for APs. So on ordinary hardware and on QEMU `-cpu max`/`-cpu host`, the
NOFLUSH path is live.

### 1.4 The unwired ASID pool

The ledger says "a Linux-style ASID pool sits beside it as dead code". Verified
precisely:

- `mm/src/mmu/asid.rs:203` `pub fn select_cr3(...) -> Cr3Value` — **zero callers**
  outside its own file.
- `mm/src/mmu/asid.rs:282` `pub fn forget_context_local(...)` — **zero callers**.
- `mm/src/mmu/cr3.rs:97` `alloc_mm_context_id()` — *is* called
  (`mm/src/process_vm.rs:1497`, `:2855`), but only to feed
  `VmSpace::set_mm_ctx_handle`, whose sole consumer is
  `mm/src/mmu/luf.rs:34` recording which context a CPU last activated — a
  **diagnostic** (`ACTIVE_MM_CTX_HANDLE`, `mm/src/mmu/luf.rs:27-49`). The
  `MmContextId` never reaches a CR3 value.
- `mm/src/process_vm.rs:557` `process_vm_get_mm_ctx_id` — **zero callers**
  either, despite a doc comment claiming "the scheduler keys the per-CPU ASID
  cache on it". The scheduler does no such thing: `sched/src/scheduler.rs:353-357`
  calls `process_vm_activate_by_handle`, which calls
  `VmSpace::activate_at_context_switch`, which calls `activate`, which reads
  `self.pcid`. That comment is the same species of aspirational prose as the
  one the ledger misquoted in §1.1, and the implementation should delete it.
- The live parts of `asid.rs` are `init_bsp`/`init_ap` (which turn PCIDE *on*,
  enabling the NOFLUSH path), `flush_pcid`, and `flush_local_all_contexts`
  (used by `mm/src/tlb.rs:444` and `mm/src/mmu/quiesce.rs:125`).

So the module that would have made PCID safe is inert, while the module that
makes PCID *dangerous* — the `CR4.PCIDE` write — runs at boot. That is the
worst possible half of the feature to have shipped.

### 1.4a Correction to revision 1: the pool is not a decoy, it is the fix

**Revision 1 got this wrong and the error propagated through §3, §4.2 and §7.**
It described `mm/src/mmu/asid.rs` as "a plausible-looking ASID pool … that is
not wired to anything" and "a decoy" worth deleting, and then specified a
**new** ~250-line OSTD module against ~300 lines of `mm` deleted. That is not
what is in the tree. Read the file:

```rust
// mm/src/mmu/asid.rs:31-44
pub const DYN_ASIDS_PER_CPU: usize = 16;

#[derive(Clone, Copy)]
struct AsidSlot {
    ctx_id: u64,
    tlb_gen: u64,
}
```

`select_cr3` (`:203-267`) already implements, line for line, the algorithm
§4.5 specifies: a `last_loaded_slot` hot check, a linear scan whose
generation-mismatch arm calls `flush_pcid(pcid_raw)` and refreshes
`slot.tlb_gen`, and a round-robin `next_asid` miss arm that rebinds the slot
and returns `Cr3Value::new(pml4_phys, pcid, /* no_flush */ false)` with the
comment "NOFLUSH=false so the processor drops any stale non-global entries
still cached under this PCID." The `PCID_ENABLED` / `INVPCID_AVAILABLE`
mirrors, the `cpu_id >= MAX_CPUS` fail-closed arm, the errata gate, the
`PerCpuSlot` choice with its stated reason, and the four per-CPU counters
(`hot_hits`, `gen_refresh`, `misses`, `legacy`) are all present.

**What is missing is not the pool. It is four wires:**

1. Nothing ever *calls* `select_cr3` — `VmSpace::activate` writes CR3 itself
   from `self.pcid` (`slopos-ostd/src/mm/vm_space.rs:403`).
2. `VmSpace` carries no `tlb_gen`, so `select_cr3`'s `ctx_tlb_gen` parameter
   has no source. Nothing in the tree bumps a per-context generation on unmap
   or protect.
3. `MmContextId` lives in `mm`, `Pcid` is duplicated in `mm` and OSTD, and
   OSTD cannot call *up* into `mm` — `mm/Cargo.toml` depends on `slopos-ostd`,
   not the reverse. The dependency direction is why the pool could not be
   wired where the CR3 write actually happens.
4. `select_cr3` returns a `Cr3Value`, and `Cr3Value::new` is a **safe public
   constructor taking `no_flush: bool`** (`mm/src/mmu/cr3.rs:117`), so it
   forges NOFLUSH as freely as `write_cr3_pcid` does.

That changes the shape of the work substantially, in the direction of *less*
risk: the fix is a **move plus four wires**, not a rewrite. §4.2 and §5 are
rewritten accordingly. It also means the existing file's judgement calls
— `DYN_ASIDS_PER_CPU = 16`, `PerCpuSlot` over `SpinLock`, `AtomicU64`
counters readable cross-CPU — are the tree's own and should be **kept**
unless there is a reason to overrule them; revision 1 overruled the first of
them for no reason, and §4.3a corrects that.

The one thing revision 1 was right about here: a reviewer auditing "does
SlopOS handle PCID correctly" finds this file, reads it, and concludes yes.
That is still worth fixing — but by *connecting* it, not deleting it.

### 1.4b R3-1: the move does not compile as revision 2 specified it

Revision 2's §5 step 1 asserted that "every symbol it uses — `IrqDisabled`,
`Cr4Flags`, `read_cr4`, `write_cr4`, the CPUID constants, `MAX_CPUS`,
`PerCpuSlot`, `invpcid`, `klog_*` — already lives in `slopos-ostd`". That list
is complete for every function in the file **except `init_bsp`**, which ends
with `mm/src/mmu/asid.rs:140-146`:

```rust
    klog_info!(
        "MMU: PCID enabled (INVPCID={}, slots/CPU={}, backend={})",
        invpcid,
        DYN_ASIDS_PER_CPU,
        super::rar::backend().name()

```

`super::rar::backend()` returns `&'static dyn ShootdownBackend`
(`mm/src/mmu/rar.rs:82`), an **`mm`-crate trait object**. `mm/Cargo.toml:25`
declares `slopos-ostd`, so the reverse edge does not exist and OSTD cannot name
that type. Moving the function verbatim is an unresolved-import build failure
on the first `cargo build`, not a subtle problem.

This is the same class of defect as revision 1's `&IrqDisabled` parameter
(§1.6): a cross-crate dependency the document asserted away instead of
checking. It is also the second `mm`-only symbol in the file — the first,
`super::errata::should_disable_pcid()` (`:129`), revision 2 *did* catch and
routed through a caller-supplied `PcidSupport`.

**Resolution (§9-D7).** The backend name is a *log-line decoration*, not an
input to any decision the pool makes: `backend()` is read nowhere else in the
file, and its value cannot change the PCID verdict. It moves to the caller.
`init_bsp` returns its verdict as a small `Copy` struct and `boot/` — which
already depends on both crates (`boot/Cargo.toml:32,34`) — emits the log line:

### 1.5 Escalation: the bug does not need 4096 processes

This is the material finding the ledger misses, and it changes the severity.

`sched/src/scheduler.rs:320` calls `tlb::notify_mm_switch(next_key, ...)` on
every dispatch. `mm/src/tlb.rs:372-389`:

```rust
pub fn notify_mm_switch(new_key: Option<TlbProcessKey>, new_process_id: u32, cpu_id: usize) {
    ...
    if let Some(old_key) = state.loaded_process_key() {
        process_tlb_info(old_key).cpumask.clear(cpu_id);
    }
    if let Some(key) = new_key {
        process_tlb_info(key).cpumask.set(cpu_id);
    }
```

A CPU that switches *away* from process P is removed from P's shootdown mask.
`mm/src/tlb.rs:730-767` `targeted_flush_request` iterates
`info.cpumask.iter_set()` and therefore **does not IPI that CPU**. That is a
correct and standard lazy-TLB optimisation — *provided* the CPU flushes when it
comes back. It does not: `activate` sets NOFLUSH unconditionally, so the CPU
resumes P with every translation it cached before it left.

The concrete reachable case is `mprotect` RW→RO:

- `mm/src/process_vm.rs:2518` `process_vm_mprotect` → `:2579`/`:2585`
  `tlb::flush_all_for_process(slot_tlb_key(slot))` — masked, so a CPU not
  currently running the process is skipped.
- Nothing else covers it. `mm/src/mmu/quiesce.rs` only arms on
  `note_deferred_unmap` (from `luf::queue_unmap`, i.e. *unmap*), and only
  gates **frame reuse**; a `protect` frees no frame, so the epoch machinery is
  never armed and the quarantine never rotates on its account.
- COW is *not* affected: `mm/src/process_vm.rs:2913` issues a full
  `tlb::flush_all()` broadcast after the COW pass, which reaches every online
  CPU and does an all-context invalidation.

**Consequence:** a two-CPU, two-process system reaches a stale-TLB condition
with no wraparound at all. Thread A on CPU0 maps a page RW and touches it; the
scheduler runs something else on CPU0; thread B on CPU1 calls
`mprotect(PROT_READ)`; CPU0 is not in the mask, gets no IPI; A is rescheduled on
CPU0, CR3 is reloaded with NOFLUSH, and A's cached writable entry is still
resident. A writes to a page the kernel believes is read-only.

That is `AC:L`, not `AC:H`. Recomputed with `scripts/cvss_calc.py`:

```
CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H  →  8.8 HIGH
```

(verified: `python3 scripts/cvss_calc.py --vector "CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H"` prints `base_score=8.8`).

**Recommended ledger amendment** (to be applied when this fix lands, or sooner
if the finding is re-triaged): raise confidence to 92 (evidence 40 — the mask
narrowing and the unconditional NOFLUSH both read directly; exploitability 28 —
two processes on two CPUs, no wraparound; reproducibility 24), and raise the
vector to the above. Add `mm/src/tlb.rs:372-389` and
`mm/src/process_vm.rs:2579` to the evidence list.

### 1.6 Correction to revision 1: `activate` has no `IrqDisabled` witness to take

Revision 1 specified `select_for_activate(irq: &IrqDisabled<'_>, ...)` and
asserted "the scheduler already guarantees [`activate`] runs with interrupts
disabled on the local CPU". The interrupts-off part is true; the witness part
is not, and it is a compile error rather than a design nicety.

`VmSpace::activate` is `pub unsafe fn activate(&self)`
(`slopos-ostd/src/mm/vm_space.rs:389`) reached through three safe wrappers
(`activate_kernel_master` `:357`, `activate_kernel_master_bsp` `:366`,
`activate_at_context_switch` `:379`).

**R3-6 correction: there are nine call sites, not five.** Revision 2 wrote
"five" above a table of nine rows and omitted a tenth site entirely. The count

    IrqDisabled::with(|irq| {

reason the fix does not ripple into `sched`, `core` or `kernel-services`.

## 2. Prior art: what mature kernels settled on, and what they abandoned

Sources consulted: Intel SDM Vol. 3A §4.10.1 (Process-Context Identifiers),
§4.10.2 (TLB and paging-structure caches, including §4.10.2.3 "Details of TLB
Use" and §4.10.2.4 on global pages), §4.10.4 (invalidation of cached
translations); the `INVPCID` instruction reference (SDM Vol. 2A); LWN's
coverage of the x86 PCID work (Lutomirski's 2016 RFC series posting, LWN
article 671299) and of KAISER/PTI (LWN 738975); the kernel.org PTI
documentation; and FreeBSD's amd64 `pmap` design description. **No text from
any of these is reproduced here or intended for the implementation.**

### 2.1 The architectural facts that constrain every design

- A PCID is 12 bits in `CR3[11:0]`; the CPU tags each non-global TLB entry with
  the PCID that was loaded when it was filled (SDM §4.10.1).
- `CR3[63]` (NOFLUSH) tells the CPU to *preserve* the entries tagged with the
  PCID being loaded. Setting it when `CR4.PCIDE = 0` is a `#GP` — which the
  existing comment in `activate` correctly notes.
- Loading CR3 **without** NOFLUSH invalidates the entries for **the PCID being
  loaded only** — not for other PCIDs. This is the fact that makes the "cheap
  patch" in §3 correct, and the fact that makes `flush_local_all_contexts`'s
  doc comment in `mm/src/mmu/asid.rs:172-186` correct as well.
- `INVPCID` type 1 invalidates all non-global entries for one PCID; type 3
  invalidates all non-global entries for every PCID. Type 2 additionally takes
  out globals.
- Global (`PG_G`) entries are **not** PCID-tagged and survive every CR3 load and
  every type-0/1/3 `INVPCID`. SlopOS already stamps the kernel half global
  (`boot/src/boot_memory.rs:94-108`), which is what makes a kernel-half
  translation correct under any PCID. Keep that; it is load-bearing for this
  design.
- `INVLPG` invalidates the given linear address for **the currently loaded
  PCID** (plus globals). It does *not* reach the same page under a different
  PCID. `mm/src/mmu/luf.rs:20-22`'s doc comment already states this correctly.

### 2.2 The two designs that survived

**(A) Small fixed per-CPU slot array, keyed on a non-recycling context id plus a
per-context generation.** This is the shape Linux converged on. Each CPU owns a
handful of dynamic PCIDs (Linux settled on six). Each address space carries a
never-recycled 64-bit context id and a TLB generation counter. On context
switch a CPU scans its own array for the context id; a hit whose recorded
generation matches means the CPU's cached entries under that PCID are current
and the CR3 load can be NOFLUSH; a hit with a stale generation means flush that
one PCID and refresh; a miss means evict a slot and load *without* NOFLUSH, so
the hardware drops the previous tenant's entries as part of the load.

**(B) Whole-space per-CPU allocation with a per-CPU generation epoch.** FreeBSD
gives each `pmap` a per-CPU record and walks the full 4095-PCID space with a
per-CPU `pcid_next`; when it runs out it bumps a per-CPU generation, which
invalidates every recorded binding at once. Remote invalidation is performed by
*zeroing another CPU's generation record for that pmap* — a plain store, no
IPI — which then forces that CPU to take a fresh PCID (and therefore a flush)
the next time it activates.

Both are correct. The reasons SlopOS should take (A)'s **structure** and (B)'s
**remote-store insight** are in §4.6.

### 2.3 What was tried and abandoned — the part that matters

- **A PCID as a property of the address space, assigned once at creation.**
  This is exactly what SlopOS does today and it is the design everyone
  abandoned, for a reason that is not the 4096 wrap: even with a perfect
  system-wide allocator, a globally-assigned PCID says nothing about *which
  CPU's* TLB holds entries under it. Correctness then requires a global
  "who has cached what" map and a shootdown on every eviction. The insight both
  Linux and FreeBSD landed on is that **a PCID is a per-CPU cache index, not an
  address-space identity**. The address-space identity is a separate,
  never-recycled 64-bit number. Conflating the two is precisely the bug in this
  finding, and no amount of better allocation fixes it.
- **Using `INVPCID` as the general-purpose flush.** Lutomirski's 2016 posting
  reports measuring `INVPCID` as *slower* than careful CR3 manipulation on the
  Skylake hardware of the day, and the merged design leans on CR3-load-side
  flushing (a non-NOFLUSH load) for the common eviction case, keeping `INVPCID`
  for the cases a CR3 load cannot express. This proposal follows that: eviction
  costs zero extra instructions because the flush rides the CR3 write that has
  to happen anyway.
- **A large per-CPU pool.** Linux's six is not a hardware limit; it is a
  working-set observation. The array is scanned linearly with interrupts
  disabled on the dispatch path, so its length is a hot-path cost, and beyond
  the handful of address spaces a CPU actually alternates between the extra
  slots buy nothing.
- **PCID as a security boundary.** It is not one, and this is the single most
  important negative result to carry forward. Meltdown-class attacks read
  through the *permission* check, not the tag; PCID's role in the PTI era is
  purely to make the mandatory dual-CR3 switching affordable. Published PTI
  overhead figures are roughly 5% typical and up to ~30% on syscall-heavy
  workloads *with* PCID, and materially worse without it. SlopOS carries KPTI
  scaffolding (`mm/src/mmu/kpti.rs`) that is explicitly not enabled. **A working
  PCID pool is a hard prerequisite for ever turning that on**, and the PCID
  space must be partitioned for it now — see §4.7.

## 3. What the minimal patch would be, and why it is not the answer

The minimal correct patch is two edits:

1. `slopos-ostd/src/mm/vm_space.rs:222-225` — bias the counter off zero so a
   user space can never receive `Pcid::KERNEL`:
   ```rust
   fn alloc_pcid() -> Pcid {
       let raw = NEXT_PCID.fetch_add(1, Ordering::Relaxed);
       Pcid::new(1 + (raw % 4095) as u16)
   }
   ```
2. `slopos-ostd/src/mm/vm_space.rs:403` — pass `false` for `no_flush`.

**This is correct.** It closes the wrap, closes the CPU-migration staleness of
§1.5, and needs no new state: a CR3 load without NOFLUSH invalidates exactly
the PCID it loads, so two address spaces aliasing PCID 7 simply flush each
other on every switch, and a CPU returning to a context it left always gets a
clean tag.

**And it is worthless.** With NOFLUSH never set, a PCID-tagged TLB behaves
exactly like an untagged one on every switch, while the machine still pays
`CR4.PCIDE` and still runs the errata gate. It is strictly worse than
`nopcid`: the honest two-line patch is not the one above but *deleting
`set_cr4_pcide_local()`* and admitting SlopOS has no PCID support. If the tree
is going to ship a switch that costs a full context flush either way, the
version that does not set PCIDE is simpler and faster.

So the real choice is: **remove PCID, or make it real.** Three things argue for
making it real, on a five-year horizon:

1. **KPTI cannot be enabled without it.** `mm/src/mmu/kpti.rs` exists,
   `KPTI_ENABLED` is `false`, and the module's own doc comment lists what is
   missing. When that work lands, every ring transition becomes a CR3 write.
   With a working pool those writes are NOFLUSH and cost a few cycles; without
   one they are full TLB flushes on every syscall and every interrupt. The
   published PTI figures make the difference between "measurable" and
   "unusable". Whatever is built now must already partition the PCID space for
   the kernel/user pair, or KPTI forces this refactor a second time.
2. **The `MmContextId`/generation machinery is the correct substrate for
   several other things SlopOS already half-has.** The quiesce epoch
   (`mm/src/mmu/quiesce.rs`), the LUF ring (`mm/src/mmu/luf.rs`), the
   per-process shootdown mask (`mm/src/tlb.rs`) and the lazy-TLB flag are four
   independent answers to "does this CPU still hold a translation it should
   not". A per-context TLB generation subsumes the hardest of those questions —
   *the CPU that is not currently running the context* — with a plain store and
   no IPI. Building it once means the next lazy-TLB question has an answer
   already.
3. **The current state is a trap for reviewers.** There is a working ASID pool
   in `mm/src/mmu/asid.rs` with correct doc comments, 300 lines long, that is
   not wired to anything, sitting next to a `Pcid` type that duplicates an OSTD
   type of the same name. Anyone auditing "does SlopOS handle PCID correctly"
   finds the pool, reads it, and concludes yes. Connecting it is worth the
   refactor on its own — and per §1.4a, connecting it is most of the work
   already done.

The refactor is close to **LoC-neutral**, not "±400 net-negative" as revision 1
claimed. Measured: `mm/src/mmu/asid.rs` is 300 lines and `mm/src/mmu/cr3.rs`
is 199 (`wc -l`). The pool moves to OSTD roughly intact (≈300 lines arriving),
`cr3.rs`'s `Pcid`/`MmContextId` merge into the OSTD types (≈100 lines of the
199 deleted, the rest — `Cr3Value` — kept per §9-D3), and the new material is
`Cr3Selection` plus `MmContext` plus the cursor's second dirty bit, ≈60 lines.
Net: **roughly −40 lines of kernel Rust, moved between crates.** §7's
`tcb_ratio` row is corrected to match.

### 4.3 Data structures, with placement and locking

**Per address space — inlined into `VmSpace`, no allocation:**

```rust
/// Never recycled. `0` is the kernel master and no other space may hold it.
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Debug)]
#[repr(transparent)]
pub struct MmContextId(u64);

impl MmContextId {
    pub const KERNEL: MmContextId = MmContextId(0);
    #[inline] pub const fn raw(self) -> u64 { self.0 }
    #[inline] pub const fn is_kernel(self) -> bool { self.0 == 0 }
}
```

Note the sentinel merge. `mm/src/mmu/cr3.rs:74` today calls `0`
`MmContextId::INVALID` ("no context": an empty slot, or an unloaded space in a
fault report) with an `is_valid()` predicate, while `AsidSlot::EMPTY`
(`asid.rs:39-43`) uses `ctx_id: 0` for "empty slot" and `luf.rs:25` uses `0` for
"no context bound". All three are the same zero. This design names it `KERNEL`
rather than `INVALID` because after the merge the kernel master genuinely holds
it — the master is a real address space with a real `VmSpace`
(`kernel-services/src/kernel_vm_space.rs`), not an absence. `is_kernel()`
replaces `is_valid()` at the one place it is read (§4.5 step 3), and the
empty-slot check stays a literal `== 0` as it is today. **The implementer must
not leave both names alive**: two predicates over one sentinel, disagreeing
about whether zero means "kernel" or "invalid", is how this finding's
neighbouring confusions started.

```rust

pub struct MmContext {
    id: MmContextId,
    /// Bumped whenever a cached translation for this context may have been
    /// invalidated. Monotone; never reset.
    tlb_gen: AtomicU64,
}

impl MmContext {
    /// The kernel master's context. `const`, so `wrap_existing` needs no
    /// allocator and cannot fail on this account.
    pub const KERNEL: MmContext = MmContext {
        id: MmContextId::KERNEL,
        tlb_gen: AtomicU64::new(0),
    };

    /// Fresh never-recycled id. `Err(MapError::Uninitialised)` at `u64::MAX`
    /// rather than wrapping — see §4.9.
    pub fn alloc() -> Result<MmContext, MapError> { .. }

    #[inline] pub fn id(&self) -> MmContextId { self.id }
    #[inline] pub fn tlb_gen(&self) -> u64 { self.tlb_gen.load(Ordering::Acquire) }
}
```

**R3-3: which constructor each `VmSpace` path uses.** Revision 2 said
`wrap_existing` "drops its `pcid: Pcid` parameter and clause 4 of its
`# Safety` contract" and stopped there, leaving the field it must initialise
unspecified — an implementer would have to invent the answer, and the plausible
wrong answer (`MmContext::alloc()`) is silently harmful. The rule:

| Construction site | Gets | Why |
|---|---|---|
| `VmSpace::new` (`vm_space.rs:236`, literal at `:259-262`) | `MmContext::alloc()?` | A real user address space; needs its own never-recycled id and its own generation. The `?` composes with the existing `Result<Self, MapError>`. |
| `VmSpace::wrap_existing` (`:285`, literal at `:294-299`) | `MmContext::KERNEL` | Every caller in the tree wraps **the kernel master**: `boot/src/boot_memory.rs:65` via `install_kernel_vm_space`, and `slopos-ostd/tests/vm_space.rs:482`/`:490` which say so in their own comment (*"Pcid 0 mirrors production"*). Handing it an allocated id would give the master a non-zero `MmContextId`, and §4.5 step 3 — `if ctx.id().is_kernel()` — would stop recognising it, silently demoting every kernel-master activate into the dynamic pool and consuming a slot per CPU forever. |

That second row is why the choice cannot be left implicit: the failure is not a
compile error, it is a pool that quietly runs one slot short and a kernel
master that takes a `misses` path on every kernel-task dispatch. The
`# Safety` contract's clause 4 (`vm_space.rs:283-284`, *"`pcid` is appropriate
for this address space"*) is not merely deleted — it is **replaced** by the
statement that `wrap_existing` is the kernel-master constructor, which is what
it has always been in practice. If a future caller needs to wrap a non-master
PML4, that is a new constructor, not a parameter on this one.

`MmContext` is 16 bytes and replaces the existing `pcid: Pcid` (2 bytes, plus
padding) and `mm_ctx_handle: AtomicU64` (8 bytes) fields, so `VmSpace` grows by
at most 8 bytes. Today's `VmSpace` (`slopos-ostd/src/mm/vm_space.rs:63-70`) is
`Frame<PageTableMeta>` + `Pcid` + two `AtomicU64`; after, it is
`Frame<PageTableMeta>` + `AtomicU64` + `MmContext`.

The `check_stack_sizes.sh` argument is **not** "it is behind a `KArc`" —
revision 1 said that and it does not follow: `VmSpace::new` materialises the
value on its own stack and *then* `KArc::try_new` moves it
(`mm/src/process_vm.rs:1498-1511`), so an 8-byte growth is 8 bytes of frame in
`VmSpace::new` regardless of where it ends up. The argument is simply that 8
bytes against a 2048-byte cap is not a risk, and that the frame in question
(`VmSpace::new`) is one the gate already measures. §4.10's `stats_for_cpu` is
the by-value return worth actually watching.

Ids come from a single `static NEXT_MM_CTX_ID: AtomicU64 = AtomicU64::new(1)`.
At one context per nanosecond it wraps in 585 years; `MmContext::alloc` still
checks and returns `Err(MapError::Uninitialised)` on `u64::MAX` rather than
wrapping, because a wrapped id would alias silently and that is the class of bug
this whole document is about.

**Per CPU — `.bss`, no allocation, no lock class.** This is the tree's existing
`PerCpuAsids` (`mm/src/mmu/asid.rs:31-80`), moved, with names kept:

```rust
/// Sixteen: `0` (kernel) plus `1..=16` fits the 12-bit PCID space and leaves
/// bit 11 free for the KPTI user/kernel pair (§4.7).
pub const DYN_ASIDS_PER_CPU: usize = 16;

#[derive(Clone, Copy)]
struct AsidSlot {
    /// `0` means empty — the kernel master never occupies a dynamic slot,
    /// and `MmContextId::KERNEL` is `0`, so the two sentinels coincide.
    ctx_id: u64,
    /// Generation this CPU last flushed this slot at.
    tlb_gen: u64,
}

/// Mutated only by its owning CPU with interrupts disabled. Counters are
/// `AtomicU64` only so other CPUs can read them non-authoritatively — which
/// is what lets §4.10's `kcommand!` sweep every CPU without an IPI.
#[repr(C, align(64))]
struct PerCpuAsids {
    slots: [AsidSlot; DYN_ASIDS_PER_CPU],
    /// Index of the slot loaded last, or `u8::MAX` — forces a miss on the
    /// first switch after boot.
    last_loaded_slot: u8,
    /// Round-robin victim cursor.
    next_asid: u8,
    _padding: [u8; 6],
    hot_hits: AtomicU64,
    gen_refresh: AtomicU64,
    misses: AtomicU64,
    legacy: AtomicU64,
    /// **New.** Bumped on a declined `PerCpuSlot` borrow (§4.9).
    borrow_declined: AtomicU64,
}

static PER_CPU: [PerCpuSlot<PerCpuAsids>; MAX_CPUS] = {
    const INIT: PerCpuSlot<PerCpuAsids> = PerCpuSlot::new(PerCpuAsids::new());
    [INIT; MAX_CPUS]
};
```

Size: `16 slots × 16 B = 256`, plus `1 + 1 + 6` of index/padding, plus
`5 × AtomicU64 = 40` → **304 B, rounded to 320 by `align(64)`**. × `MAX_CPUS =
256` (`slopos-ostd/src/cpu/x86_64/pcr.rs:17`) = **80 KiB** of `.bss`, cache-line
aligned so two CPUs never share a line.

That is the size the tree already carries: today's `PerCpuAsids` is
`256 + 8 + 4×8 = 296`, which rounds to the *same* 320. `PER_CPU`
(`mm/src/mmu/asid.rs:78`) is `.bss` in the shipped kernel right now, unwired.
So this fix adds **literally zero** new `.bss` — the fifth counter fits in the
existing alignment padding. Worth stating because an 80 KiB static is the kind
of thing a reviewer reasonably challenges, and the answer is that it is already
there and already paid for.

#### 4.3a Correction to revision 1: the pool is 16, not 6

Revision 1 specified `DYN_PCIDS_PER_CPU = 6` and justified it as "the working-set
observation the mature implementations converged on", then admitted in its own
§9 that the number was "inherited judgement, not a SlopOS measurement". Both
halves were wrong to act on:

- The tree has already chosen **16** (`mm/src/mmu/asid.rs:31`), with a stated
  reason that is *architectural* rather than inherited: `0` plus `1..=16` fits
  the 12-bit field and leaves bit 11 clear for KPTI. Lowering it to 6 would be
  a behavioural change made by a document that had not noticed it was changing
  anything.
- Copying a specific tuning constant *because Linux picked it* is exactly the
  reasoning `AGENTS.md`'s licensing discipline warns against leaning on, and
  it is worse engineering besides: SlopOS's `MAX_PROCESSES` is 256
  (`abi/src/task.rs:28`) and its scheduler is not Linux's.

**Decision: keep 16.** The cost of the extra ten slots is bounded and
computable: the miss arm scans at most `DYN_ASIDS_PER_CPU` entries of 16 bytes
each, i.e. 256 bytes = 4 cache lines, contiguous and prefetch-friendly, on a
path that is already writing CR3 (a serialising instruction costing hundreds of
cycles). The scan is in the noise of the operation it precedes. The `hot_hits`
fast path (§4.5 step 6) skips the scan entirely on the common
switch-back-to-the-same-context case.

§9-D1 records how the number would be re-derived if it ever needs to be.

**Why `PerCpuSlot` and not a `SpinLock`.** `PerCpuSlot` is the tree's existing
runtime-checked exclusive borrow (`slopos-ostd/src/sync/per_cpu_slot.rs`),
requires an `&IrqDisabled<'_>` witness, and — decisively — **registers no lock
class**, so `check_lockdep_headroom.sh` does not move. A `SpinLock` here would
be wrong on the merits too: this state is touched only from the dispatch path
with interrupts already off, and taking a lock there would add an ordering edge
between the scheduler and the MMU that nothing needs. The unwired pool already
chose `PerCpuSlot` (`mm/src/mmu/asid.rs:74-80`), so this is a decision inherited
rather than made — but its *stated* reason no longer applies and the
replacement reason should be written down on the move. The comment there says
`PerCpuSlot` was chosen because "`forget_context_local` takes a caller-supplied
index, so nothing about the signature confines a caller to its own slot";
`forget_context_local` is deleted by this fix (§4.2, §4.6). The reason it stays
the right choice is the other hazard `per_cpu_slot.rs:9-12` names: **an IRQ
handler re-entering a slot its own CPU is mid-update on.** `select_for_activate`
runs with interrupts off, so that is currently unreachable — which is exactly
why the checked borrow is worth keeping rather than dropping to a bare
`UnsafeCell`: it is what turns a future violation of that assumption into a
declined borrow (§4.9) instead of aliasing UB in the trusted crate.

**Global feature state:**

```rust
/// Written once from `init_bsp`, read on every dispatch.
static PCID_ENABLED: AtomicBool = AtomicBool::new(false);
static INVPCID_AVAILABLE: AtomicBool = AtomicBool::new(false);
```

Both `Relaxed` on the read path: they are written before any AP is online and
before the first user `activate`, and the `BspToken` on `init_bsp` is what
witnesses that.

### 4.4 The selection token — how NOFLUSH stops being forgeable

```rust
/// A CR3 value's PCID and flush decision, minted only by
/// [`select_for_activate`] or by one of the two kernel-master constructors.
/// There is no public field and no public constructor taking a `bool`, so a
/// caller cannot set NOFLUSH without having gone through the pool that just
/// proved it safe.
#[derive(Clone, Copy, Debug)]
pub struct Cr3Selection {
    pcid: Pcid,
    no_flush: bool,
}

impl Cr3Selection {
    /// Kernel master with PCID 0. NOFLUSH only when PCIDE is on **and**
    /// PCID 0 is structurally reserved to the master, which it is: the
    /// dynamic pool issues `1..=DYN_ASIDS_PER_CPU` and never 0.
    ///
    /// Reads `PCID_ENABLED`, not live CR4. That is the same fact
    /// `VmSpace::activate:396` reads today, but from a mirror written once
    /// under a `BspToken` instead of a `mov %cr4` on every dispatch.
    pub(crate) fn kernel_master() -> Self {
        Self { pcid: Pcid::KERNEL, no_flush: PCID_ENABLED.load(Ordering::Relaxed) }
    }
    /// PCID 0, flushing. The pre-PCIDE and fail-closed path.
    pub(crate) fn kernel_flush() -> Self {
        Self { pcid: Pcid::KERNEL, no_flush: false }
    }
    #[inline] pub(crate) fn pcid(self) -> Pcid { self.pcid }
    #[inline] pub(crate) fn no_flush(self) -> bool { self.no_flush }

    /// Test-only inspection. `pub(crate)` is not enough for
    /// `slopos-ostd/tests/asid.rs`, which is an *integration* test and sees
    /// only the public API; gating on the existing `test-helpers` feature
    /// (`slopos-ostd/Cargo.toml:16`, auto-enabled for `cargo test` via the
    /// dev-dependency self-reference at `:33-35`) exposes it there without
    /// widening the kernel build's surface.
    #[cfg(any(test, feature = "test-helpers"))]
    pub fn parts_for_test(self) -> (Pcid, bool) { (self.pcid, self.no_flush) }
}
```

**Why `kernel_master` may set NOFLUSH at all.** Loading PCID 0 with NOFLUSH
preserves PCID 0's own cached entries, which are the kernel master's — and the
kernel master's leaves are stamped `GLOBAL`
(`boot/src/boot_memory.rs:93-110` → `mm/src/kernel_mappings.rs:214-245`), so
they survive regardless. The bit is therefore free of consequence for
correctness here and saves a flush on every kernel-task dispatch, of which
`sched/src/scheduler.rs:289`/`:354`/`:357` are three. This is a real behavioural
improvement over today: today `activate` sets NOFLUSH on the kernel master too,
but for the wrong reason ("is PCIDE on") rather than a reason that survives a
change of PCID policy.

`write_cr3_pcid` becomes:

```rust
/// # Safety
/// - `pml4_phys` must point to a 4 KiB-aligned, well-formed PML4 reachable
///   through the kernel HHDM.
/// - Kernel-half indices 256..512 must match the canonical master.
///
/// The PCID/NOFLUSH clause that used to live here is discharged by the type:
/// `sel` can only be minted by `mm::asid`, which owns the per-CPU binding.
pub(crate) unsafe fn write_cr3(pml4_phys: PhysAddr, sel: Cr3Selection) { ... }
```

Note what this does to `check_safe_contract_surface.sh`: the gate's baseline is
0 safe `pub fn`s carrying a `# Safety` section (`scripts/check_safe_contract_surface.sh:42`),
and this design adds none. The PCID obligation is expressed as a **mint-only
token**, which is exactly the list of sanctioned expressions in `AGENTS.md`
(`&IrqDisabled`, `&BspToken`, `Xcr0Mask`, `OneShotBuf`, …). The third bullet of
the old `write_cr3_pcid` contract (`cr3.rs:47-49`) — "if `pcid == Pcid::KERNEL`
and another PCID is currently loaded, choose `no_flush == false`" — becomes
unrepresentable rather than documented.

**`Cr3Value` gets the same treatment, and this is not optional.** `Cr3Value::new`
(`mm/src/mmu/cr3.rs:117`) is a **safe `pub fn` in a `#![forbid(unsafe_code)]`
crate taking `no_flush: bool`**, and `with_noflush` (`:135`) sets the bit on an
existing value. Leaving those in place while sealing `write_cr3_pcid` would
seal the front door and leave the back one open: any `mm` caller could still
mint a NOFLUSH CR3 value. Since `write_cr3_value` is deleted along with them
(§4.2), what remains of `Cr3Value` is a pure decoder — `from_raw` + the getters
+ the `Debug` impl — with **no constructor that takes a flush decision at all**.

### 4.5 The selection algorithm

Called from `VmSpace::activate`. Every call site has interrupts off already
(§1.6's table), but none holds an `IrqDisabled<'_>` to pass, so the pool mints
its own via the tree's existing re-entrant helper rather than taking one as a
parameter:

```rust
/// `cpu` is `get_current_cpu()`; the caller is on that CPU.
///
/// Interrupts are off at every call site (eight of the nine reach `activate`
/// under a `SpinLockGuard`, which `cli`s; the ninth is BSP init under a
/// `BspToken`), but the witness is minted here rather than
/// threaded through `VmSpace::activate`, whose signature must not change:
/// five of the nine sites are method calls on a lock-guard temporary with no
/// scope to wrap. `IrqDisabled::with` is re-entrant, so this costs a
/// `pushfq`/`cli`/`popfq` and re-enables nothing.
///
/// `pub`, not `pub(crate)`: `slopos-ostd/tests/asid.rs` is an integration test
/// and sees only the public API (R3-5).
pub fn select_for_activate(cpu: usize, ctx: &MmContext) -> Cr3Selection
```

Steps 1–4 run before the borrow; 5–8 inside `with_asid_state`'s closure, which
is the moved `mm/src/mmu/asid.rs:272` helper with its `expect` replaced by the
fail-closed arm of step 5.

**R3-2: step order is load-bearing, and revision 2 had it wrong.** Revision 2
listed the `PCID_ENABLED` check as step 1 and the `cpu >= MAX_CPUS` bounds
check as step 2, then wrote in step 2's own parenthetical *"the moved code
checks this first for the same reason; keep the order"* — contradicting itself
in the same sentence. The order matters because step 1 is **not** a pure
return: it bumps the `legacy` counter, which lives in `PER_CPU[cpu]`. The tree
gets this right (`mm/src/mmu/asid.rs:208-215`: the `cpu_id >= MAX_CPUS` arm
precedes the `!pcid_enabled()` arm, and only the latter touches
`with_asid_state`). Implementing revision 2's stated order would index a
256-entry array with an unchecked `cpu` on a legacy machine — an out-of-bounds
panic in the trusted crate on the dispatch path. Corrected below; the bounds
check is step 1.

1. `if cpu >= MAX_CPUS { return Cr3Selection::kernel_flush(); }` — fail closed,
   **before any `PER_CPU[cpu]` index**, including the counter bumps in the
   steps below. This is a bounds check, not a policy.
2. `if !PCID_ENABLED { legacy += 1; return Cr3Selection::kernel_flush(); }`
   A CR3 load with PCID 0 and no NOFLUSH is exactly the legacy behaviour. The
   counter bump goes through `with_asid_state`, which is why step 1 precedes
   it.
3. `if ctx.id().is_kernel() { return Cr3Selection::kernel_master(); }`
   No counter, no borrow — the kernel master must not consume a dynamic slot
   (§4.3's R3-3 table, T7).
4. `let gen = ctx.tlb_gen.load(Ordering::Acquire);`
   **Read before the CR3 write, recorded after.** See the ordering rule below.
5. Borrow the CPU's slot with `PerCpuSlot::with_mut`. On `None`, bump
   `borrow_declined`, `debug_assert!(false, ...)`, and return
   `Cr3Selection::kernel_flush()`. This is a **deliberate change from the moved
   code**, which does `.expect("asid: per-CPU slot already borrowed")`: that
   expect was written for a function nothing called. On the dispatch path with
   interrupts off, a panic is a machine-wide halt, and the fail-closed answer
   is available and merely slower. The counter plus §4.10's `kcommand!` make
   the condition visible instead of silent.
6. **Hot path.** If `last_loaded_slot < DYN_ASIDS_PER_CPU` and
   `slots[last_loaded_slot].ctx_id == ctx.id().raw()`:
   - `tlb_gen == gen` → `hot_hits += 1`; return `(pcid(last), no_flush = true)`.
   - else fall through to the scan, which will find the same slot and take its
     stale arm. (The moved code does exactly this; the fallthrough is not a
     bug.)
7. **Scan.** For `i in 0..DYN_ASIDS_PER_CPU`, if `slots[i].ctx_id == ctx.id().raw()`:
   - `tlb_gen == gen` → `hot_hits += 1`; `last_loaded_slot = i`; return
     `(pcid(i), true)`.
   - `tlb_gen != gen` → stale. Call `flush_pcid(pcid(i))`, set
     `slots[i].tlb_gen = gen`, `gen_refresh += 1`, `last_loaded_slot = i`,
     return `(pcid(i), true)`.
     `flush_pcid` (moved, `mm/src/mmu/asid.rs:165`) already handles the
     no-`INVPCID` case correctly and non-obviously: it falls back to
     `flush_local_all_contexts()`, **not** to a non-NOFLUSH CR3 load, because
     with `CR4.PCIDE` set a CR3 reload drops only the tag it loads and `pcid(i)`
     is generally not the tag currently in CR3. Revision 1's "return
     `(pcid(i), no_flush = false)` and let the CR3 load do the same job" was
     wrong *here* — it is right in the miss arm (step 8), where the PCID being
     refreshed **is** the one about to be loaded, and wrong in this arm only
     because this arm may run without reaching a CR3 write to that tag at all.
     Keep the tree's fallback. It is over-broad (it flushes every context, not
     one) but correct, and it only runs on hosts lacking `INVPCID`.
8. **Miss.** `let v = next_asid; next_asid = (v + 1) % DYN_ASIDS_PER_CPU;`
   If `slots[v].ctx_id != 0`, the moved code calls `flush_pcid(pcid(v))` here.
   **That call is redundant and should be deleted on the move**: this arm
   returns `no_flush = false`, and a non-NOFLUSH CR3 load invalidates precisely
   the PCID being loaded, which is `pcid(v)`. Deleting it removes an `INVPCID`
   (or, on a host without one, a whole-CPU all-context flush) from every cold
   dispatch. T2 pins the `no_flush == false` that makes the deletion safe.
   Then `slots[v] = AsidSlot { ctx_id: ctx.id().raw(), tlb_gen: gen };`
   `last_loaded_slot = v; misses += 1;` return `(pcid(v), no_flush = false)`.

`pcid(i)` is `Pcid::new_dynamic(i)` = `i + 1`, so PCID 0 is never issued and
bit 11 is never set (see §4.7).

**The ordering rule, which is the correctness core.** `gen` is read *before*
CR3 is written and stored into the slot afterwards. If a remote CPU bumps
`tlb_gen` concurrently, this CPU records the *older* value, so the next activate
sees a mismatch and flushes — a spurious flush, which is safe. Recording the
*newer* value would claim to have flushed at a generation it never flushed at,
losing an invalidation. Every store to `tlb_gen` is `Release` and every load
`Acquire`, pairing the page-table write that preceded the bump with the CR3
write that follows the load.

### 4.6 The invalidation side, and the remote-store insight

```rust
impl MmContext {
    /// Publish that a cached translation for this context may now be stale.
    /// Callable from any CPU, from IRQ context, under any lock: one atomic
    /// increment, no allocation, no wait.
    #[inline]
    pub fn bump_tlb_gen(&self) { self.tlb_gen.fetch_add(1, Ordering::AcqRel); }
}
```

Bumped from exactly one place: `CursorMut::drop`
(`slopos-ostd/src/mm/vm_space.rs:1106-1112`), alongside the existing
`generation` bump, when the cursor performed an `unmap` or a `protect`.

`map` (absent → present) deliberately does **not** bump, and this is a
documented-behaviour argument rather than an optimisation: SDM §4.10.2.3 states
the processor does not cache translations for a linear address whose paging
entries are marked not-present, so nothing stale exists to invalidate. The tree
already relies on exactly this reasoning and already writes it down —
`mm/src/kernel_mappings.rs:66-69`: *"No TLB invalidation on the map side: the
cursor refuses to overwrite a present leaf, so every kernel-half map takes the
entry from not-present to present, and x86-64 architecturally caches no
translation for a not-present entry (SDM Vol. 3A §4.10.2.3)."* This design
inherits that argument rather than introducing it, and the `Overlap` guard it
leans on is the one `verification/proofs/vm_space_cursor.rs:322` machine-checks.

The cursor therefore needs two dirty bits rather than one. Precisely, against
the six `self.dirty = true` sites in `slopos-ostd/src/mm/vm_space.rs`:

| Site | Method | `dirty` | `invalidating` |
|---|---|---|---|
| `:706` | `map` | yes | **no** |
| `:777` | `map_kernel` | yes | **no** |
| `:845` | `map_io` | yes | **no** |
| `:963` | `unmap` inner (present → absent) | yes | **yes** |
| `:1043` | `protect` (flags narrowed in place) | yes | **yes** |

(The sixth `dirty` write is `:349`'s initialiser, `dirty: false`.) The two
`invalidating` sites are exactly the two that already call
`flush_leaf_local::<S>(self.cur)` immediately above the assignment — which is
the local half of the same obligation, and a useful cross-check for the
implementer: **if the line above it is a local invalidation, the bit is set.**

This is the one place where getting the rule wrong is silent, so it should
carry the SDM citation as a comment; it is exactly the "hardware/spec quirk"
case `AGENTS.md` exempts from the no-comments rule.

**Why the bump is itself a remote shootdown.** A CPU not currently running
context C has, by construction, not yet performed the activate that will read
`tlb_gen`. Whenever it does return to C it takes step 7's stale arm or step 8's
miss arm, and either way it flushes before using a single cached entry. So the
bump alone — a plain atomic store, no IPI, no wait — covers **every CPU that is
not currently running the context**. That is the piece §1.5 is missing, and it
is what makes `notify_mm_switch`'s mask narrowing sound instead of a bug.

**What the bump does not cover, and must not be claimed to.** A CPU that *is*
currently running C does not re-read `tlb_gen` — it is not activating. That CPU
still needs the IPI, and `targeted_flush_request` still sends it, because that
CPU is in the mask. The division of labour is exact:

| Target CPU | Covered by |
|---|---|
| currently running C | the existing IPI, via `info.cpumask` |
| not running C, will return to it | `tlb_gen` bump, checked at its next `activate` |
| not running C, never returns (context destroyed) | `mm::mmu::quiesce` — frame reuse is already gated on every online CPU performing an all-context invalidation |

The third row is why this design needs **no** `forget_context` broadcast, and
why the dead `forget_context_local` can simply be deleted. A destroyed
context's id is 64-bit and never recycled, so a stale slot entry can never be
matched by a future context; it is inert until evicted, and the frames its
entries pointed at cannot be reused until quiesce says every CPU flushed
(`mm/src/mmu/quiesce.rs:12-18`).

### 4.7 PCID space partition, reserved now for KPTI

```rust
impl Pcid {
    pub const KERNEL: Pcid = Pcid(0);
    /// Bit 11. When KPTI is enabled, the user page-table CR3 for a context
    /// uses `kernel_pcid | USER_PT_BIT`, so the two halves of one address
    /// space never share a tag and a syscall's CR3 pair can both be NOFLUSH.
    pub const USER_PT_BIT: u16 = 0x800;
    #[inline] const fn new_dynamic(slot: usize) -> Self { Pcid(slot as u16 + 1) }
}
```

`DYN_ASIDS_PER_CPU = 16` issues `1..=16`; bit 11 is structurally clear, so
`kpti.rs` can be turned on later without renumbering anything or revisiting
this module. A `const _: () = assert!(DYN_ASIDS_PER_CPU < 0x800);` in the
module pins it, and one of the tests (§6, T10) asserts it at run time so a
future widening of the pool fails loudly rather than colliding with the user-PT
tag.

### 4.8 Interaction with each existing subsystem

- **TLB shootdown (`mm/src/tlb.rs`).** Unchanged in shape. `flush_local_all_contexts`
  moves into OSTD with its `INVPCID` type-3 / `CR4.PGE` toggle logic intact —
  its existing doc comment (`mm/src/mmu/asid.rs:172-186`) is already correct and
  should move with it verbatim, since it is first-party prose. `mm/src/tlb.rs:444`
  (inside `flush_tlb_local_full`) and `mm/src/mmu/quiesce.rs:125` change import
  path only. The mask-narrowing in `notify_mm_switch` becomes *justified* rather
  than merely present, and should gain a one-line comment pointing at the
  `tlb_gen` mechanism.
- **R3-7: `try_flush_asid` keys on a CR3 value, and this design changes what a
  CR3 value means.** Revision 2 did not mention this path at all. It is worth
  stating because it looks like a break and is not. `mm/src/tlb.rs:896-899`:

  ```rust
  /// `asid` is a CR3 value; a CPU flushes only if its live CR3 matches it.
  pub fn try_flush_asid(asid: u64) -> TlbResult {
      let current_cr3 = cpu::read_cr3();
      let local_needs_flush = (current_cr3 & !0xFFF) == (asid & !0xFFF);
  ```

  Today a `VmSpace`'s CR3 is a constant — same PML4, same PCID, forever — so
  "does my live CR3 match" is a stable question. After this fix the PCID field
  varies per CPU and over time, so the *full* CR3 value is no longer a stable
  identity for an address space. **The comparison masks off the low 12 bits
  (`& !0xFFF`), which is exactly the PCID field**, so it compares PML4
  physical addresses only and is unaffected. Verified against the callers:
  `flush_asid` is reached from `mm/src/mmu/shootdown.rs:5` (a re-export) and
  from `mm/src/tests/tlb_tests.rs:89,94,435`, and every one passes either `0`
  or a synthesised value — no production caller passes a real CR3. **No change
  required.** The implementer should nonetheless not "tidy" that mask away, and
  the comment on `:896` should be reworded from "`asid` is a CR3 value" to name
  the PML4 address, since after this fix "asid" is actively misleading there.
- **`mprotect` (`mm/src/process_vm.rs:2518`).** No source change; it calls
  `CursorMut::protect`, which now bumps `tlb_gen` on cursor drop. The §1.5 hole
  closes without the call site being touched. This is the strongest single
  argument for putting the bump in the cursor rather than in `mm`: every
  page-table mutation in the kernel already goes through it, so no caller can
  forget.
- **Quiesce (`mm/src/mmu/quiesce.rs`).** Untouched. Its epoch remains the
  authority on frame reuse; the PCID pool takes no responsibility for freed
  frames. Note the two are complementary, not redundant: quiesce answers "may
  this *frame* be handed to someone else", the generation answers "may this
  *CPU* trust its cached entries for this context".
- **LUF (`mm/src/mmu/luf.rs`).** Untouched behaviourally. `on_activate` now
  receives `ctx.id().raw()` instead of an `mm_ctx_handle` that was a copy of the
  same number; `VmSpace::set_mm_ctx_handle`/`mm_ctx_handle` and the whole
  `alloc_mm_context_id` plumbing in `process_vm.rs` disappear.
- **Quota accounting.** No account is charged; the fix allocates nothing. The

### 4.9 Failure paths, enumerated

| Condition | Behaviour | Rationale |
|---|---|---|
| PCIDE off (unsupported, or errata) | `(Pcid::KERNEL, no_flush = false)` | Legacy behaviour exactly. NOFLUSH with `PCIDE = 0` is `#GP`. |
| `INVPCID` unavailable, stale generation | `flush_pcid` falls back to `flush_local_all_contexts()` (all-context, non-global), then `(pcid, no_flush = true)` | **Corrected from revision 1**, which said `(pcid, no_flush = false)` and let the CR3 load do it. That is wrong in this arm: with `CR4.PCIDE` set, a CR3 load invalidates only the tag it loads, and the tag being refreshed here is not necessarily the one in CR3. The tree's existing fallback (`mm/src/mmu/asid.rs:165-171`) is over-broad but correct. Keep it. |
| `cpu >= MAX_CPUS` | `(Pcid::KERNEL, false)` | Fail closed. Checked **before** indexing `PER_CPU`, so it is a bounds check and not merely a policy. |
| `MmContextId::KERNEL` (the master) | `(Pcid::KERNEL, no_flush = PCID_ENABLED)` | The master's leaves are `GLOBAL`, so its entries survive either way; the bit saves a flush per kernel-task dispatch. §4.4. |
| `PerCpuSlot` borrow declined | `(Pcid::KERNEL, false)`, counter bumped, `debug_assert!` | A panic on the dispatch path with IRQs off halts the machine; the safe answer is available and merely slower. The counter and the `kcommand!` make the condition visible instead of silent. |
| `MmContextId` space exhausted (2⁶⁴) | `VmSpace::new` returns `Err(MapError::Uninitialised)` | Refuse rather than wrap. A wrapped id aliases silently, which is the class of bug being fixed. Reusing this existing variant rather than adding one keeps every `match` on `MapError` exhaustive without edits — relevant because `slopos-ostd/src/user/copy.rs:146-151` matches it with a catch-all that would silently absorb a new variant, and `VmSpace::new`'s callers (`mm/src/process_vm.rs:1498`, `:2856`) already log-and-bail on any `Err`. |
| `tlb_gen` overflow (2⁶⁴) | Wraps. | A generation only needs to *differ*; the only failure is the 2⁻⁶⁴ chance a CPU's recorded gen coincides after exactly 2⁶⁴ bumps of one context. Documented, not defended against. |

### 4.10 Diagnostics

One `kcommand!` in `mm/` (OSTD defines the registry and must not name an entry
— `AGENTS.md`), printing per-CPU `hot_hits / gen_refresh / misses / legacy /
borrow_declined` and the sixteen slot bindings. This is how a future stale-TLB
report gets triaged without a rebuild, and it is the reason the counters exist
at all. Not `KCMD_DESTRUCTIVE` — `KCMD_INFORMATIONAL`, like `mm/src/kconsole.rs:11`.

Two constraints on the implementation, both load-bearing:

- It reads peer CPUs' state via `PerCpuSlot::try_with_ref`, **not** `with_mut`
  — `try_with_ref` is the shared-borrow accessor
  (`slopos-ostd/src/sync/per_cpu_slot.rs:99`) and returns `None` rather than
  blocking if the owning CPU is mid-update. A `kcommand!` that could decline a
  CPU's row is correct; one that could wedge on a peer is not.
- The registration lives in `mm/src/kconsole.rs`, not in OSTD, because OSTD is
  linked into userland binaries whose linker script brackets no
  `.kconsole_registry` section (`AGENTS.md`). The pool's stats therefore need a
  `pub fn` accessor in OSTD that `mm` calls:

  ```rust
  #[derive(Clone, Copy)]
  pub struct AsidStats {
      pub slots: [(u64, u64); DYN_ASIDS_PER_CPU],   // (ctx_id, tlb_gen)
      pub last_loaded_slot: u8,
      pub hot_hits: u64,
      pub gen_refresh: u64,
      pub misses: u64,
      pub legacy: u64,
      pub borrow_declined: u64,
  }

  pub fn stats_for_cpu(cpu: usize) -> Option<AsidStats>;
  ```

  **R3: the size, stated rather than gestured at.** `16 × 16 = 256` bytes of
  slots + 5×8 counters + 1 index, padded = **304 B**, and the caller holds one
  at a time inside the per-CPU loop. Revision 2 said only "if
  `check_stack_sizes.sh` moves, look here first", which is not a design. The
  bound: `run_asid` must **not** collect a `[AsidStats; MAX_CPUS]` — that is
  78 KiB of frame and instant gate failure — but call `stats_for_cpu` inside
  the loop body and print each row before the next iteration, so exactly one
  `AsidStats` is live at a time and the frame stays ~320 B against the 2048 B
  cap. Written as a `for cpu in 0..MAX_CPUS { if let Some(s) = stats_for_cpu(cpu) { … } }`
  this is the natural shape; the failure mode is only reachable by someone
  deliberately gathering first and printing second.

  `stats_for_cpu` is unconditionally `pub` — the `kcommand!` needs it in a
  production build, so it is **not** feature-gated (§6-T8 relies on this too).

A new `kcommand!` needs an unused key. Re-grepped for R3 with
`grep -rn "key = b'" --include=*.rs . | grep -v builddir | sort -t\' -k2`, the
complete taken set is: `b` (`boot/src/kconsole.rs:17`), `d` `h` `k` `p`
(`core/src/kconsole.rs:31,15,23,39`), `m` (`mm/src/kconsole.rs:9`), `n`
(`net/src/kconsole.rs:28`), `o` (`boot/src/kconsole.rs:9`), `q`
(`sched/src/quota_console.rs:17`), `s` `t` `w` `x`
(`sched/src/kconsole.rs:32,16,24,40`), plus `y`/`z`
(`core/src/tests/kconsole_tests.rs:32,24`, tests only). Revision 2's list
omitted `n` — harmless, since it did not pick `n`, but the list is now
exhaustive. **`a`** is free and mnemonic for asid.

## 5. Migration order

The refactor must not have a window in which PCIDE is on and the pool is not
wired, because that window is the current bug.

**Step 0 (prerequisite, blocking — see §9-D4).** Audit the `#PF` handler for
spurious-fault tolerance and record the finding. This is now step *zero* rather
than a pre-step-5 checklist item, because if it fails, §4.6's "`map` does not
bump" rule changes and T11 changes with it — which would be a design change
discovered after the design was implemented. The audit itself is in §8.3 and is
**already done in this revision**; step 0 is now only "re-confirm nothing
changed", which is a `git log` on four files.

1. **`git mv mm/src/mmu/asid.rs slopos-ostd/src/mm/asid.rs`**, plus the type
   merge: pull `MmContextId` out of `mm/src/mmu/cr3.rs` into it, and drop the
   `super::cr3` / `super::errata` / `super::rar` / `slopos_arch` imports for
   OSTD-local paths.

   already lives in `slopos-ostd`". That is true of `IrqDisabled`, `Cr4Flags`,
   `read_cr4`, `write_cr4`, the CPUID constants, `MAX_CPUS`, `PerCpuSlot`,

   - `super::rar::backend().name()` (`:144`) — an `mm` trait object; the log

   Nothing changes at runtime.
2. Switch `VmSpace` to `MmContext` and route `activate` through
   `select_for_activate`. With `PCID_ENABLED` false this is behaviourally

   correct and strictly safer than today. Delete `alloc_pcid`/`NEXT_PCID`/
   `reset_pcid_counter_for_test`/`pcid()`/`set_mm_ctx_handle`/`mm_ctx_handle`

   `:490`, `:588`, `:632` — in the same commit (§6); the import at `:11` is not
   optional, `warnings = "deny"` (`Cargo.toml:53`) fails the build on an unused
   one.
   **This is the commit that closes the headline finding.** PCID 0 can no
   longer be handed to a user space, because no user space has a PCID.
3. Add the second dirty bit and the `tlb_gen` bump to `CursorMut`. Still inert
   — nothing reads `tlb_gen` while `PCID_ENABLED` is false.
4. Delete `mm/src/mmu/asid.rs`; repoint `boot/src/boot_memory.rs:22-25` and
   `boot/src/smp.rs:48` at the OSTD init, and `mm/src/tlb.rs:444` +

5. Flip `init_bsp` to compute and store the real verdict, re-enabling

are the performance recovery. If step 5 ever needs to be reverted in a hurry,
reverting it lands on step 4's no-PCID kernel, which is the `nopcid` machine

## 6. Tests

`slopos-ostd` has a host-side integration test suite
(`slopos-ostd/tests/vm_space.rs` is the model: it stubs `FrameAlloc`,
`META_SLOTS` and the HHDM offset behind a `OnceLock<Mutex<()>>` setup gate).
The pool is pure safe Rust with no hardware dependency, and the three
instructions it can reach are already host no-ops in the tree:
`invpcid` (`slopos-ostd/src/cpu/x86_64/tlb.rs:51`, body under
`#[cfg(target_os = "none")]`), `read_cr4`/`write_cr4`
(`control_regs.rs:187,208`, backed by a `MOCK_CR4` static off-target) and the
CR3 write (`cr3.rs:56-75`, `MOCK_CR3`). So the host tests need **no new
mocking layer** — the seams exist. Two things they *do* need, and the
implementer should know before starting:

- `PCID_ENABLED`/`INVPCID_AVAILABLE` are set only by `init_bsp`, which reads
  real CPUID. The host tests need a `#[cfg(any(test, feature = "test-helpers"))]`
  setter — `pub fn force_pcid_state_for_test(pcid: bool, invpcid: bool)` —
  alongside the existing `reset_*_for_test` helpers OSTD already carries
  (`vm_space.rs:207`, `:212`, `:227`).
- **R3-4: the pool itself must be resettable, and revision 2 omitted this.**
  `PER_CPU` is one `static` shared by every test in the process. T1 drives 5000
  contexts through CPU 0's slots; T2 then asserts that the
  `DYN_ASIDS_PER_CPU + 1`-th activation misses. If T1 ran first, every slot is
  already occupied and T2's arithmetic about which slot the round-robin cursor
  lands on is wrong — and `cargo test` runs integration tests on threads in one
  process, in nondeterministic order, so the contamination is *intermittent*.
  A flaky test on the pin for this finding is worse than no test. Required, in
  the same file as the pool:

  ```rust
  /// Reset one CPU's slot array, cursor and counters to their `const` initial
  /// state. Host tests share one process and one `PER_CPU`.
  #[cfg(any(test, feature = "test-helpers"))]
  pub fn reset_pool_for_test(cpu: usize);
  ```

  Every test in `slopos-ostd/tests/asid.rs` calls `reset_pool_for_test(0)` and
  `force_pcid_state_for_test(true, true)` as its first two statements, under
  the same `OnceLock<Mutex<()>>` setup gate `slopos-ostd/tests/vm_space.rs`
  already uses — which serialises them, so the reset is not itself racy. The
  gate is not optional here: without it two tests can interleave between the
  reset and the assertion.
- **R3-5: `select_for_activate`, `MmContext`, `Cr3Selection::parts_for_test`,
  `stats_for_cpu`, `MmContextId` and `DYN_ASIDS_PER_CPU` must all be reachable
  from an integration test.** `slopos-ostd/tests/*.rs` are separate crates that
  link the library and see only `pub` items — `pub(crate)` is invisible to them.
  Revision 2 specified `select_for_activate` as `pub(crate)` and
  `Cr3Selection`'s accessors as `pub(crate)`, which makes T1, T2, T3, T5, T6,
  T7 and T10 fail to compile. Resolution: `select_for_activate`, `MmContext`,
  `MmContextId`, `AsidStats`, `stats_for_cpu`, `DYN_ASIDS_PER_CPU` and
  `PcidVerdict` are `pub`; `Cr3Selection` is `pub` as a type but its `pcid()` /
  `no_flush()` accessors and its two constructors stay `pub(crate)`, with
  `parts_for_test` (feature-gated, already specified in §4.4) as the test
  window. That keeps the mint-only property — a `pub` type with no `pub`
  constructor cannot be forged from outside the crate — while letting the tests
  observe the decision. `write_cr3` stays `pub(crate)`: no test needs it.
- `PerCpuSlot::with_mut` needs an `IrqDisabled`, which `IrqDisabled::with`
  mints on the host too (`interrupts.rs:60-63` mocks RFLAGS via `MOCK_RFLAGS`).
  No special case.

#### T4's plumbing, in full

Revision 1 wrote T4 as a one-line sketch ending "→ expect `SIGSEGV`". It is not
implementable as written, and the reason is worth stating because it changes
the cost of this test from "write a file" to "add a syscall wrapper":

**There is no userland `mprotect`.** `SYSCALL_MPROTECT = 94` exists
(`abi/src/syscall/numbers.rs:146`), the handler exists
(`core/src/syscall/memory_handlers.rs:85`), and `slibc`'s PAL trait implements

exposes `brk`, `sbrk`, `memfd_create`, `ftruncate`, `mmap`, `munmap`, `close`
and **not** `mprotect`, and nothing under `userland/`, `appkit/` or
`slopos-rt/` calls it (`grep -rn mprotect` over those trees: no hits). So T4
needs, in the same commit:

1. `userland/src/syscall/memory.rs` — add
   `pub fn mprotect(addr: u64, length: u64, prot: u64) -> i32`, wrapping

3. `userland/Cargo.toml` — a `[[bin]]` stanza.
4. `scripts/build_userland.sh` — add to the `--bin` list (≈`:76`), the copy

The test body, given that plumbing:

```text
main thread:
  cpus = get_current_cpu-observable count; if < 2 -> print SKIP, exit 0
  page = mmap(anon, RW, 1 page)
  set_cpu_affinity(0, 1 << 0); yield; assert get_current_cpu() == 0
  *page = 0x41                       // fills CPU 0's TLB with a writable entry
  spawn thread T:
      set_cpu_affinity(0, 1 << 1); yield
      if get_current_cpu() != 1 { record PRECONDITION_FAILED; signal; return }
      mprotect(page, 4096, PROT_READ)
      signal main
  main: wait for T's signal
  set_cpu_affinity(0, 1 << 0); yield; assert get_current_cpu() == 0
  *page = 0x42                       // must fault
  -> if this line returns, the test FAILS
```

The write must fault, so the process dies rather than returning a value; the
`utest!` harness grades a binary by its exit status
(`core/src/exec/utest.rs`), so the test is inverted relative to the others:
**the child is expected to die**, and the parent-side expectation is a
non-zero/faulted exit. Two ways to express that, and the implementer must pick
one rather than discovering the problem mid-write:

- **(a)** Install a `SIGSEGV` handler and `_exit(0)` from it. `userland/` already
  has `signal_handler_test` and `spin_signal_test` binaries, so the machinery
  exists and this keeps the utest's exit-status contract ordinary.
- **(b)** `fork()` and have the parent `waitpid` the child, asserting the child
  faulted. `userland/src/syscall/process.rs:127,203` provide both.

**(a) is the recommendation** — it keeps the whole test on one address space,
which matters because `fork` in (b) creates a *second* context and COW-marks
the page (`mm/src/process_vm.rs:2913` broadcasts a full `flush_all()` after the
COW pass), and that broadcast would mask the very staleness the test is trying
to observe. That interaction is exactly the kind of thing §1.5 says makes COW
unaffected by this bug, and it would make (b) a vacuous pass.

## 8. Residual risk — what this does NOT close

1. **PCID is not an isolation boundary.** Nothing here mitigates Meltdown or
   any speculative-execution channel. `mm/src/mmu/kpti.rs` remains scaffolding
   with `KPTI_ENABLED == false`, and the ring-transition assembly still performs
   a single CR3 load. After this fix, user translations are *deliberately
   preserved* across a syscall, which is the whole point and is also precisely
   what PTI exists to undo. This fix makes PTI affordable; it does not make it
   unnecessary, and the tree should not read a green PCID pool as progress on
   that axis.
2. **A CPU currently running the context still needs the IPI.** The `tlb_gen`
   store is only read at activate. A CPU spinning in kernel mode inside the
   target context — or in userland in it — never re-reads it. The existing
   `targeted_flush_request` path remains load-bearing and is not made redundant.
   Anyone reading "the bump is a remote shootdown" as "we can delete the IPI"
   will reintroduce a worse version of this bug.
3. **Spurious faults on absent→present — audited, and the tolerance is there.**
   Not bumping on `map` is correct per SDM §4.10.2.3, but it presumes the fault
   path tolerates a spurious `#PF` arriving after another CPU installed the
   mapping. Revision 1 left this unaudited and made it a blocking prerequisite.
   **It is now audited** — the tolerance exists, in two independent places:

   - `mm/src/demand.rs:74-77` — `handle_demand_fault` re-walks before doing
     anything: `let existing_phys = ostd_virt_to_phys_4kb(...); if
     !existing_phys.is_null() { return Ok(()); }`. A fault on a page another
     CPU already populated returns `Ok(())`, which
     `mm/src/page_fault.rs:82` grades as `FaultOutcome::Resolved`, and the
     faulting instruction is retried. That is precisely the spurious-fault
     path, and it is already handled — not incidentally, but with a re-read
     whose only purpose is this.
   - `mm/src/cow.rs:41-43` — `handle_cow_fault` re-reads the PTE flags and
     returns `NotCowPage` if the COW bit is gone, and `resolve_single_ref`
     (`:47`) handles the "someone else already dropped the refcount" race.

   The residual is narrower than revision 1 stated, and it is **pre-existing**
   rather than introduced: a spurious fault on an address in **no** VMA, or in
   a VMA that is neither demand-paged-anonymous nor COW, falls through to
   `FaultOutcome::Fatal(TaskFaultReason::UserPage)` (`page_fault.rs:92`) and
   kills the task. But such a fault cannot be spurious in the sense that
   matters here, because this design only declines to bump on `map`, and `map`
   into a region with no VMA is not a thing the kernel does. **Step 0 of §5 is
   therefore a re-confirmation, not an investigation** — `git log` those four
   files and check nothing changed. It is no longer a blocking unknown.
4. **Thrash beyond sixteen slots is a correctness-safe cliff, not a solved
   problem.** Seventeen-plus address spaces alternating on one CPU flush on
   every switch, i.e. degrade to the minimal patch. Nothing bounds or reports
   this except the `misses` counter and the `kcommand!`. `MAX_PROCESSES` is 256
   (`abi/src/task.rs:28`), so a pathological workload can trivially arrange it.
   Perf, not safety. (Revision 1 said "six" here, following its own incorrect
   pool size — see §4.3a.)
5. **`INVPCID`-less hosts degrade.** Where `INVPCID` is absent the
   stale-generation arm falls back to a non-NOFLUSH CR3 load, which is correct
   but forfeits the "refresh one context, keep the rest" benefit. Some older
   hypervisor configurations expose PCID without INVPCID.
6. **The Alder/Raptor Lake erratum path is untested on real silicon.**
   `mm/src/mmu/errata.rs` disables PCID wholesale on those parts, so they take
   the legacy path; nobody has run it on an affected CPU, and the detection is
   family/model-based with a `false` default for unreadable CPUID. An affected
   part that misreports its model gets PCID enabled.
7. **T4's determinism.** The end-to-end migration test depends on the scheduler
   actually placing the two threads on different CPUs. On a single-CPU QEMU run
   it degenerates to a same-CPU test and passes vacuously. It needs the SMP
   tests kernel and must assert its own preconditions — that the two touches
   really happened on different `get_current_cpu()` values — and report `Skip`
   rather than `Pass` when they did not. A vacuous pass on the test that pins
   the escalation would be worse than no test.
   The mechanism to make this deterministic exists and T4's sketch uses it:
   `set_cpu_affinity` with a strict single-bit mask, exactly as
   `userland/src/bin/tests/percore_reactor_test.rs:75-77` does, with its stated
   reason — *"Strict pin: keeping CPU 0 in the mask would let every worker fall
   back to it, hiding the cross-core re-dispatch path"* — which is the same
   hazard T4 faces. Follow that file's pattern rather than inventing one.
   Residual after that: `set_cpu_affinity` + `yield` is a request, and T4 must
   *verify* placement with `get_current_cpu()` rather than assume it, which is
   why the sketch checks and skips.
8. **Weak-memory reasoning is audited, not proved.** The Acquire/Release pairing
   between the page-table write, the `tlb_gen` bump, the pre-CR3 read and the
   post-CR3 slot store is argued in §4.5 and checked by tests that cannot
   observe reordering on x86-TSO. Verus does not model it. This joins the
   existing list in `verification/STATUS.md` of things that are reasoned about
   rather than machine-checked.
9. **Nothing here fixes SLOPOS-2026-0020 (`execve` is not an address-space
   boundary).** A context that survives `execve` keeps its `MmContextId` and its
   per-CPU bindings, which is *correct* for this mechanism — the tables really
   are the same tables — and is exactly why 0020 is a separate finding. The two
   fixes are independent; neither masks the other.
10. **The interaction with SLOPOS-2026-0010 (pid ceiling) noted in the ledger
    disappears rather than being fixed.** The ledger says the pid fix must land
    alongside this one because the pid ceiling is hit before the 4096th PCID.
    After this fix, PCIDs are not a per-process resource at all, so the coupling
    is gone — but the pid finding stands on its own merits and this document
    makes no claim about it.

## 9. Decisions

Revision 1 ended with four open questions. A proposal that claims to be
implementable without further design work cannot have any, so each is now
resolved, with the reasoning that resolved it. Nothing below is left to the
implementer's discretion.

**D1 — Pool size: `DYN_ASIDS_PER_CPU = 16`. Keep the tree's number.**
Revision 1 proposed lowering it to 6 on inherited judgement; §4.3a explains why
that was wrong twice over (the tree has a number, with an *architectural*
rationale, and "Linux picked 6" is not a reason SlopOS should act on). The
number is not re-derived as part of this fix.
If it ever needs re-deriving, the mechanism is already specified rather than
asked about: the four per-CPU counters are `AtomicU64` **specifically so a
foreign CPU can read them** (`mm/src/mmu/asid.rs:46-47`'s comment says so), and
§4.10's `kcommand!` prints them. A boot-log line is **not** added: the
counters are a diagnostic, not a ratchet, and `AGENTS.md` is explicit that a
gate file's numbers are measurements to re-take rather than targets — adding a
number to the boot log invites someone to turn it into a gate, and a
scheduling-dependent hit rate would be a flaky one. `hits/misses` is read on
demand via the `kcommand!`, which is what that facility is for.

**D2 — `flush_local_all_contexts` and `flush_pcid` move into OSTD.**
The dependency direction settles this and it is not a matter of taste:
`mm/Cargo.toml:25` declares `slopos-ostd`, so OSTD cannot call into `mm`.
`select_for_activate` needs `flush_pcid` (§4.5 step 7), and `flush_pcid` needs
`flush_local_all_contexts` as its no-`INVPCID` fallback
(`mm/src/mmu/asid.rs:165-171`), and both need `PCID_ENABLED`/`INVPCID_AVAILABLE`.
Leaving any of them in `mm` would require OSTD to call up, which does not
compile. The two external callers (`mm/src/tlb.rs:444`,
`mm/src/mmu/quiesce.rs:125`) change an import path and nothing else.
Its doc comment (`asid.rs:172-186`) moves **verbatim** — it is first-party
prose, it is correct, and it explains the `CR4.PGE`-toggle fallback, which is
the least obvious thing in the module. One line of it needs editing: it refers
to `select_cr3`, which is being renamed.

**D3 — `Cr3Value` is kept, reduced to a decoder.**
Revision 1 asked whether to delete it and leaned toward deleting. It has two
live uses that make deletion a regression: `mm/src/paging/tables.rs:32`
(`read_cr3_value().pml4_phys()`, the kernel PML4 lookup) and the fault
reporter, which prints a raw CR3 (`boot/src/exception.rs:212-213`) that this
type's field-wise `Debug` (`mm/src/mmu/cr3.rs:167-181`) exists to make legible
— *"so tracing a stale TLB bug does not mean decoding a raw hex value by
hand"*, per its own comment. Deleting the decoder while fixing a stale-TLB bug
would be removing the instrument.
What **is** deleted is its ability to *construct* a flush decision:
`Cr3Value::new`'s `no_flush` parameter, `with_noflush`, `without_noflush`,
`Cr3Value::kernel`, and `write_cr3_value` (§4.4). Read-only survives; the
write side does not.

**D4 — The `#PF` audit is done, and is no longer a prerequisite.**
Revision 1 asked whether to make it blocking for step 1 rather than step 5.
The question is moot: §8.3 carries the audit, the tolerance is present in
`mm/src/demand.rs:74-77` and `mm/src/cow.rs:41-43`, and §5's step 0 is reduced
to re-confirming that those four files have not changed. Had the audit come
back the other way, the correct response would have been to bump `tlb_gen` on
`map` as well — costing a permanent miss on every first touch of a new mapping
— and §6-T11's second half would have inverted. It did not, so §4.6's table
stands as written.

**D5 — The `flush_pcid` call in the miss arm is deleted.** (Not a revision-1
question; surfaced by reading the code this revision.) See §4.5 step 8: it is
redundant against the `no_flush = false` the same arm returns, and it costs an
`INVPCID` — or on an `INVPCID`-less host, a full all-context flush — on every
cold dispatch. T2 is the pin that makes the deletion safe.

**D7 — `init_bsp` returns `PcidVerdict`; the backend name is logged by the
caller.** (R3-1; not a revision-2 question — a compile blocker it did not
notice.) `super::rar::backend().name()` at `mm/src/mmu/asid.rs:144` is an
`mm`-crate trait object inside the moved function, and OSTD cannot depend on
`mm`. The alternatives were: (a) move `ShootdownBackend` into OSTD too —
rejected, it drags the whole `rar`/`IntelRar` surface across for a log string;
(b) pass the name in as a `&'static str` on `PcidSupport` — rejected, it makes
the pool's init signature carry a field it never reads, which is the same
confused-input smell as §4.2's `PcidSupport` correction; (c) log in the caller.
**(c).** `boot/` already depends on both crates (`boot/Cargo.toml:32,34`) and
`mm/src/mmu/mod.rs:16` already re-exports `backend` as `shootdown_backend`, so
the caller needs no new surface. §1.4b gives the exact code.

**D8 — `wrap_existing` is the kernel-master constructor and takes no context
parameter.** (R3-3.) Its three callers in the tree all wrap the master. Giving
it `MmContext::KERNEL` unconditionally is what keeps §4.5 step 3 able to
recognise the master; giving it an allocated id would silently consume a
dynamic slot per CPU forever. A future non-master wrapper is a new
constructor, not a parameter on this one — stated as a decision so nobody
"generalises" it back. §4.3 carries the table.

**D6 — `impl Default for Pcid` is deleted.** (Same.) It yields `Pcid::KERNEL`
(`slopos-ostd/src/arch/x86_64/cr3.rs:30-34`), i.e. a silently-defaulted kernel
PCID, which is the exact confusion this finding is about. It has no callers.

## 10. What a reviewer should check first

In descending order of "if this is wrong, the rest does not matter":

1. **§4.6's table.** The `map` / `unmap` / `protect` split is the correctness
   core, and getting it wrong is silent in both directions — a missing bump
   reintroduces §1.5, a gratuitous one makes the pool a no-op that still looks
   green. Cross-check it against the `flush_leaf_local` call sites, which is
   the invariant the table encodes.
2. **§4.5's ordering rule.** `gen` is read before the CR3 write and stored
   after. The failure mode of getting it backwards is a *lost invalidation*,
   which no test in §6 can observe on x86-TSO (§8.8).
3. **§1.6.** If `activate`'s call sites are not all IRQs-off, the `PerCpuSlot`
   borrow is not sound and the design needs a different exclusion mechanism.
   The table lists all **nine** (revision 2 said five and listed nine — R3-6);
   re-run the grep rather than trusting it. Row 9 is tests-kernel-only, which
   is the variant `just test` grades.
4. **§4.7's bit-11 reservation.** Cheap to check, catastrophic and
   undetectable-until-KPTI if wrong.
5. **§4.5 steps 1–2.** The bounds check precedes the `PCID_ENABLED` check
   because the latter bumps a counter inside `PER_CPU[cpu]`. Revision 2 had
   these the wrong way round (R3-2). An out-of-bounds index on the dispatch
   path is a panic in the trusted crate.
