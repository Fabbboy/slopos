## 1. What the code actually does

Every claim below was read out of the tree at the stated line, not taken from
the ledger.

### 1.1 The site the ledger names

`fs/src/ext2/mod.rs:527-535`

```rust
fn read_group_desc(&mut self, group: GroupIdx) -> Result<GroupDesc, Ext2Error> {
    let table_start: u32 = if self.block_size == 1024 { 2 } else { 1 };
    let desc_per_block = self.block_size as usize / 32;
    let block_idx = group.raw() as usize / desc_per_block;
    let within = (group.raw() as usize % desc_per_block) * 32;
    let blk_num = BlockNum(table_start + block_idx as u32);
    let block = self.cache.get(blk_num, self.device)?;
    Ok(GroupDesc::parse(&block.data()[within..within + 32]))
}
```

`GroupDesc::parse` (`fs/src/ext2/ondisk.rs:164-174`) reads fixed offsets
`0,4,8,12,14,16` out of that slice — so it does trust the slice length, exactly
as the ledger says. `le32`/`le16` (`ondisk.rs:333-345`) index `data` directly,
with no `get`, so a short slice is a panic and not an error.

### 1.2 The ledger's headline claim is **false**

> *"...slices `&block.data()[within..within + 32]` … malformed-image-triggered
> out-of-bounds slice index."*

`within` is `(group % desc_per_block) * 32`, so `within <= (desc_per_block-1)*32`
and therefore `within + 32 <= desc_per_block * 32`. `desc_per_block` is
`block_size / 32`, and `block.data()` is exactly `block_size` bytes long
(`fs/src/ext2/cache.rs:366-369`, `CachedBlock::data` slices `..bs` where `bs` is
the cache's `block_size`). Since 32 divides 1024, 2048 and 4096 — the only block
sizes `Superblock::block_size()` admits (`ondisk.rs:128-136`, which rejects
anything outside `EXT2_MIN_BLOCK_SIZE..=EXT2_MAX_BLOCK_SIZE` after a
`checked_shl`) — `desc_per_block * 32 == block_size` exactly.

Verified over the whole admissible domain:

| `block_size` | `desc_per_block` | max `within` | `within+32` | `data().len()` | OOB? |
|---|---|---|---|---|---|
| 1024 | 32 | 992 | 1024 | 1024 | **no** |
| 2048 | 64 | 2016 | 2048 | 2048 | **no** |
| 4096 | 128 | 4064 | 4096 | 4096 | **no** |

The modulo is a total bound. **This slice cannot go out of bounds, for any
`group`, on any mountable image.** The same holds for the duplicate at
`alloc.rs:250`. The ledger's remediation ("bound each `within + size` against
the containing block") would add a branch that provably never fires.

The residual as written should be **corrected in `CVSS.md`**, not merely closed.

### 1.3 What is actually wrong at that site

The bug is the *other* half of the computation, which the ledger does not name:

- **`block_idx` is unbounded.** `blk_num = table_start + block_idx` is fed
  straight to `cache.get` with no check that `group` names a group that exists,
  and no check that the resulting block is inside the descriptor table — or
  inside the filesystem at all. `groups_count()` is never consulted at either
  call site. A `group` past the table reads *some other block* — a bitmap, an
  inode table, file data — and `GroupDesc::parse` interprets 32 bytes of it as
  bitmap and inode-table block pointers. That is **metadata type confusion**,
  and it is strictly worse than the panic the ledger describes, because it
  does not stop: `read_inode_num` (`mod.rs:211-218`) then computes an inode
  offset from the attacker-chosen `inode_table` value and `write_inode_num`
  (`mod.rs:233`) *writes* through it.
- **`table_start + block_idx as u32` can wrap** (`mod.rs:532`), and
  `block_idx as u32` truncates a `usize` — two silent narrowings on a path
  whose input is on-disk data.
- **The logic is duplicated and already diverging.** `alloc.rs:229-239`
  `group_desc_offset` is a second copy with a different signature (it takes a
  `_superblock` it ignores). Two copies of an unchecked computation is the
  structural defect; a bound added to one is a bound missing from the other.

### 1.4 Real panics found nearby (the ledger has the wrong ones)

These are genuine `Ext2Error`-less panics on malformed input. Overflow checks
are **on** in the dev and tests kernels and **off** in release — confirmed by
scanning the built ELFs (`strings builddir/kernel-{dev,release}.elf | grep -cF`,
re-run for this revision):

```
attempt to add with overflow          dev=1  release=0
attempt to multiply with overflow     dev=1  release=0
attempt to subtract with overflow     dev=1  release=0
range end index                       dev=1  release=1
```

So in dev/tests these are panics; in release they are silent wrong values that
feed the same type confusion. Both outcomes are bad, differently.

| # | Site | Expression | Trigger | Debug | Release |
|---|---|---|---|---|---|
| P1 | `ondisk.rs:150` | `(blocks_count + blocks_per_group - 1) / blocks_per_group` | `blocks_count` near `u32::MAX` | add overflow panic | wraps → tiny `groups_count` |
| P2 | `alloc.rs:183` | `group.raw() * superblock.blocks_per_group + …` | large `blocks_per_group` | mul overflow panic | wraps → block number aliases a live block |
| P3 | `alloc.rs:225` | `group.raw() * superblock.inodes_per_group + bit + 1` | large `inodes_per_group` | mul overflow panic | wraps → inode number aliases a live inode |
| P4 | `dir.rs:235` | `let slack = rec_len - actual_size;` | `rec_len=9, name_len=1` | **sub underflow panic** | wraps to huge `usize`, `slack >= needed` taken, then `data[new_cursor..new_cursor+new_rec_len]` panics on range |

Note the release column of P4: `range end index` is present in **both** ELFs
(dev=1, release=1), because a slice-range panic is not an overflow check and is
not compiled out. So P4 is a panic in every variant — it merely reaches the
panic by a different route in release.

P4 deserves emphasis: it is reachable from an ordinary `create_file` into a
crafted directory, and `for_each_entry`'s own validation does **not** catch it.
`for_each_entry` checks `rec_len >= DIR_ENTRY_HEADER_SIZE || cursor + rec_len >
bs` (`dir.rs:44-46`) and, only for a record whose inode is non-zero,
`name_start + name_len <= cursor + rec_len` (`dir.rs:50-52`); `append_dir_entry`
instead computes `actual_size = dir_entry_size(name_len) = (8 + name_len + 3) &
!3` (`ondisk.rs:279-281`), which rounds *up*. For `name_len=1, rec_len=9` the
entry passes `for_each_entry` (9 ≥ 8, and 8+1=9 ≤ 9) while `dir_entry_size(1) =
12 > 9`. Verified:

```
name_len=1  rec_len=9 : for_each_entry_passes=True  actual_size=12  slack=-3  underflow
name_len=2  rec_len=10: for_each_entry_passes=True  actual_size=12  slack=-2  underflow
name_len=5  rec_len=13: for_each_entry_passes=True  actual_size=16  slack=-3  underflow
```

This is the same *shape* as CVE-2025-37785 (ext4 `ext4_empty_dir` OOB read): a
directory record whose `rec_len` is individually legal but inconsistent with the
walker's own step arithmetic, where the validator and the consumer disagree
about what "valid" means.

### 1.5 Spec invariants that are never checked

From the ext2 on-disk format (the format facts, not anyone's implementation):

- **A group's block bitmap and inode bitmap each occupy exactly one block.**
  Therefore `blocks_per_group <= 8 * block_size` and
  `inodes_per_group <= 8 * block_size`. `Superblock::parse` checks only
  `!= 0` (`ondisk.rs:96`). Today the code accepts up to `u32::MAX`, i.e. up to
  524 288× the legal maximum at 4 KiB blocks. `try_alloc_block_in_group`
  (`alloc.rs:160-167`) then calls `find_first_zero(bmap.data(), bits_in_group)`
  with `bits_in_group` far past the block. `bitmap_slice::find_first_zero`
  (`slopos-ostd/src/bitmap_slice.rs:31-51`) iterates `data.iter().enumerate()`,
  so it cannot fault — it simply never reaches `abs >= nbits` and returns the
  first zero bit in the block — but the *derived* block number at `alloc.rs:182`
  is then outside the group. Likewise `set_bit`/`clear_bit`
  (`bitmap_slice.rs:13-28`) use `get_mut` and silently no-op out of range, so a
  free of an out-of-group block silently does nothing rather than erroring.
- **`s_first_data_block` is 1 for 1 KiB block sizes and 0 otherwise.** Never
  checked. `read_group_desc` hardcodes the consequence
  (`table_start = if block_size == 1024 { 2 } else { 1 }`) while
  `free_block`/`allocate_block_near` independently `saturating_sub` the
  superblock's own field — two encodings of one fact that can disagree.
- **`s_inodes_count` must equal `s_inodes_per_group ×` the number of groups.**
  Never checked, so the `ino.raw() > inodes_count` guard at `mod.rs:202` admits
  inode numbers whose derived group index exceeds `groups_count()`. **This is
  the concrete path from an unprivileged-looking call into §1.3's type
  confusion:** `read_inode(ino)` (`mod.rs:197`, `pub`, takes a bare `u32`) →
  `read_inode_num` → `ino.block_group(inodes_per_group)` (`types.rs:70-72`,
  which is `(ino-1)/ipg` with no upper bound) → out-of-range `GroupIdx` →
  `read_group_desc` reads an arbitrary block as a descriptor. `read_inode` is
  reached from the VFS `stat`/`lookup`/`read` handlers
  (`ext2_vfs.rs:120-160`), so the inode number is caller-supplied.
- **The group-descriptor table's extent is never bounded.** Nothing asserts
  `table_start + ceil(groups_count / desc_per_block) <= blocks_count`.

### 1.6 Threat model — stated honestly

There is **no `mount(2)` syscall**. The only ext2 mount is boot-time, from
virtio-blk `disk0`, in `boot/src/boot_services.rs:97-120` (`boot_step_fs_init`,
registered at `boot_services.rs:207`) via `ext2_vfs_init_with_device`. `devfs`
(`fs/src/devfs/mod.rs:44-50`) exposes exactly five nodes — `null`, `zero`,
`random`, `console`, `kmsg` — and no raw block-device node, so no unprivileged
process can write raw metadata bytes.

Feeding a crafted image therefore requires control of the VM's disk, which is
close to control of the machine. That is why the ledger's confidence of 60 is
right and why this is **not** a CVSS-scored guaranteed issue.

What makes it still worth fixing properly:

1. **Non-malicious corruption reaches the same code.** A torn write or a bad
   sector in the GDT produces exactly the crafted-descriptor state. Then the
   dev/tests kernel panics and the release kernel silently writes an inode
   through an attacker-shaped `inode_table` pointer.
2. **`verity` is not the mitigation it looks like.** `fs/src/verity.rs` is
   CRC-32, and its own header says so: *"CRC-32 is an integrity check, not an
   authenticity one."* It also disables itself when the trailer is absent or
   corrupt (`parse_trailer` returns `None` → `build_verified` returns the device
   unwrapped), and it stops verifying any block once written
   (`write_at` sets the `written` bit). It does not bound this.
3. **The blast radius grows the day a `mount(2)` exists.** The whole ext2 stack
   is currently written as if the image is trusted. That assumption is
   undocumented and unenforced, and it is the thing that will silently become
   false.

## 2. Prior art

Format facts and documented behaviour only; no implementation text is taken
from any GPL-2.0-only or CDDL source. Sources consulted: the ext4 on-disk layout
documentation on kernel.org (`filesystems/ext4/globals.html`,
`group_descr.html`, `super.html`) — a *specification description* — the
`ext2-doc` project's *The Second Extended File System* (nongnu.org), and the NVD
entry for CVE-2025-37785.

**What mature filesystem implementations converged on:**

1. **Validate the whole geometry once, at mount, then never re-derive.** The
   superblock's fields are mutually constrained (block size ↔ bitmap capacity ↔
   per-group counts ↔ group count ↔ table extent). Checking them one at a time
   at the point of use always misses a cross-field contradiction, because each
   field is individually plausible. The settled shape is a single mount-time
   pass that computes every derived quantity and refuses the mount if any of
   them is inconsistent — after which in-kernel code reads *derived* values, not
   raw on-disk ones.

2. **Designs that were tried and abandoned:**
   - *Bounds-check at the point of use.* Abandoned because it scales with call
     sites rather than with invariants; every new caller re-litigates it, and a
     forgotten one is silent. It is precisely the state this tree is in: two
     copies of `read_group_desc`, neither bounded.
   - *Trust `e2fsck` to have run.* Abandoned once removable media and
     attacker-supplied images became normal. A kernel cannot assume a fsck.
   - *Clamp instead of reject.* Abandoned because clamping a contradictory
     superblock produces a geometry that describes *no* real image, so
     allocation then writes into whatever the clamp happened to select.
     **Reject the mount** is the settled answer.
   - *Checksums as the validator.* `metadata_csum`/`gdt_csum` were added, and
     the lesson was that a checksum proves *provenance*, not *consistency*:
     mke2fs will happily checksum a geometry, and the checksum does not tell
     you the descriptor table fits inside the volume. Structural validation
     stayed and is separate from checksum validation. (This is directly why
     §1.6's point 2 holds for `verity` here.)

3. **Directory-record validation converged on one entry point.** The
   CVE-2025-37785 class exists because a record can satisfy a per-record check
   and still be inconsistent with the *walker's* step. The settled answer is a
   single shared `check_dir_entry`-shaped predicate that every walker calls, so
   validator and consumer cannot disagree — which is exactly the P4 defect in
   §1.4, where `for_each_entry` and `append_dir_entry` disagree.

4. **e2fsprogs validation ordering** (documented behaviour): magic → revision →
   feature flags → block size → per-group counts → group count → descriptor
   table extent → per-descriptor pointers. Later checks depend on earlier ones
   having established sane divisors, so the order is load-bearing.

**What SlopOS can do that these cannot:** make the invalid state
unrepresentable. A validated-geometry *type* whose constructor is the only way
to obtain a `GroupIdx` means an unchecked group index is not a value a future
author can produce. C kernels cannot express this; a `#![forbid(unsafe_code)]`
Rust crate can, and it converts a recurring review burden into a compile error.

## 3. The fix

### 3.0 Placement, ownership and locking — decided, not deferred

The reviewer is right that a data structure without a stated home is not an
implementable design. Stated once, here, and referenced by the rest of §3.

**`Ext2Geometry` is per-mount immutable data, owned by `CachedExt2`, protected
by the mutex that already protects `CachedExt2`.**

- **Home**: one field on `CachedExt2` (`fs/src/ext2_vfs.rs:15-27`), which lives
  inside `static CACHED_EXT2: Mutex<Option<CachedExt2>>`
  (`ext2_vfs.rs:31-32`, class `lock_class!("CACHED_EXT2",
  LOCK_LEVEL_RESOURCE)`). No new `static`, no new lock, no new lock class.
- **Lifetime and mutability**: written exactly once, by
  `ext2_vfs_init_with_device`, before `*guard = Some(CachedExt2 { .. })`
  publishes the value. Never mutated afterwards. There is no interior
  mutability and no atomic; the mutex is what makes the single write happen
  before every read, and after publication the value is only ever read.
- **Per-call handle**: `Ext2Fs` (`mod.rs:53-66`) is rebuilt per VFS call from
  the guarded `CachedExt2` — four sites, `ext2_vfs.rs:66`, `270`, `301`, `343`
  — and takes a `Ext2Geometry` **by value** at construction, exactly as it
  takes `superblock: Superblock` by value today. That copy is legitimate: it is
  a `Copy` snapshot of immutable data taken under the lock.
- **Concurrency**: every `Ext2Fs` method runs with `CACHED_EXT2` held
  (`with_fs`, `ext2_vfs.rs:59-91`), so there is exactly one `Ext2Fs` alive at a
  time and `&mut BlockCache` is uncontended by construction. `Ext2Geometry`
  changes none of this.

Two alternatives, both rejected:

- **A `static Ext2Geometry` (or `Once<Ext2Geometry>`).** Rejected: it would
  outlive the mount. `ext2_vfs_init_with_device` is explicitly retryable — every
  failure path calls `EXT2_VFS_INIT.reset()` (`ext2_vfs.rs:239`, `247`, `252`)
  so a later attempt can re-mount — and a `static` geometry from a failed or
  previous mount would then describe a different image. Tying the geometry's
  lifetime to `CachedExt2`'s makes that unrepresentable.
- **Per-CPU.** Rejected: there is nothing per-CPU about it. It is immutable
  after mount, read under a sleeping mutex on a path that already blocks on
  block I/O, and 52 bytes; a per-CPU copy would add a `PerCpuSlot` and a
  coherence question to buy nothing.

**The test path uses the same type without the mutex.** `mount_ext2!`
(`tests.rs:17-30`) builds a stack-local `BlockCache` and `Ext2Fs`, and will
likewise hold a stack-local `Ext2Geometry`. That is sound for the same reason
the existing stack-local `Superblock` is: the handle is not shared.

### 3.1 Minimal patch, and why it is insufficient

The cheap patch is three lines:

```rust
// mod.rs:527 and alloc.rs:229
if group.raw() >= self.superblock.groups_count() { return Err(Ext2Error::InvalidBlock); }
// dir.rs:235
let slack = rec_len.checked_sub(actual_size).ok_or(Ext2Error::DirectoryFormat)?;
```

It is insufficient because:

- `groups_count()` (`ondisk.rs:146-151`) is **itself unvalidated and itself
  overflows** (P1). Bounding a group index against a number derived by
  overflowing arithmetic on attacker data is not a bound.
- It leaves the duplication that produced the defect. Two copies of the check
  will diverge exactly as the two copies of the computation already have.
- It does not stop the descriptor's *contents* (`inode_table`,
  `block_bitmap`) from pointing anywhere. That is the pointer `write_inode_num`
  writes through, and it is untouched by a group-index bound.
- It leaves P2/P3 and the §1.5 spec invariants entirely open.
- It does not correct the record: the ledger claims an OOB slice that does not
  exist, so the cheap patch "fixes" a non-bug and leaves the real one.

**What the refactor buys over five years:** it moves the invariant from *"every
present and future caller remembers to check"* to *"an unchecked group index is
not constructible."* The tree currently has **6** `GroupIdx` construction sites
(enumerated in §3.4); every one is a place a bound can be forgotten. After the
change there is one. When `mount(2)` lands, or an ext3/ext4 reader is added, or
a second on-disk filesystem reuses `BlockCache`, the validation is inherited
rather than re-derived. That is the difference between a patch and a fix.

> **Correction.** Rev 2 said "13 construction sites (`alloc.rs` ×7, `mod.rs`,
> `types.rs`)". That was wrong: it counted `group: GroupIdx` *parameter
> declarations* as constructions. The verified count of expressions that build
> a `GroupIdx` value is **6**, and `mod.rs` builds none. The argument does not
> depend on the number — 6 unchecked sites is still 6 places a bound can be
> forgotten, and the fix still leaves 1 — but the number is now measured.

### 3.2 New module: `fs/src/ext2/geometry.rs`

The single parse-once/trust-after type. Plain `Copy` data, no allocation, no
locks, no interior mutability. Placement and ownership are §3.0.

**Layout, counted rather than guessed.** Thirteen fields: ten `u32`
(`block_size`, `blocks_count`, `inodes_count`, `blocks_per_group`,
`inodes_per_group`, `groups_count`, `desc_per_block`, `gdt_blocks`,
`itable_blocks_per_group`, `ptrs_per_block`), two `BlockNum`
(`#[repr(transparent)]` over `u32`, `types.rs:8-16`), and one `u16`
(`inode_size`). That is 12×4 + 2 = 50 bytes, aligned to 4 → **52 bytes**.

**Calling convention, decided.** The SysV x86-64 ABI classifies any aggregate
larger than 16 bytes as MEMORY, so a 52-byte by-value parameter is a stack copy
at every call. Therefore:

- **Free functions take `&Ext2Geometry`.** This covers `read_group_desc`,
  `write_group_desc` and every `alloc.rs` helper — the sites §6 previously left
  as "must be checked".
- **Inherent accessors take `self` (`Copy`) and are `#[inline]`.** They are
  field reads; inlining removes the copy entirely, and `&self` on a `Copy` type
  whose methods all inline buys nothing.
- **`Ext2Fs` stores it by value**, as it already stores `Superblock` by value.

This is a decision, not a caveat: §6 now records "no ext2 frame is expected to
cross 2048 B, and the by-value-parameter shape that would have risked it is not
in the design."

```rust
use super::types::{BlockNum, GroupIdx, InodeNum};
use super::ondisk::{GroupDesc, Superblock};
use super::Ext2Error;

/// Every quantity derived from the superblock, validated once at mount.
///
/// Constructing one is the only way to obtain a `GroupIdx`, so an
/// unchecked group index is not a value that can be produced.
#[derive(Debug, Copy, Clone)]
pub struct Ext2Geometry {
    block_size: u32,
    inode_size: u16,
    blocks_count: u32,
    inodes_count: u32,
    first_data_block: BlockNum,
    blocks_per_group: u32,
    inodes_per_group: u32,
    groups_count: u32,
    desc_per_block: u32,
    gdt_first_block: BlockNum,
    gdt_blocks: u32,
    itable_blocks_per_group: u32,
    ptrs_per_block: u32,
}
```

### 3.3 `Ext2Geometry::derive` — the validation, in order

Order is load-bearing: each step may rely on the previous having established a
sane divisor. Every failure is `Err`, never a clamp. All arithmetic uses
`checked_*` / `div_ceil`.

| # | Check | Error | Rationale |
|---|---|---|---|
| G1 | `block_size` ∈ {1024,2048,4096} (existing `block_size()`) | `UnsupportedBlockSize` | establishes `desc_per_block`, bitmap capacity |
| G2 | `inode_size` power of two in `128..=block_size` (**exists**, `ondisk.rs:111`) | `InvalidSuperblock` | already landed; keep |
| G3 | `blocks_per_group != 0 && inodes_per_group != 0 && inodes_count != 0` (**exists**, `ondisk.rs:96`) | `InvalidSuperblock` | divisor sanity |
| G4 | **new** `blocks_per_group <= 8 * block_size` | `InvalidSuperblock` | block bitmap occupies exactly one block |
| G5 | **new** `inodes_per_group <= 8 * block_size` | `InvalidSuperblock` | inode bitmap occupies exactly one block |
| G6 | **new** `inodes_per_group * inode_size` checked; `itable_blocks_per_group = div_ceil(that, block_size)` | `InvalidSuperblock` | bounds the inode table |
| G7 | **new** `first_data_block == if block_size == 1024 { 1 } else { 0 }` | `InvalidSuperblock` | removes the two-encodings divergence in §1.5 |
| G8 | **new** `blocks_count > first_data_block` | `InvalidSuperblock` | non-empty volume |
| G9 | **new** `groups_count = div_ceil(blocks_count - first_data_block, blocks_per_group)`; require `!= 0` | `InvalidSuperblock` | replaces the overflowing `ondisk.rs:150` (P1) |

### 3.5 Fixed-size parse windows — where the "size trust" actually dies

The finding is named *size trust*. Bound-checking the slice would leave
`GroupDesc::parse(&[u8])` still trusting its argument. Make the footprint a
type instead, in `fs/src/ext2/cache.rs`:

```rust
impl CachedBlock<'_> {
    /// A fixed-size window, or `None` if it does not fit in the block.
    pub fn window<const N: usize>(&self, at: usize) -> Option<&[u8; N]>;
    pub fn window_mut<const N: usize>(&mut self, at: usize) -> Option<&mut [u8; N]>;
}
```

Implemented with `self.data().get(at..at.checked_add(N)?)?.try_into().ok()` —
safe, no `unsafe`, no allocation, const-generic so the length is a compile-time
fact at the parse site.

Then, in `fs/src/ext2/ondisk.rs`:

```rust
pub const GROUP_DESC_SIZE: usize = 32;
pub const INODE_CORE_SIZE:  usize = 128;

impl GroupDesc {
    pub fn parse(data: &[u8; GROUP_DESC_SIZE]) -> Self;      // was &[u8]
    pub fn encode(&self, data: &mut [u8; GROUP_DESC_SIZE]);  // was &mut [u8]
}

impl Inode {
    pub fn parse(data: &[u8; INODE_CORE_SIZE]) -> Self;      // was &[u8]
    pub fn encode(&self, data: &mut [u8; INODE_CORE_SIZE]);  // was &mut [u8]
}
```

`Inode::parse` (`ondisk.rs:202-224`) reads `le16`/`le32` at offsets 0..36 and
the fifteen block pointers from offset 40, i.e. the last byte touched is at
offset 99 — so 128, the architectural minimum `inode_size` already enforced by
G2, is the correct footprint. `Inode::encode` (`ondisk.rs:226-248`) writes the
same span but first zeroes *all* of `data` (`for byte in data.iter_mut()`), so
narrowing its parameter to `&mut [u8; 128]` is a **behaviour change**: today it
zeroes the full `inode_size` bytes, tomorrow only the first 128. That is
correct for a 128-byte inode and correct for the ext2 rev-1 layout, where bytes
128.. of a larger inode are the extended-attribute area that the writer must
*not* clobber — today's zeroing is the bug, and `test_ext2_inode_extra_bytes_
preserved` (§5) pins the new behaviour. Call it out at review time rather than
letting it land unremarked.

The current read slices `inode_size` bytes (`mod.rs:216-218`) and the current
write slices `inode_size` bytes (`mod.rs:233`); narrowing to the bytes actually
touched also means the `within + inode_size` arithmetic no longer has to be in
range, only `within + 128`. G2 plus G6 guarantee that.

After this change `le32(data, 8)` cannot index out of bounds *by construction*:
the array length is in the type. The `le16`/`le32` helpers
(`ondisk.rs:333-345`) keep their `&[u8]` signatures — `&[u8; N]` coerces — and
simply become infallible at these call sites.

### 3.6 Single descriptor accessor, replacing both copies

```rust
pub fn read_group_desc(
    geom: Ext2Geometry,
    group: GroupIdx,
    cache: &mut BlockCache,
    device: &dyn BlockDevice,

    let loc = geom.group_desc_loc(group);
    let block = cache.get(loc.block(), device)?;

        .window::<GROUP_DESC_SIZE>(loc.within())
        .ok_or(Ext2Error::InvalidBlock)?;   // unreachable given G11; fail closed
```

### 3.7 `validate_desc` — the check that stops the write-through

This is the part the ledger's proposed remediation does not contain, and the
part that actually matters. Called on every descriptor read, cheap (six
comparisons), no I/O:

```rust
pub fn validate_desc(&self, group: GroupIdx, d: &GroupDesc) -> Result<(), Ext2Error> {
    let lo = self.first_data_block.raw();
    let hi = self.blocks_count;                       // exclusive
    let in_vol = |b: BlockNum| b.raw() >= lo && b.raw() < hi;

    if !in_vol(d.block_bitmap) || !in_vol(d.inode_bitmap) || !in_vol(d.inode_table) {
        return Err(Ext2Error::InvalidBlock);
    }
    // The whole inode table must fit, not just its first block: `read_inode_num`
    // indexes `inode_table + local * inode_size` and would otherwise walk out.
    let end = d.inode_table.raw()
        .checked_add(self.itable_blocks_per_group)
        .ok_or(Ext2Error::InvalidBlock)?;
    if end > hi {
        return Err(Ext2Error::InvalidBlock);
    }
    if d.free_blocks_count as u32 > self.blocks_per_group
        || d.free_inodes_count as u32 > self.inodes_per_group
    {
        return Err(Ext2Error::InvalidBlock);
    }
    let _ = group;
    Ok(())
}
```

The inode-table *extent* check (not merely its first block) is what closes
`write_inode_num`'s write-through at `mod.rs:233`: `byte_off` is
`inode_table * block_size + local * inode_size`, with `local < inodes_per_group`
by G3/G10, so `byte_off / block_size < inode_table + itable_blocks_per_group`,
which G-checked `end <= blocks_count` now bounds inside the volume.

**The free-count bounds are checked against a real image, not assumed.** On a
`mkfs.ext2 -F -b 4096` 16 MiB image, group 0's descriptor reads
`block_bitmap=2, inode_bitmap=3, inode_table=4, free_blocks=3830,
free_inodes=4085, used_dirs=2`, against `blocks_per_group=32768` and
`inodes_per_group=4096` — so both `<=` comparisons hold with margin, and the
inode-table extent is `4 + 256 = 260 <= 4096`. Note `free_blocks_count` and
`free_inodes_count` are `u16` on disk (`ondisk.rs:159-161`), so the `as u32`
casts in the comparison widen rather than truncate and the check can only ever
reject a value above 65 535 groups' worth — i.e. it is a cheap sanity bound, not
a tight one. Say so rather than overselling it.

`lo` is deliberately `first_data_block`, not `gdt_first_block + gdt_blocks`. A
descriptor pointing *into* the descriptor table is nonsense, but rejecting it
here would also reject a legal sparse-super layout where the backup descriptors
sit at group boundaries; bounding to the volume is the safety-relevant half, and
the tighter check belongs with metadata checksums (§8 item 3).

### 3.8 `read_inode_num` / `write_inode_num`

`mod.rs:201-235`. Replace the `ino.raw() > inodes_count` guard and the raw
`block_group`/`local_index` calls with `geom.locate_inode(ino)`:

```rust
fn read_inode_num(&mut self, ino: InodeNum) -> Result<Inode, Ext2Error> {
    let (group, local) = self.geom.locate_inode(ino).ok_or(Ext2Error::InvalidInode)?;
    let desc = self.read_group_desc(group)?;          // now validates
    let byte_off = desc.inode_table.to_disk_offset(self.geom.block_size()).raw()
        + (local as u64 * self.geom.inode_size() as u64);
    let blk_num = BlockNum((byte_off / self.geom.block_size() as u64) as u32);
    let within = (byte_off % self.geom.block_size() as u64) as usize;
    let block = self.cache.get(blk_num, self.device)?;
    let win = block.window::<INODE_CORE_SIZE>(within).ok_or(Ext2Error::InvalidInode)?;
    Ok(Inode::parse(win))
}
```

Note the existing `desc.inode_table.is_valid()` check at `mod.rs:208-210` is
subsumed by `validate_desc` — which checks the pointer is inside the volume, a

### 3.10 `dir.rs` — one shared record predicate (P4)

Add to `fs/src/ext2/ondisk.rs`:

```rust
/// Every field of one on-disk directory record, validated against the block.
#[derive(Debug, Copy, Clone)]
pub struct DirRecord {
    pub inode: InodeNum,
    pub rec_len: usize,
    pub name_len: usize,
    pub file_type: u8,
}

/// The single validator. Every directory walker must reach a record through
/// this, so no walker can disagree with another about what "valid" means.
pub fn parse_dir_record(
    data: &[u8],
    cursor: usize,
    block_size: usize,
) -> Result<DirRecord, Ext2Error>;
```

`parse_dir_record` enforces, in one place:

1. `cursor + DIR_ENTRY_HEADER_SIZE <= block_size`
2. `rec_len >= DIR_ENTRY_HEADER_SIZE`
3. `rec_len % 4 == 0` — **new**; records are 4-byte aligned, and this alone
   kills the `rec_len=9,10,13` family in §1.4
4. `cursor + rec_len <= block_size` (checked add)
5. **if `inode != 0`**, `DIR_ENTRY_HEADER_SIZE + name_len <= rec_len`
6. **if `inode != 0`**, `dir_entry_size(name_len) <= rec_len` — the check whose
   absence *is* P4. This is the walker-vs-consumer agreement:
   `append_dir_entry`'s `actual_size` can now never exceed `rec_len`, so
   `slack` cannot underflow.
7. For a record at `cursor == 0`, `rec_len < block_size` is *not* required —
   an empty directory block legitimately has one full-block record.

> **Defect found in review; fixed above.** Rev 2 stated checks 5 and 6
> unconditionally, which **would have rejected valid images**. A *free* record
> (`inode == 0`) has no name, and its `name_len` byte is whatever the deleted
> entry left there. `remove_dir_entry` (`dir.rs:145-152`) frees a first-in-block
> entry by zeroing only the four inode bytes — `name_len` at offset 6 is left
> stale — so a block containing any deleted first entry carries a record with
> `inode == 0` and an arbitrary `name_len`. An unconditional check 6 fails it
> and the whole directory becomes unreadable. Gating both on `inode != 0`
> matches what the tree already does: `for_each_entry` applies its own name
> bound only inside `if entry_inode != 0` (`dir.rs:47-52`), and
> `append_dir_entry` already computes `actual_size = DIR_ENTRY_HEADER_SIZE` —
> *not* `dir_entry_size(name_len)` — for a free record (`dir.rs:228-233`). The
> conditional form is therefore exactly consistent with the consumer, which is
> the whole point of the shared predicate. `test_ext2_dir_free_record_stale_
> name_len_still_walks` (§5) pins this so the stricter form cannot creep back.

`DirRecord` accordingly exposes `actual_size()` as
`if inode.raw() != 0 { dir_entry_size(name_len) } else { DIR_ENTRY_HEADER_SIZE }`,
which is `append_dir_entry`'s existing expression moved into the type.

Then:

- `for_each_entry` (`dir.rs:13-66`), `remove_dir_entry` (`dir.rs:99-161`),
  `append_dir_entry` (`dir.rs:192-286`) and `update_dotdot` (`dir.rs:288-330`)
  all drop their hand-rolled header decoding and call `parse_dir_record`.
- `dir.rs:235` becomes `let slack = rec.rec_len - rec.actual_size();`, and the
  subtraction is now *proved* non-negative by check 6 in the `inode != 0` arm
  and by check 2 (`rec_len >= 8 == DIR_ENTRY_HEADER_SIZE`) in the `inode == 0`
  arm — both arms total, which is why gating check 6 does not reopen P4. (A
  `debug_assert!` documents the dependency.)
- `remove_dir_entry`'s `cmp::min(name_len, rec_len - DIR_ENTRY_HEADER_SIZE)`
  (`dir.rs:140`) — a clamp papering over the same disagreement — is deleted;
  check 5 makes it dead on the `inode != 0` path, which is the only path that
  reads a name. The `use core::cmp;` at `dir.rs:8` goes with it if nothing else
  in the file needs it.
- **Termination**: every walker advances `cursor += rec.rec_len` with
  `rec_len >= 8`, so the loop is bounded by `block_size / 8` iterations. Today
  this holds only incidentally.

### 3.12 Subsystem interactions

Each claim below names what was inspected, so a reviewer can re-check it rather
than take it on trust.

- **TLB shootdown**: none. The only TLB interaction in this subsystem is
  `BlockCache`'s frame lifetime — `CacheEntry` holds a `Frame<PageCacheMeta>`
  (`cache.rs:23-32`), allocated by `Frame::<PageCacheMeta>::alloc()`
  (`cache.rs:36`, into `slopos-ostd/src/mm/frame.rs:1170`) and released by
  `shrink_clean` (`cache.rs:279-311`). This proposal adds and removes no
  `Frame`, changes `CACHE_ENTRIES` (`cache.rs:9`) not at all, and touches
  neither `find_or_evict` nor `shrink_clean`. `Ext2Geometry` is `Copy` data in
  an existing struct — no page tables, no frame ownership change, so no
  shootdown edge exists to change.
- **Quota accounting**: none. Zero new allocations. `Ext2Geometry` is a `Copy`
  struct stored inline; `window::<N>` returns a borrow (`get` + `try_into`);
  `parse_dir_record` returns a `Copy` `DirRecord`. The only `KVec` allocations
  in the ext2 tree are `BlockCache::new` (`cache.rs:69-77`),
  `release_file_blocks`'s `freed` list (`mod.rs:556`) and `file::free_indirect`'s
  `ptrs` (`file.rs:187-188`) — none is on a path this changes. `scripts/gates/
  quota/tests.txt` accounts (`fdslot`, `objectrow`, `process`, `task`,
  `kernelmeta`, `pages`, …) have no ext2 row, and nothing here creates one.
- **Lockdep ordering**: none. `fs/src/ext2_vfs.rs` declares exactly one lock
  class, `lock_class!("CACHED_EXT2", LOCK_LEVEL_RESOURCE)` (`ext2_vfs.rs:32`),
  plus `EXT2_FLUSH_STOP.waiters` (`ext2_vfs.rs:41`); `fs/src/verity.rs:166`
  declares `VerifiedBlockDevice.written` and `fs/src/blockdev.rs:47-51`
  declares `MemoryBlockDevice.data`. §3.0 puts `Ext2Geometry` inside the
  existing `CACHED_EXT2` critical section and adds no `lock_class!`, no
  acquire, and no ordering edge — so class, edge and chain counts in
  `scripts/gates/lockdep/tests.txt` are all unchanged. If the gate moves,
  something unintended was added.
- **Authority model**: none. `scripts/gates/authority/{dev,tests,release}.txt`
  contain no `fs`/`ext2` entry — grepped, zero hits — because no ext2 function
  reaches a power primitive. This proposal adds no syscall handler and no call
  into `PowerOps`; the deepest new call is `cache.get`, which the ext2 path
  already makes.
- **Task ownership (I1–I8)**: not touched. No `KArc<Task>`, no `TaskRef`, no
  raw task pointer, no blocking primitive added. The ext2 flusher kthread
  (`ext2_vfs.rs:366-392`, spawned via `spawn_kernel_io!` at `ext2_vfs.rs:352`)
  is unchanged; it calls `ext2_vfs_sync`, which this proposal does not modify.
- **Write-back cache / ordered durability**: unchanged. `validate_desc` is a
  read-path predicate; `sync`'s data → barrier → metadata → barrier →

- **`verity`**: orthogonal and complementary. Verity answers "are these the
  bytes we shipped"; geometry answers "are these bytes self-consistent".

  when verity has disabled itself.
- **Boot**: `boot_step_fs_init` (`boot_services.rs:97-120`) already treats a
  failed `ext2_vfs_init_with_device` as non-fatal — the failure arm merely logs
  `"FS: virtio-blk disk0 found but ext2 init failed"` (`boot_services.rs:109`)

  disk0", not a panic. `ROOTFS_IS_RAMFS` (`boot_services.rs:93`) is already set
  by the earlier initramfs step, so the fallback root exists.

## 7. Rollout risk, called out explicitly

**G12 (`blocks_count * block_size <= device.capacity()`) was the one check that
could reject an image that currently mounts. It has now been measured, and it
holds.**

Rev 2 said the inequality "should hold, but 'should' is not 'measured'". It has
been measured. Reproducing the production recipe exactly — `truncate -s 16M`
then `mkfs.ext2 -F -b 4096` (the parameters `scripts/build_fs_image.sh:41-42`
uses, with the default `FS_IMAGE_SIZE=16M` from `justfile:16`), then
`scripts/gen_verity.py` as the last step (`build_fs_image.sh:110`):

| Quantity | Value |
|---|---|
| `block_size` (`sb[24..28]` → `1024 << 2`) | 4096 |
| `blocks_count` (`sb[4..8]`) | 4096 |
| `blocks_count * block_size` | 16 777 216 |
| image size **before** `gen_verity.py` | 16 777 216 |
| image size **after** `gen_verity.py` | 16 793 632 |
| **G12 slack** | **+16 416 bytes** |

So G12 holds with equality before the trailer and 16 416 bytes of slack after —
the trailer is 4096 hashes × 4 B + a 32 B header, appended, exactly as
`gen_verity.py`'s docstring describes. The virtio-blk `capacity()`
(`drivers/src/virtio_blk.rs:812-814` → `capacity_bytes`, `:265-267`,
`capacity_sectors * SECTOR_SIZE`) reports the whole backing file, so the kernel
sees the post-trailer figure.

Every other G-check was measured on the same image at the same time:

| Check | Measured | Holds |
|---|---|---|
| G4 `blocks_per_group <= 8*bs` | 32 768 vs 32 768 | yes (at equality — so `<=`, never `<`) |
| G5 `inodes_per_group <= 8*bs` | 4 096 vs 32 768 | yes |
| G6 `itable_blocks_per_group` | `ceil(4096*256/4096)` = 256 | yes |
| G7 `first_data_block` | 0, expected 0 for `bs != 1024` | yes |
| G9 `groups_count` | `ceil((4096-0)/32768)` = 1 | yes, non-zero |
| G10 `inodes_count <= ipg*gc` | 4 096 vs 4 096 | yes (at equality — confirms `<=` is required, `<` would reject) |
| G11 `gdt_first + gdt_blocks <= blocks_count` | 1 + 1 = 2 vs 4 096 | yes |

**G4 and G10 both hold at exact equality on a real image.** That is the
load-bearing detail: had either been written `<` instead of `<=`, the fix would
have made the production root filesystem unmountable. §3.3's table already says
`<=`; this is the evidence for why.

The directory records of that image were walked too, against §3.10's checks:
`(ino=2, rec_len=12, name_len=1)`, `(ino=2, rec_len=12, name_len=2)`,
`(ino=11, rec_len=4072, name_len=10)` — every `rec_len % 4 == 0`, every
`dir_entry_size(name_len) <= rec_len`. No free record appears in a fresh image,
which is precisely why the R4 defect in §3.10 would not have been caught by
mounting one and had to be found by reading `remove_dir_entry`.

If G12 nevertheless rejects some future image, **land the other eleven checks
and drop G12** rather than weakening any of them. G12 remains the least valuable
of the twelve: G11 already bounds the descriptor table, and out-of-volume reads
already fail as `DeviceError` (`MemoryBlockDevice::read_at` returns
`OutOfBounds`, `blockdev.rs:73-81`; `test_ext2_read_block_out_of_bounds` at
`tests.rs:779-805` depends on exactly that).

Second risk: **G10 uses `<=` rather than the spec's `==`.** Measured above at
exact equality on the production image, so `==` would also pass there — but a
last partial group makes `inodes_count < inodes_per_group * groups_count` legal
and common, and `==` would then reject a valid image. `<=` is the
safety-relevant direction and is what should land.

Third: the `GroupIdx` field-privatisation touches the **6** construction sites
enumerated in §3.4 plus 8 type-position mentions. It is mechanical, but it is
the change most likely to produce a large diff, and it is worth doing as its own
commit ahead of the validation commit so the two review separately.

Fourth, added by this revision: **`Inode::encode`'s narrowing to 128 bytes is a
behaviour change on the write path** (§3.5). It stops zeroing bytes 128.. of a
larger inode. That is the correct behaviour and is pinned by
`test_ext2_inode_extra_bytes_preserved`, but it is a semantic change riding
along with a validation fix, and it should be called out in the commit message
rather than discovered later.

## 8. Residual risk this does **not** close

Stated honestly; these remain open after the fix.

1. **No `mount(2)`, so this is not an unprivileged attack surface today — and
   the fix does not make ext2 safe for one.** Untrusted-image mounting needs a
   privilege model, per-mount resource limits and a fuzz corpus. This proposal
   hardens the parser; it does not authorise untrusted mounting. **Do not read a
   landed 0006 as "ext2 can now mount untrusted images."**
2. **Everything past the geometry is still trusted.** Indirect block pointers
   (`blockmap.rs:76-99` — `map_block` returns whatever `read_ptr`
   (`blockmap.rs:60-68`) finds, with no volume bound), `inode.size` versus
   actual blocks, symlink targets (`symlink.rs`), and `i_blocks` are all still
   taken at face value. Only `read_at` failing out-of-bounds stops them.
   Bounding indirect pointers through `geom.checked_block` is the obvious next
   step and is **out of scope here** — it is a different finding, needs
   `&Ext2Geometry` threaded through `file.rs`/`blockmap.rs` (the signatures
   §3.11 explicitly declines to touch), and should get its own ID.
3. **No metadata checksums.** `gdt_csum` / `metadata_csum` are not implemented
   (`SUPPORTED_RO_COMPAT` is `SPARSE_SUPER | LARGE_FILE`, `ondisk.rs:44`), so a
   descriptor that is *structurally* consistent but semantically wrong — e.g. two
   groups sharing one inode table — still mounts. Structural validation cannot
   detect that; only a checksum or a full fsck can.
4. **`verity` remains CRC-32.** An adversary who rewrites a block, the hash
   array and the root defeats it, as `fs/src/verity.rs`'s own header states. It
   is not an authenticity mechanism and this change does not make it one.
5. **Release builds still have overflow checks off.** The fix converts the
   specific overflow sites in §1.4 to `checked_*`, but any *other* arithmetic on
   on-disk data in `fs/` wraps silently in release. A crate-level
   `overflow-checks = true` for `fs` would close the class; it has a measurable
   cost and is a separate decision.
6. **Time-of-check/time-of-use on the descriptor.** `validate_desc` runs at
   read; the block stays in `BlockCache` and a *later* mutation
   (`write_group_desc`, or an eviction/re-read) is not re-validated by the same
   call. Re-validating on write closes the in-kernel half; a device that returns
   different bytes on two reads of the same block is not defended against by
   anything short of verity.
7. **Torn writes are still possible.** The `TODO(tech-debt)` at
   `ext2_vfs.rs:87-89` — a failed op leaves dirtied blocks cached, so a later
   sync can persist partial metadata — is untouched. That needs a journal.
8. **No fuzzing.** These 16 tests pin 16 known shapes (13 failing without the
   fix, 2 regression guards, 1 API-derivation guard — §5). The class is "malformed on-disk
   metadata", and the only method that covers a class rather than a list is a
   fuzzer over `Ext2Geometry::derive` + `parse_dir_record`. Both are pure
   functions over `&[u8]` — deliberately, so they are fuzzable — but no harness
   is proposed here.
9. **The R4 class is not closed, only this instance.** §3.10's conditional
   checks 5/6 make the validator agree with `append_dir_entry`'s consumer
   *today*. Nothing structurally prevents a future third consumer from
   computing a different `actual_size`. The shared `DirRecord::actual_size()`
   is the mitigation — one expression, one place — but it is a convention, not
   a type-level guarantee, and it is the weakest link in this proposal's
   "make it unrepresentable" argument. Said plainly rather than glossed.

## 9. Constraint compliance

- **`AGENTS.md` read in full first.** Yes, before any code was read.
- **`unsafe`**: none introduced. `fs` keeps `#![forbid(unsafe_code)]`. Nothing
  in this design needs `unsafe`, so nothing is added to `slopos-ostd`.
- **Allocation**: no new allocation at all. `Ext2Geometry` is `Copy` and stored
  inline in the existing `CachedExt2`; `window::<N>` returns a borrow. No
  `alloc::*` anywhere.
- **2048-byte stack cap**: `Ext2Geometry` is **52 bytes** (field-by-field count
  in §3.2) and `Ext2Fs` **grows by 40 bytes**, `CachedExt2` by 44 — rev 2's
  "does not grow" was wrong and is corrected in §3.11. The cap is still safe,
  for a stated reason rather than an assumption: free functions take
  `&Ext2Geometry` so no 52-byte MEMORY-class argument is pushed (§3.2), and the
  four frames that hold an `Ext2Fs` by value appear in no
  `scripts/gates/stack/*.txt` allowlist, so each is under 2048 B with more than
  40 B of headroom. No large struct is constructed by value, so no
  `KBox::try_init` is required. §6 states the verification command.
- **Soft-float**: integer arithmetic only; no float, no vector.
- **Licensing**: no code or prose from any GPL-2.0-only or CDDL source. What is
  used is format facts (field offsets, the bitmap-fits-one-block constraint, the
  4-byte record alignment, the inode-location formulas) and *documented
  behaviour* (validation ordering, the reject-don't-clamp convention). Citations
  in the eventual code comments must name **the ext2/ext4 on-disk format**, never
  an upstream implementation file. CVE-2025-37785 is cited as a public
  vulnerability class, not as a source of text.
- **Task ownership I1–I8**: untouched. No task handle, no raw task pointer, no
  blocking primitive.
- **Every fix pinned by a test that fails without it**: §5, **16** tests with
  byte-exact injections. **13 fail without the fix** (2 by *panic*, 11 by
  wrong-`Ok`); 2 are regression guards that pass both before and after, and 1

- **Data-structure placement, locking and ownership**: §3.0 — per-mount

## 10. Ledger correction required

`CVSS.md` entry `SLOPOS-2026-0006` should be **rewritten**, not just closed:

- The stated evidence — an out-of-bounds slice at
  `&block.data()[within..within + 32]` — is **not reachable**, for the reason in
  §1.2. The proposed remediation ("bound each `within + size` against the
  containing block") would add provably-dead code.
- The real defects at that site are an **unbounded `block_idx`** (§1.3, a
  wrong-block metadata read, not a panic) and **`groups_count()` being
  unvalidated and itself overflowing** (§1.4 P1).
- The genuinely reachable panic in this subsystem is **`dir.rs:235`** (§1.4 P4),
  which the entry does not mention at all and which is a closer analogue of the
  CVE-2025-37785 class the entry cites in its comparator table (`CVSS.md:198`).
  Unlike P1/P2/P3, P4 panics in **every** variant, because its release-build
  route ends in a slice-range panic and `range end index` is present in
  `kernel-release.elf` (§1.4).
- The entry's current "Remediation (proposed)" — *"bound each `within + size`
  against the containing block"* — should be replaced, not amended, since §1.2
  shows the bound it asks for can never fire. `CVSS.md:118` is the line.
- Impact should read **"metadata type confusion on a malformed image; panic
  (DoS) in dev/tests builds, silent wrong-block read/write in release"**, not
  "bounded-slice panic, never memory unsafety". The `#![forbid(unsafe_code)]`
  reasoning is correct — this is not UB — but "never memory unsafety" undersells
  a path that writes an inode through an image-controlled block pointer.
- Confidence should stay **below 80** and remain unscored: §1.6's threat model
  (no `mount(2)`; `devfs` exposes exactly five nodes, `devfs/mod.rs:44-50`, none
  a raw block device) means there is no unprivileged attacker path, which is the
  honest reason not to score it. The *evidence* sub-score should nonetheless
  rise, since §1.3–§1.5 replace a non-reachable claim with reachable ones —
  higher-quality evidence for a lower-severity finding, which is the correct
  direction for both numbers to move independently.

Per `AGENTS.md`'s pre-alpha ledger policy, the entry stays `open` (it is not
fixed) and is **rewritten in place**; it is not removed, and the ID does not
change.
