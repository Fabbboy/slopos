# SLOPOS-2026-0020 — `execve` is not an address-space boundary

**Status of this document:** design proposal, **revision 3** — revisions 1 and 2 were both rejected
by adversarial review. §0 is the revision-2 log; **§0.5 is the revision-3 log**, which is the one to
read first: revision 2 contained **two defects that do not compile** (`Drop` plus move-out, in both
`ExecImage` and `RetiredVm`), a **retire path with no failure branch**, an **un-enumerated
visibility surface** that made the module unimplementable as written, a **quota bound wrong by a
factor of ~20**, and **arithmetic that did not sum** in two tables. No implementation in this
change; nothing outside `plans/fixes/` is touched.

Every file:line citation below was re-read against the working tree while writing **this** revision,
not inherited from the last one. Where an earlier draft cited something that does not exist or does
not behave as claimed, the correction is marked inline rather than silently patched — the point of a
design document is that the next reader can check it.

**The bar this revision is written to** is the reviewer's: *implementable without further design
work*. Concretely, that means every item below is now stated rather than gestured at — the exact
visibility change for every existing private item the new module touches (§5.3.3), the exact type
and shape of every struct that has both a consuming method and a destructor (§5.2, §5.3), the
failure branch of every step described as infallible (§5.3.2), the derivation of every field written
under the commit lock (§5.8), and a constraint-by-constraint compliance audit with file:line
evidence rather than assertion (§11).

**Constraint compliance (stated up front, per the task brief):**

- `AGENTS.md` read in full before any code was inspected; every rule below is applied to the design.
- **No `unsafe` outside `slopos-ostd`.** The whole fix lives in `mm/` and `core/`, both
  `#![forbid(unsafe_code)]`. It needs *zero* new `unsafe`, because every primitive it composes —
  `VmSpace::new`, `CursorMut::map`/`unmap`, `KArc`, `KBox`, `VmaMap` — is already a safe API
  exported by OSTD. No new OSTD surface is required. `check_unsafe_expansion.sh` should therefore
  be unmoved; that is an assertion the implementation must verify, not assume.
- **Allocation only through `slopos_ostd::mm::heap`.** New allocations are `KBox`, `KVec`,
  `KArc`; no `alloc::*` anywhere.
- **2 KiB stack cap.** `ExecImage` is **measured**, not assumed large: §6.1 accounts every field
  and lands at **136 bytes**, so `KBox::try_new` is correct and the in-place-init machinery
  (`#[derive(SlotFields)]` + `init_struct_with`) is *not* required. §6.1 states the byte budget at
  which that flips. Function-by-function frame budgeting is in §6.2.
- **`+soft-float`.** No floating point, no vector types anywhere in this design.
- **Licensing.** Linux and FreeBSD were read *as documented behaviour* (§3). Nothing is copied.
  Where an influence is cited, the citation names the **behaviour or the specification**
  (POSIX `execve` semantics, "install a fresh address space then commit"), never an upstream file
  as the source of text. No upstream comment, essay or paragraph appears here or in the proposed
  code comments.
- **`KArc<Task>` / `TaskRef`.** The de-thread step (§5.6) uses `task_for_each_enumerable` +
  `task_kill_and_wake`, i.e. kill-is-a-flag (I8). No task is torn down from another task's
  context; the exec'ing task waits for siblings to leave the process by their own return path.
  The walk lends a `TaskRef` (I2/I6) and self-exclusion is via a `CurrentTask` borrow, never a
  bare task id (I5).
- **No bare `u32` process id.** Every new entry point takes `slopos_ostd::process::ProcessId`
  (§5.3, §5.6), so `check_process_designator.sh` stays green on its own terms and not merely
  because the new file is outside `SCAN_PATHS` — §8 adds it to the scan anyway.
- **Every fix pinned by a test that fails without it.** Eleven tests in §7, each with the exact
  failure mode it catches, a statement of why it fails on today's tree, and its registration
  mechanics (module wiring, `[[bin]]`, `test_userland_bins`, `utest!`).

### 1.3 `teardown_inner_mappings` — the ledger is wrong twice

Ledger says "`mm/src/process_vm.rs:610-619`, called only from `destroy_process_vm`". Actual,
`mm/src/process_vm.rs:649-656`:

```rust
647: /// The caller drops the slot's `KArc<VmSpace>`; the shootdown issued here is
648: /// what makes the frames that drop releases safe to reuse.
649: fn teardown_inner_mappings(inner: &mut ProcessVm, key: TlbProcessKey) {
650:     tlb::flush_all_for_process(key);
651:     inner.vma_map.drain(|start, end, region| {
652:         dec_removed_shared_mapcount(start, end, region);
653:     });
654:     inner.heap_end = inner.heap_start;
655:     inner.heap_break = inner.heap_start;
656: }
```

It has **four** call sites, not one: `:1575` and `:1607` (the two `create_process_vm_for` failure
paths), `:1675` (`destroy_process_vm`), `:2925` (the `process_vm_clone_cow_for` failure path).
None is on the exec path — which is the finding — but "only called from `destroy_process_vm`" is
not the tree.

**More important, and missed by the ledger's proposed remediation:** `teardown_inner_mappings`
does *not* unmap anything. It flushes the TLB, drains the VMA *metadata*, and resets the heap
scalars. The PTEs and the frames behind them are reclaimed by `KArc<VmSpace>`'s `Drop`
(`slopos-ostd/src/mm/vm_space.rs:1167-1190` → `drop_user_half_tree` →
`recursively_reclaim_subtree`), which every one of its four callers arranges by setting
`proc.vm_space = None` immediately after. The ledger's remediation — "add
`process_vm_reset_for_exec(pid)` reusing `teardown_inner_mappings`" — would therefore, taken
literally, **drop the VMA metadata while leaving every PTE live**: the pages would become
permanently unaccounted, invisible to `munmap`, still mapped and writable by the new image, and
still charged. That is strictly worse than the bug. §4 explains why the correct answer is a
*replacement* address space rather than an in-place wipe, and this is the first reason.

### 1.5 Two additional facts the ledger does not record

**(a) The loader holds an IRQ-off spinlock across page allocation.**
`load_segments_and_tls` takes `PROCESS_VMS[slot].lock()` at `mm/src/process_vm.rs:1152` and holds
it through `load_segment_pages` (`:1197`), which calls `alloc_kernel_page()` (`:1398`) per page,
up to `MAX_TOTAL_MAPPED_SIZE` = 256 MiB (`mm/src/elf.rs:59`) — 65 536 allocations under a
`LOCK_LEVEL_RESOURCE` `SpinLock` with interrupts disabled. `process_vm_reset_stack` explicitly
avoids exactly this shape and says why at `mm/src/process_vm.rs:1888-1889`: *"allocating under
that IRQs-off lock can itself trigger a cross-CPU drain, and deadlock."* The loader does the thing
its neighbour documents as a deadlock. The design in §5 removes the lock from the load path
entirely.

**(b) exec never gets a fresh `MmContextId` or PCID.** `alloc_mm_context_id()`
(`mm/src/mmu/cr3.rs:97-99`) runs exactly twice in the tree: `create_process_vm_for`
(`mm/src/process_vm.rs:1497`) and `process_vm_clone_cow_for` (`:2855`). Neither is the exec path,
so an in-place exec keeps the same `MmContextId` **and the same `Pcid`** — the latter is a field
of `VmSpace`, assigned once in `VmSpace::new` (`slopos-ostd/src/mm/vm_space.rs:259`, via
`alloc_pcid` at `:222-225`) and never reassigned.

**Correction to the first draft (R2).** That draft attributed the hazard to
`mm/src/mmu/asid.rs:203` `select_cr3` and its per-CPU slot/`tlb_gen` machinery. That attribution
is **wrong**: `select_cr3` has no callers.

```
$ grep -rn 'select_cr3' --include=*.rs . | grep -v builddir
./mm/src/mmu/asid.rs:178:/// the tag in the value being loaded, and [`select_cr3`] hands back `NOFLUSH`
./mm/src/mmu/asid.rs:203:pub fn select_cr3(
```

One definition and one doc-link. The per-CPU ASID pool is built but not on the dispatch path; the
CR3 write that actually happens is `VmSpace::activate` (`slopos-ostd/src/mm/vm_space.rs:388-405`),
reached from `process_vm_activate_by_handle` (`mm/src/process_vm.rs:380`) on every context switch
(`sched/src/scheduler.rs:353`).

The hazard is therefore *simpler and still real*: `activate` calls
`write_cr3_pcid(self.pml4_paddr(), self.pcid, pcide_enabled)` — i.e. it sets **CR3 bit 63
(NOFLUSH) whenever `CR4.PCIDE` is on** (`slopos-ostd/src/mm/vm_space.rs:396-404`,
`slopos-ostd/src/arch/x86_64/cr3.rs:50-56`). A `mov cr3` with bit 63 set invalidates nothing. So
after an in-place exec, a CPU switching back into the process reloads *the same PCID and the same
PML4 physical address* with the flush suppressed, and any translation it still caches for a VA
exec re-purposed remains live. Nothing in `do_exec` issues a shootdown — `unmap_user_range`
(`mm/src/process_vm.rs:241-258`) only walks `ostd_unmap_4kb_user`, whose local invalidation comes
from the LUF hook (`mm/src/mmu/luf.rs:19-22`, one `invlpg` on the *unmapping* CPU). That is the
seam SLOPOS-2026-0017 names, and an in-place exec sits directly on it.

A *replacement* `VmSpace` closes it three ways at once, all by construction: a fresh `Pcid` from
`alloc_pcid`, a fresh PML4 physical address, and — because §5.8 step 8 issues
`flush_all_for_process` before the old frames are released — no reliance on the NOFLUSH path at
all. (`alloc_pcid` masks a monotonic counter to 12 bits and its own `TODO(tech-debt)` at
`vm_space.rs:218-221` records that it aliases after 4096 address spaces; this fix does not close
*that*, and §9.9 says so.)

## 2. What actually goes wrong, stated as attacks

1. **Cross-image data retention (confidentiality).** A process maps a shared memfd or an
   anonymous region, receives secret material into it, and `execve`s a program the user chose from
   a shell. The new program's address space still contains that region at the same VA, still
   readable and writable, with no descriptor and no syscall involved in the transfer. This is the
   ledger's own repro and it works.

2. **Cross-image code injection (integrity).** More severe than retention. Nothing stops the old
   image from placing a `PROT_READ|PROT_WRITE` mmap in the arena and then, post-exec, having the
   new image reach it. Worse: `process_vm_mmap_inner` accepts `MAP_FIXED` in
   `[PROCESS_MMAP_START_VA, PROCESS_MMAP_END_VA)` (`mm/src/process_vm.rs:2258-2273`) and
   `prot_to_region` honours `PROT_EXEC` (`mm/src/process_vm.rs:608-622`), so the pre-exec image can
   place *executable* attacker-controlled bytes at a fixed address which the post-exec image
   inherits. Combined with the `/bin/halt`, `/bin/ip`, `/bin/keymap` grants in
   `core/src/exec/grants.rs:32-104` — where **authority is conferred by the program's path at exec
   time** — this is a privilege-escalation primitive: exec `/bin/halt` (gaining `TASK_FLAG_POWER`)
   from a process that pre-planted executable pages, and the planted pages are in the address
   space of a task that now holds Power. The grant table's own header calls itself "containment,
   not a privilege model", but exec-time authority conferral plus address-space carry-over is a
   specific, exploitable combination that the containment argument does not cover.

3. **Resume-into-nothing (availability, and worse).** Any of the four post-load failures in §1.4
   returns an errno to a process whose text was replaced under it. What runs next is whatever
   bytes now live at the old `rip`. Undefined, attacker-influenceable (the attacker chooses the
   ELF whose segments determine those bytes), and not a clean fault.

4. **Sibling-thread address-space swap.** `CLONE_VM|CLONE_THREAD` is supported
   (`sched/src/task/task_lifecycle.rs:1445-1463`); several tasks can share one
   `process_vm_handle`. Nothing in `do_exec` de-threads. Today the siblings survive into the new
   image and keep running with `rip`/`rsp` from the old one, in a partly-replaced address space.

## 3. Prior art, and the designs that were tried and abandoned

Researched online; cited as documented behaviour, per the licensing rule.

**Linux.** The documented shape is a *staging* address space plus a single explicit point of no
return. `execve` builds `struct linux_binprm` holding a **new, not-yet-installed** `mm_struct`; the
argv/envp strings are copied into a stack VMA belonging to that new mm before anything about the
caller changes. `begin_new_exec()` is the documented boundary: it calls `exec_mmap()` to install the
new mm — *"this replaces current->mm — old mappings gone"* — then closes `O_CLOEXEC` descriptors,
resets signal handlers to `SIG_DFL`, applies credentials, and sets the process name. Everything
fallible about parsing and staging happens *before* that call. The relevant history is that this
discipline was not there originally and had to be retrofitted, twice:

- Commit-era work by Eric Biederman renamed the internal flag `called_exec_mmap` to
  `point_of_no_return` precisely to make the boundary findable, with the published rationale that
  *"with the new mm installed it is completely impossible to fail and return to the original
  process"*. The failure mode that motivated it is exactly SlopOS's: an error return after the mm
  swap left `search_binary_handler` about to SEGV `current`.
- A separate series moved the handling of the point of no return *up* into the top-level
  `__do_execve_file`, on the stated grounds that scattering it through the binfmt handlers made it
  impossible to keep correct as code changed.
- The failure-after-no-return case is handled by *killing the process*, never by returning an
  error: `force_sigsegv`. A 2018 patch (Ivan Delalande) narrowed even that — a pending fatal signal
  takes precedence over the forced SIGSEGV — after real segfaults in coreutils were traced to
  `binfmt_elf` failing to load `ld.so` segments for a process being SIGKILLed mid-load.

The design Linux **abandoned** is instructive and is the one SlopOS currently implements: mutate
the live address space incrementally and hope the remaining steps succeed. It was abandoned
because the set of steps after the mutation kept growing, and each new one was a new way to return
an error to a process that no longer had an image.

**FreeBSD.** Same conclusion by a different route. `exec_new_vmspace()` (documented as "destroy old
address space, allocate a new stack") sets `imgp->vmspace_destroyed = 1` as its *first* action, and
`kern_execve` carries the header note that it *"has the astonishing property of not always
returning to the caller"* — because at the bottom, `if (error && imgp->vmspace_destroyed)` calls
`exit1(td, W_EXITCODE(0, SIGABRT))`. FreeBSD also shows the two-branch structure worth stealing:
if the vmspace is unshared and already spans the right range it is wiped in place; otherwise
`vmspace_exec()` allocates a **new** one so *"other threads are not disrupted"*. And it
single-threads first: `thread_single(SINGLE_BOUNDARY)` before anything, returning `ERESTART` — retry
later — when it cannot. Notably, FreeBSD later changed `vmspace_exec()`/`vmspace_unshare()` to
*return an errno* rather than being infallible, i.e. moved the fallible work earlier so the
commit could be clean.

**Fuchsia/Zircon.** The most radical answer: there is no `execve` at all. A process's address space
is a VMAR handle obtained at `zx_process_create`; replacing a program means creating a new process
and a new root VMAR, and the launcher composes it. The reason is precisely that "replace the
address space under a running process" has no atomic formulation on a live object — so the object
is never reused. SlopOS cannot adopt this (POSIX `execve` is in the ABI and `slibc` exports it,
`slibc/src/process/mod.rs:30`) but it validates the direction: **build the new thing beside the old
one and swap, never mutate in place.**

**What every mature kernel settled on, and why:** the new address space is constructed detached,
all fallible work happens against it, and installation is a single infallible step, after which
failure means killing the process rather than returning an error. SlopOS today has neither half.

## 4. Minimal patch, why it is insufficient, and what the refactor buys

### 4.1 The minimal patch

Literally the ledger's remediation: a `process_vm_reset_for_exec(process)` in
`mm/src/process_vm.rs` that, under the slot lock, walks the VMA map and unmaps every region with
its correct per-backing unmap (`unmap_region_range_dir`, `mm/src/process_vm.rs:785+` — the
dispatcher `munmap` already uses, which distinguishes `RegionBacking::Ring`,
`RegionBacking::SharedMemfd` and `RegionBacking::Anonymous`, `mm/src/vma_region.rs:18-32`), drains
the map with `dec_removed_shared_mapcount` (`:764-768`), resets `heap_*`, re-seeds the three
initial VMAs, remaps the stack, and issues one `flush_all_for_process`. Call it from `do_exec`
between `table.process()` and `process_vm_load_elf_data`. Roughly 90 lines.

That backing dispatch is not incidental — it is the same requirement the *refactor* has to meet at
retire (§5.3.2, E9), and the first draft of this document got it wrong there. The minimal patch's
version of the problem is if anything harder, because it must dispatch correctly while the address
space is live and the process is running in it.

### 4.2 Why it is insufficient

1. **It does not fix half the finding.** The ledger's own evidence includes "every failure after
   the load returns `Err` to a process whose old image is gone". An in-place reset makes that
   strictly *worse*: the point of no return moves earlier (to the reset) and now covers the entire
   ELF load, so an OOM at segment three of eight destroys a process that today at least keeps its
   heap.
2. **It cannot be written correctly as a reuse of `teardown_inner_mappings`** — see §1.3. Getting
   it right means duplicating the per-backing unmap dispatch and the frame-lifetime reasoning that
   `destroy_process_vm` gets for free from `VmSpace::drop`. Two implementations of "tear an address
   space down", diverging on the next backing type added.
3. **It keeps the `MmContextId` and the PCID** (§1.5b), leaving exec sitting on the PCID-reuse
   seam of SLOPOS-2026-0017.
4. **It keeps the IRQs-off-lock-across-allocation shape** (§1.5a), and adds to it: the reset must
   free tens of thousands of frames under that same lock.
5. **It cannot re-randomise the layout.** ASLR offsets are chosen once, in `create_process_vm_for`
   (`mm/src/process_vm.rs:1486`). An in-place reset with a *new* layout would have to move the
   stack while the exec'ing task is running on it; with the *old* layout, every exec descendant of
   one parent shares that parent's offsets forever. Today `fork`+`exec` from a shell means the
   shell's ASLR roll is the ASLR roll of every command the user ever types.
6. **It does not de-thread**, so §2.4 stays open.
7. **It leaves the "point of no return" implicit.** Nothing in the type system or the review
   checklist marks where it is. Linux needed two separate refactors to make that boundary findable
   and keep it findable; the minimal patch reproduces the pre-refactor state.

### 4.3 What the refactor buys over five years

- **Failure atomicity becomes structural, not vigilance.** A new fallible step added to exec
  cannot land after the commit, because the commit takes an already-complete `ExecImage` by value
  and everything before it operates on a detached object. The class of bug the ledger describes
  becomes unwriteable rather than avoided.
- **One definition of "a fresh user address space",** shared by `create_process_vm_for` and by
  exec (`seed_fresh_layout`, §5.3). Today spawn and exec construct different-shaped address spaces
  from different code; a new region kind (a vDSO, a signal trampoline page, a `[vvar]` analogue)
  gets added in one place.
- **Exec becomes a real revocation point for memory**, which the authority model currently
  documents that it is not (`CVSS.md:29`). Every future capability keyed on "which address space
  am I" — and the framekernel direction points that way — can rely on it.
- **A fresh `MmContextId`/PCID per exec**, closing exec's instance of 0017 permanently rather
  than per-audit.
- **The loader stops running under an IRQs-off lock**, removing an allocation-under-lock hazard
  and a lockdep edge that constrains every future change to `PROCESS_VMS` ordering.
- **De-threading gets a home.** POSIX requires it; SlopOS will grow more thread users; the
  place to put it is the exec transaction's prologue.

Cost estimate: ~640 lines added (`mm/src/exec_image.rs` ≈ 380 including `RetiredVm`'s
backing-aware retire, `core/src/exec/mod.rs` rework ≈ 140 including `exec_dethread`, tests ≈ 480
across nine `stest!` and two `utest!` plus a helper binary), ~180 lines deleted:
`unmap_existing_code_region` (10), `process_vm_reset_stack` (≈ 80,
`mm/src/process_vm.rs:1882-1965`), `process_vm_load_elf_data`'s slot plumbing and the lock section
of `load_segments_and_tls` (≈ 40), `process_vm_get_stack_top` if retired (12), and the
`create_process_vm_for` body that `seed_fresh_layout` absorbs (≈ 40, offset by the new function).
Net ≈ +460 excluding tests.

## 5. The design

### 5.1 Shape

Exec becomes a three-phase transaction. Phase names are the vocabulary; they should appear in
the code as function names so the boundary is greppable.

```
  PREPARE (fallible, no user-visible effect, old image fully intact)
    ├─ de-thread: kill siblings, wait for task_count <= 1   [execve path only, 5.7.1]
    ├─ open + stat + read the ELF into a KVec<u8>           [unchanged]
    ├─ exec_image_begin()        -> KBox<ExecImage>         [new address space, detached]
    ├─ exec_image_load_elf()     -> ElfExecInfo             [segments into the detached space]
    └─ setup_user_stack_in_image() -> u64 (rsp)            [argv/envp/auxv into the detached space]
         ^ every one of these allocates with IRQs ON and no lock held

  COMMIT (infallible past one generation check; THE point of no return)
    ├─ slot lock: swap vm_space / vma_map / layout          -> RetiredVm
    │    (three mem::replace + seven scalar stores; no alloc, nothing fallible)
    └─ lock released, THEN: load the new CR3 -- only if this CPU is running
         the space being replaced (5.3.1 / E5). Not on the spawn path.

  EPILOGUE (infallible, no user instruction has executed yet)
    ├─ retire the old space: shootdown -> unmap ring/memfd regions by backing
    │    (E9) -> drain VMA metadata -> refund charge -> drop frames
    ├─ close-on-exec descriptors, reset caught signal handlers, resource hooks
    ├─ apply the program-identity grant / restrict capabilities
    └─ rewrite the user register file, reset FPU state, return NoReturn
```

The last three epilogue lines stay in `syscall_exec` (`core/src/syscall/process_handlers.rs:453-518`)
where they already are; only the first two are new. `do_exec` returns `Ok(())` and the handler's
comment at `:453` — `// Point of no return: the old image is gone.` — becomes **true where it
stands**, which today it is not (§1.4).

### 5.2 New module: `mm/src/exec_image.rs`

```rust
//! A user address space under construction, owned by nobody but its builder.

use slopos_ostd::KBox;
use slopos_ostd::mm::KArc;
use slopos_ostd::mm::vm_space::{MapError, VmSpace};
use slopos_ostd::process::ProcessId;

use crate::memory_layout_defs::ProcessMemoryLayout;
use crate::mmu::MmContextId;
use crate::tlb::TlbProcessKey;
use crate::vma_region::VmaMap;

/// The fields of an address space under construction. Split out from
/// [`ExecImage`] so commit can move them out wholesale; see the `Drop` note
/// below for why the wrapper cannot own them directly.
struct ImageParts {
    /// **Uniquely held** (invariant E10): every mapping primitive routes
    /// through `user_mappings::vm_space_get_mut`, which returns
    /// `MapError::ConcurrentAccess` unless `strong_count == 1 &&
    /// weak_count == 0` (`mm/src/user_mappings.rs:84-98`). Nothing clones
    /// this handle before commit.
    vm_space: KArc<VmSpace>,
    vma_map: VmaMap,
    mm_ctx: MmContextId,
    layout: ProcessMemoryLayout,
}

/// A complete user address space that no CPU has ever loaded.
///
/// Detached by construction: it is reachable only through the `KBox` its
/// builder holds, so no lock covers it and no concurrent walker exists.
/// Dropping one is a complete rollback (E2).
pub struct ExecImage {
    /// `None` only between [`exec_image_commit`]'s `take()` and the end of
    /// that call, when the parts have been installed and this shell is about
    /// to be dropped.
    parts: Option<ImageParts>,
}
```

**S1 — why the `Option`, and why revision 2 did not compile.** Revision 2 specified an `ExecImage`
with four plain fields, a commit that moves `image.vm_space` and `image.vma_map` out of it (§5.8
step 3), *and* an explicit `Drop` impl (§5.9 E2, "implement `Drop for ExecImage` explicitly rather
than relying on the derived field drops"). Those three are jointly impossible: `rustc` rejects a
move out of a field of a type implementing `Drop` with **E0509** ("cannot move out of type
`ExecImage`, which implements the `Drop` trait"). The escape hatches are `unsafe`
(`ptr::read` + `ManuallyDrop`) — which `mm/` may not contain, since it is `#![forbid(unsafe_code)]`
like every non-OSTD kernel crate — or `Option::take`, which is safe, allocation-free, and costs one
discriminant. The `Option` is the whole fix:

```rust
impl ExecImage {
    /// Consume the image, yielding its parts. Commit's first act, so nothing
    /// after it can observe a half-installed image.
    fn take_parts(&mut self) -> Option<ImageParts> {
        self.parts.take()
    }
}

impl Drop for ExecImage {
    /// Rollback (E2). `None` after a successful commit, where the parts now
    /// live in the slot; `Some` on every fallible-path drop, where the tree
    /// this reclaims is entirely anonymous by construction — see E2 for what
    /// makes that true and what breaks it.
    fn drop(&mut self) {
        let Some(parts) = self.parts.take() else {
            return;
        };
        // `VmaMap`'s ChargeSlot::drop refunds (ostd .../quota/token.rs:349-356);
        // `VmSpace::drop` reclaims the anonymous user-half tree
        // (ostd .../vm_space.rs:1167-1171). No shootdown: no CPU ever held a
        // translation into this space.
        drop(parts);
    }
}
```

The `Drop` impl exists for the reason E2 gives — a place for the invariant to live and to break
loudly if a future change maps something non-anonymous — not because the field drops need help.
With the `Option`, having both a `Drop` and a consuming path is legal.

**The account is not a field.** The first draft carried an `account: AccountId`; it is redundant.
`VmaMap` already owns the binding (`account: AccountId` + `ChargeSlot<PagesAxis>`,
`mm/src/vma_region.rs:164-173`) and exposes it as `VmaMap::account()` (`:203-205`), which is the
same single-source-of-truth `create_process_vm_for` relies on at `mm/src/process_vm.rs:1529`. A
second copy is a field that can disagree.

**R4 — why `vm_space` is `KArc<VmSpace>` and not a bare `VmSpace`.** The mapping helpers this
module must call (`map_user_range`, `unmap_user_range`, `load_segment_pages`,
`ostd_map_4kb_user`) all take `&mut KArc<VmSpace>` and immediately call `vm_space_get_mut`
(`mm/src/user_mappings.rs:84-98`), which spins `VM_SPACE_MUT_RETRY_SPINS` times and then returns
`MapError::ConcurrentAccess` if any other strong or weak ref exists. Storing a bare `VmSpace`
would mean reimplementing every one of those helpers. Storing the `KArc` and **never cloning it
before commit** satisfies the helpers' contract trivially — the count is 1 by construction, so
`vm_space_get_mut` takes its fast path on the first iteration. That is invariant **E10** (§5.9),
and it is why `exec_image_load_elf` and `exec_image_write_bytes` take `&mut ExecImage`, not
`&ExecImage`: a shared borrow cannot reach `KArc::get_mut`.

**Errors.** One enum, because callers need to distinguish "no memory" from "the process died under
me" from "the ELF is bad":

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum ExecImageError {
    /// The frame allocator, the heap, or the page-table walk ran out.
    NoMemory,
    /// The slot no longer names this process (killed, or generation moved).
    ProcessGone,
    /// A page-table operation failed for a reason that is not exhaustion.
    Map(MapError),
    /// A quota axis refused the charge.
    Charge(TryChargeError),
    /// Sibling threads did not leave the process within the de-thread budget.
    Busy,
}

impl From<SeedError> for ExecImageError {
    fn from(e: SeedError) -> Self {
        match e {
            SeedError::Map(err) => ExecImageError::Map(err),
            SeedError::Charge(err) => ExecImageError::Charge(err),
            SeedError::Range => ExecImageError::NoMemory,
        }
    }
}
```

`Charge` is a distinct arm rather than folded into `NoMemory` because they are different facts: one
is "the machine is out of pages", the other is "this account's ceiling refused". Both map to
`ExecError::NoMem` (`ENOMEM`) at the ABI, matching what `mmap` already returns on a refused charge,
but the kernel log distinguishes them — which is exactly the distinction §9.2's residual needs to be
diagnosable in the field. `TryChargeError` is `slopos_ostd::process::quota::TryChargeError`, the
error `VmaMap::insert` already returns (`mm/src/vma_region.rs:266-274`).

`ExecError` (`core/src/exec/mod.rs:48-58`) gains one variant and one `From`:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[repr(i32)]
pub enum ExecError {
    NoEntry = -2,
    IoError = -5,
    TooManyArgs = -7,
    NoExec = -8,
    BadFd = -9,
    Again = -11,          // NEW
    NoMem = -12,
    Fault = -14,
    NameTooLong = -36,
}

impl From<ExecImageError> for ExecError {
    fn from(e: ExecImageError) -> Self {
        match e {
            ExecImageError::NoMemory | ExecImageError::Map(_) => ExecError::NoMem,
            ExecImageError::ProcessGone => ExecError::Fault,
            ExecImageError::Busy => ExecError::Again,
        }
    }
}
```

**R8 — rebuttal, with evidence.** The review called `Again = -11` a discriminant conflict. It is
not; it is the convention the enum already follows, and the syscall path already handles it.

1. The enum is `#[repr(i32)]` with every variant a *negative* errno — `NoMem = -12`,
   `Fault = -14`, `NameTooLong = -36` (`core/src/exec/mod.rs:48-58`). `-11` is the unused slot
   between `BadFd = -9` and `NoMem = -12`; nothing collides.
2. `EAGAIN` is 11 (`abi/src/errno.rs:120`: `EAGAIN = 11, "Resource temporarily unavailable"`),
   and `define_errnos!` mints `pub const EAGAIN: Self = Self::new(-11)` (`abi/src/errno.rs:81`).
   So `-11` *is* `Errno::EAGAIN`'s raw value.
3. The syscall arm is `Errno::from_raw(e as i32).unwrap_or(Errno::EINVAL)`
   (`core/src/syscall/process_handlers.rs:519`), and `from_raw` accepts any value in
   `[-4095, -1]` (`abi/src/errno.rs:40-49`). `-11` is in range, so it converts rather than
   falling back to `EINVAL`. No change to the handler is needed.

The influence citation is the *documented behaviour* — FreeBSD's `kern_execve` refuses an exec it
cannot single-thread rather than proceeding — not any implementation file.

### 5.3 Public API (exact signatures)

All in `mm/src/exec_image.rs`, re-exported from `mm/src/lib.rs`. `process` is a
`slopos_ostd::process::ProcessId` throughout — never a bare `u32` — so
`scripts/check_process_designator.sh` stays green (its `SCAN_PATHS` covers
`mm/src/process_vm.rs`; the new module should be added to that list, see §8).

```rust
/// Build a fresh, detached address space for `process`, with a newly
/// randomised layout and the three initial VMAs seeded, but no program
/// mapped. The image is charged to `process`'s account from this point, so a
/// refusal here is the address-space ceiling refusing an exec, not a
/// half-charged image.
///
/// Takes no lock. `process.account()` (`slopos-ostd/src/process/mod.rs:364`)
/// is read once and handed to `VmaMap::bind_account`.
pub fn exec_image_begin(process: ProcessId) -> Result<KBox<ExecImage>, ExecImageError>;

/// Map `data`'s PT_LOAD segments into `image`, apply relocations, and return
/// the ELF geometry. Takes no lock.
///
/// `&mut` because the mapping helpers need `KArc::get_mut` — see E10.
pub fn exec_image_load_elf(
    image: &mut ExecImage,
    data: &[u8],
    entry_out: &mut u64,
) -> Result<crate::elf::ElfExecInfo, crate::elf::ElfError>;

/// The top of `image`'s stack, from its own (randomised) layout — i.e.
/// `image.layout.stack_top`, the value today's `process_vm_get_stack_top`
/// reads out of the slot as `stack_end` (`mm/src/process_vm.rs:1879`).
pub fn exec_image_stack_top(image: &ExecImage) -> u64;

/// Write `data` at `addr` in `image`. The argv/envp/auxv builder's only
/// mutator; fails if `addr` is not backed in `image`.
///
/// Body is `write_user_bytes(&image.vm_space, addr, data)`
/// (`mm/src/process_vm.rs:1339-1360`), which walks the page table read-only
/// and writes through the HHDM — so it needs only `&KArc<VmSpace>`. `&mut
/// ExecImage` regardless, so callers cannot interleave it with a shared
/// borrow that would later defeat `KArc::get_mut`.
pub fn exec_image_write_bytes(
    image: &mut ExecImage,
    addr: u64,
    data: &[u8],
) -> Result<(), crate::elf::ElfError>;

/// **The point of no return.**
///
/// Installs `image` as `process`'s address space and hands back the old one.
/// Fails only on the generation check — a slot that no longer names `process`
/// — in which case `image` is returned unconsumed and nothing has changed.
/// Past that check nothing fallible runs.
///
/// **Does not unconditionally load CR3.** It reloads the current CPU's CR3
/// only if that CPU is running *the address space being replaced*; see E5.
///
/// The caller must call [`RetiredVm::retire`] on the result.
pub fn exec_image_commit(
    process: ProcessId,
    image: KBox<ExecImage>,
) -> Result<RetiredVm, (KBox<ExecImage>, ExecImageError)>;

/// The address space exec replaced, carried out of the slot lock so its frames
/// are freed with interrupts enabled and no lock held (I3's shape, applied to
/// an address space rather than a task).
///
/// Same `Option` shape as [`ExecImage`], for the same reason (S1): `retire`
/// consumes the parts and `Drop` is the backstop, and a type cannot have both
/// unless the move goes through an `Option`.
#[must_use = "an unretired address space leaks its frames and its page charge"]
pub struct RetiredVm {
    parts: Option<RetiredParts>,
}

struct RetiredParts {
    vm_space: KArc<VmSpace>,
    vma_map: VmaMap,
    mm_ctx: MmContextId,
    key: TlbProcessKey,
}

impl RetiredVm {
    /// Shoot down every CPU that may hold a translation, unmap every
    /// non-anonymous region through its own backing-aware path, drain the
    /// VMA map, then release the frames. §5.8 steps 8–12 give the exact order
    /// and why each edge is load-bearing.
    ///
    /// Must not run while any CPU's CR3 names the retired space; E5 and E8
    /// together are what establish that.
    ///
    /// Infallible **as a signature**: the one fallible step inside it (the
    /// backing-aware unmap) has a stated terminal branch — see §5.3.2.
    pub fn retire(mut self) {
        if let Some(parts) = self.parts.take() {
            retire_parts(parts);
        }
    }
}

impl Drop for RetiredVm {
    /// Backstop for the unwind path: `"panic-strategy": "unwind"`
    /// (`targets/x86_64-slos.json:17`), so a panic between commit and
    /// `retire()` must not leak an address space. `retire()` stays the named,
    /// greppable call site.
    fn drop(&mut self) {
        if let Some(parts) = self.parts.take() {
            retire_parts(parts);
        }
    }
}
```

### 5.3.1 R1 — commit must not blindly load CR3

The first draft's step 6 was an unconditional `new_space.activate_at_context_switch()`. That is
**wrong**, and the counter-example is in the tree: `do_exec` has *two* callers.

```
$ grep -rn 'do_exec' --include=*.rs core/
core/src/exec/mod.rs:302:        do_exec(          # inside spawn_program_with_attrs
core/src/exec/mod.rs:421:pub fn do_exec(
core/src/syscall/process_handlers.rs:428:    let exec_result = exec::do_exec(
```

`spawn_program_with_attrs` (`core/src/exec/mod.rs:226-306`) calls `do_exec` against
**`spawn.child_table()`** — the *pending child's* descriptor table (`:299`), for a task that has
not been published and is not running anywhere. The calling CPU is the **parent**. Loading the
child's CR3 there would put the parent onto the child's page tables mid-spawn; the parent's next
stack access is to a VA the child's PML4 does not map, and the CPU takes a fault with no valid
stack. That is a boot-time triple fault, since `launch_init` reaches this path
(`core/src/exec/mod.rs:262-266` names it).

The predicate is available and cheap. `mm/src/mmu/luf.rs` maintains, per CPU, the
`mm_ctx_handle` of the address space currently in CR3 — written from `LufHook::on_activate`
*before* `VmSpace::activate` writes CR3 (`mm/src/mmu/luf.rs:33-40`, hooked at
`mm/src/mmu/luf_hook.rs:23`) and read back by `current_cpu_active_mm_ctx()`
(`mm/src/mmu/luf.rs:44-52`). So:

```rust
// Inside exec_image_commit, after the slot guard is dropped:
let self_is_running_old = luf::current_cpu_active_mm_ctx() == old_mm_ctx.raw();
if self_is_running_old {
    IrqDisabled::with(|_irq| new_space.activate_at_context_switch());
}
```

- **The `execve` syscall path**: the calling CPU *is* running the process being replaced, so the
  predicate is true and CR3 is reloaded before `do_exec` returns. Required — the epilogue's
  `exec_image_write_bytes`-free tail and the syscall return both need the new mappings live.
- **The `spawn_program_with_attrs` path**: the parent CPU is running the *parent's* context, whose
  handle differs, so the predicate is false and no CR3 write happens. The child picks the new
  space up on its first dispatch through `process_vm_activate_by_handle`
  (`sched/src/scheduler.rs:353`), exactly as it does today.

The `IrqDisabled::with` wrapper (`slopos-ostd/src/cpu/x86_64/interrupts.rs:117-126`) is what makes
`activate_at_context_switch` legal: its doc comment states the contract as "IRQs off, on the local
CPU" (`slopos-ostd/src/mm/vm_space.rs:372-384`). No `unsafe` is written —
`activate_at_context_switch` is the safe wrapper OSTD exports for precisely this.

Test **10** (§7) pins this: it drives a commit from a CPU running a *different* address space and
asserts the caller's CR3 is unchanged.

### 5.3.2 R3 — retire must not free ring or memfd frames through `VmSpace::drop`

The first draft specified retire as `flush` → `drain` → `drop(map)` → `drop(space)`. That leaks
refcounts at best and double-frees at worst, and the reason is in `VmSpace::drop`.

`drop_user_half_tree` → `recursively_reclaim_subtree` (`slopos-ostd/src/mm/vm_space.rs:1173-1220`)
walks every present user-half PTE and calls `reclaim_leaked_frame(child)` on each leaf. It is
**backing-blind**: it does not consult the VMA map, so it treats a `RegionBacking::Ring` leaf and
a `RegionBacking::SharedMemfd` leaf exactly like an anonymous one.

Those two are not anonymous:

- **`Ring`** — `mm/src/vma_region.rs:25-31` records that the kernel ring object owns the frames as
  `Frame<RingMeta>` and the user PTE holds an *independent* `from_in_use` ref. The mapping path is
  `ostd_map_ring_4kb_user` (`mm/src/user_mappings.rs:171+`), a different primitive with a
  different meta type.
- **`SharedMemfd`** — `mm/src/vma_region.rs:22-24`: "pages belong to the MemfdObject, not the
  process. Must not be freed on munmap; only mapcount decrement."

The tree already has the correct primitive: `unmap_region_range_dir` (`mm/src/process_vm.rs:785+`),
which is what `munmap` uses and which dispatches per backing. So retire becomes:

```
8.  tlb::flush_all_for_process(key);
9.  for (start, end, region) in non-anonymous regions of vma_map:
        unmap_region_range_dir(&mut vm_space, key, start, end);   // ring + memfd
10. vma_map.drain(|s, e, r| dec_removed_shared_mapcount(s, e, r));
11. drop(vma_map);   // ChargeSlot::drop refunds
12. drop(vm_space);  // only anonymous leaves remain for the blind walk
```

Step 9 runs *after* the shootdown of step 8 and with no lock held, which is the ordering
`unmap_region_range_dir`'s own callers use. Invariant **E9** (§5.9) names this; test **11** (§7)
pins the ring half and test **4** the memfd half.

`RetiredVm` is deliberately `#[must_use]` and has no `Drop`-only path that skips the shootdown:
its `Drop` performs the same work as `retire()` (so a panic-unwind still frees — the target is
`"panic-strategy": "unwind"`, `targets/x86_64-slos.json:17`) but `retire()` is the named, greppable
call site. The linear-handle shape is the same one `slopos-ostd` uses elsewhere
(`util/ptr_buf.rs:103` `OneShotBuf`) and is what `check_safe_contract_surface.sh` wants instead of
a `# Safety` note.

### 5.4 Shared seeding — the anti-drift measure

Extract from `create_process_vm_for` (`mm/src/process_vm.rs:1519-1645`), verbatim in behaviour:

```rust
/// Seed a brand-new user address space: the code/data/stack VMAs, the mapped
/// stack, and the compatibility zero page at VA 0.
///
/// The single definition of "what a fresh SlopOS address space looks like";
/// `create_process_vm_for` and `exec_image_begin` both call it, so a new
/// region kind is added once.
///
/// Takes the map and the space separately rather than a `&mut ProcessVm`, so
/// it can serve a detached `ExecImage` that has no slot.
fn seed_fresh_layout(
    vm_space: &mut KArc<VmSpace>,
    vma_map: &mut VmaMap,
    layout: &ProcessMemoryLayout,
) -> Result<(), MapError>;
```

What it must contain, in the order `create_process_vm_for` does it today:

1. Three `VmaRegion`s inserted — `Code` (`Protection::RX`, `[code_start, data_start)`), `Data`
   (`RW`, `[data_start, heap_start)`), `Stack` (`RW`, `[stack_top - stack_size, stack_top)`) —
   `mm/src/process_vm.rs:1544-1585`.
2. `map_user_range` over the stack extent with the stack region's page flags (`:1588-1610`).
3. The zero page at VA 0, `PageFlags::USER_RW`, plus its `General` VMA — tolerated null accesses
   (`:1617-1642`). Failure here is **logged and ignored** today; preserve that, or change it
   deliberately and say so (§9.5).

Two mechanical differences from the current code, both because the callee no longer has a
`ProcessVm`:

- `add_vma_to_inner(&mut proc, ...)` (`:598-606`) becomes a direct `vma_map.insert(...)`; the
  helper's only extra work is `vma_range_valid` plus mapping the error to `c_int`.
- The seven layout scalars (`code_start` … `stack_end`) stay in the *caller*: `create_process_vm_for`
  writes them into the slot (`:1530-1537`), and `exec_image_begin` keeps them in
  `ExecImage::layout`. `seed_fresh_layout` reads `layout` and never writes slot state.

`create_process_vm_for` is rewritten to call it under its slot lock (behaviour-identical);
`exec_image_begin` calls it on the detached image with no lock held. **`create_process_vm_for`'s
version still allocates under the slot lock** — that is pre-existing and out of scope here; the
exec path is what this fix takes off the lock. This is where the five-year value is: one place
defines the shape.

"No new edge" is not an assertion to take on faith; here is what each phase acquires, in order.
`SpinLock::lock` is `PreemptGuard::new()` then `save_flags_cli()` (`slopos-ostd/src/sync/spin.rs:417-429`),

| Phase | Acquires, in order | Level | Allocates under it? |

| `setup_user_stack_in_image` | **none** | — | yes: the argv/auxv `KVec`s, IRQs on |
| `exec_image_commit` | `PROCESS_VMS[slot]` — and nothing else | `LOCK_LEVEL_RESOURCE` | **no.** Three `core::mem::replace`s and seven scalar stores (E4) |

Two consequences, both load-bearing:

1. **No new lock class** is declared — `lock_class!` appears nowhere in the new module.
2. **One edge is removed and none added.** Today `load_segments_and_tls` holds
   `PROCESS_VMS` (`LOCK_LEVEL_RESOURCE`) across `alloc_kernel_page()`
   (`LOCK_LEVEL_ALLOCATOR`), which is the `PROCESS_VMS -> BUDDY_ALLOCATOR` edge and the deadlock
   `process_vm_reset_stack` documents at `mm/src/process_vm.rs:1888-1889`. After this change the

   design acquires the buddy allocator while `PROCESS_VMS` is held: commit allocates nothing, and
   retire runs after `drop(guard)`.

Because an edge *disappearing* changes edge and chain counts, `check_lockdep_headroom.sh` moves.
§8 says so and says to re-measure rather than hand-edit.

Per-CPU vs global: nothing new is per-CPU. The existing per-CPU state exec interacts with is the
ASID cache (`mm/src/mmu/asid.rs`) and the TLB CPU mask (`mm/src/tlb.rs:372` `notify_mm_switch`),
both already keyed on `MmContextId` / `TlbProcessKey`; the fresh `MmContextId` means the new image
starts with no stale bindings anywhere and the old context's bindings become unreachable rather
than reused (§1.5b).

### 5.6 De-threading

```rust
/// Make `process` single-threaded, as POSIX requires of a successful exec.
///
/// Kill is a flag (task-ownership I8): each sibling is marked and woken, and
/// leaves the process from its own context by returning out of whatever it
/// was blocked in. This waits for that to happen; it never tears a peer down.
///
/// `caller` is the borrow that names the task performing the exec, so it can
/// exclude itself without a bare id. Lives in `core/src/exec/mod.rs`, not in
/// `mm/`: it touches only the task registry and the process refcount.
fn exec_dethread(
    process: ProcessId,
    caller: &slopos_sched::task_struct::CurrentTask,
) -> Result<(), ExecImageError>;
```

**R6 — designator and predicate, both restated.**

The first draft took `(&Process, u32)`. Two problems, both fixed:

1. **The bare `u32` is gone.** `process: ProcessId` is the generation-checked designator
   (`slopos-ostd/src/process/mod.rs:296-301`), matching what `do_exec` already holds from
   `table.process()`. Self-exclusion uses `caller`, a `CurrentTask` borrow — the I5 shape (`current`
   is a borrow, never an owned handle) — rather than comparing task ids. This also keeps
   `check_process_designator.sh` green independently of §8's `SCAN_PATHS` change.
2. **The wait predicate is stated with its race.**

The kill sweep:

```rust
// The packed word a Task actually carries. `Handle<Process>` has no `raw()`;
// `pack_process_handle` (ostd/process/mod.rs:45-48) is the encoder, and it is
// the same one `Task::process()` decodes with at kernel_task.rs:1008-1012.
let target_handle = slopos_ostd::process::pack_process_handle(process.handle());
slopos_sched::task::task_for_each_enumerable(|task| {
    if task.process_handle_raw() != target_handle { return; }   // ostd .../kernel_task.rs:994
    if core::ptr::eq(&**task, caller.task()) { return; }         // never self
    slopos_ostd::task::ops::task_kill_and_wake(&**task);         // ostd/task/ops.rs:109
});
```

Comparing the *packed word* rather than calling `task.process()` is deliberate: `process()`
clones a `KArc<Process>` per task (`slopos-ostd/src/task/kernel_task.rs:1008-1012`), which is an
atomic increment per registry entry inside a walk. The packed word carries both slot and
generation, so the comparison is exactly as safe and is one load.

`task_for_each_enumerable` (`sched/src/task/task_table.rs:835-841`) is the right walk: it is
`task_for_each_active` minus exited tasks, and it lends a `TaskRef` — an owning handle — rather
than a bare `&Task`, which is what makes killing a peer from the walk sound under I2/I6.
`task_kill_and_wake` sets the flag and wakes; every blocking primitive then returns
`Err(WaitAbort::Killed)` and the sibling unwinds by *returning*, so its destructors run on its own
stack (I8). Nothing is torn down from this context.

The wait:

```rust
const DETHREAD_BUDGET_MS: u32 = 250;
let mut waited = 0u32;
while process.get().map_or(0, |p| p.task_count()) > 1 {
    if waited >= DETHREAD_BUDGET_MS { return Err(ExecImageError::Busy); }
    slopos_sched::scheduler::sleep_current_task_ms(1);
    waited += 1;
}
```

`Process::task_count()` is one `Acquire` load of an `AtomicU32`
(`slopos-ostd/src/process/mod.rs:194-196`); a departing sibling decrements it via
`task_leave()` from `task_leaves_process` (`sched/src/task/task_lifecycle.rs:415`). `> 1` rather
than `!= 0` because the caller is itself counted. The loop holds **no lock** — the sleep between
polls is what lets the siblings actually run.

**The race this does not close, and why that is acceptable.** `task_count` can *rise* again: a
surviving sibling could call `clone` between the sweep and the check, and `task_join`
(`slopos-ostd/src/process/mod.rs:202-204`) increments. Two mitigations, neither of them a lock:

- A sibling that reaches `clone` has reached a syscall, so it has reached the kill check and is
  already unwinding — the window needs the clone to be *in flight* at sweep time.
- If it does happen, the loop simply does not converge and returns `Busy` → `EAGAIN`. **A raced
  exec is refused, never committed**, because the check is a precondition of the commit and not a
  post-condition of the sweep. §5.9 E8 states the invariant the commit relies on and §5.9 says
  where it is asserted.

This whole function runs **before any state change**, so a refusal costs nothing: no image has
been built, no charge taken, no mapping touched.

### 5.7 The rewritten `do_exec`

```rust
pub fn do_exec(
    table: FdTable,
    path: &[u8],
    argv: Option<&[&[u8]]>,
    envp: Option<&[&[u8]]>,
    entry_out: &mut u64,
    stack_ptr_out: &mut u64,
    tls_tp_out: &mut u64,
) -> Result<(), ExecError> {
    // --- PREPARE: every fallible step, old image untouched ------------------
    let vm_process = table.process().ok_or(ExecError::NoMem)?;

    // Only when this call is replacing a *running* image. On the spawn path
    // the target is a pending child with exactly one task and no siblings to
    // shed, and `Current` is the parent -- de-threading against it would kill
    // the parent's own threads. See 5.7.1.
    if let Some(caller) = slopos_sched::task_struct::Current::get()
        && caller.task().process_handle_raw()
            == slopos_ostd::process::pack_process_handle(vm_process.handle())
    {
        exec_dethread(vm_process, &caller)?;          // EAGAIN if it cannot
    }

    let elf_data = read_executable(path)?;            // open + stat + read, unchanged

    let mut image = exec_image_begin(vm_process)?;
    let exec_info = exec_image_load_elf(&mut image, elf_data.as_slice(), entry_out)?;
    let stack_top = setup_user_stack_in_image(&mut image, argv, envp, &exec_info)?;

    // --- COMMIT: the point of no return ------------------------------------
    // Reloads this CPU's CR3 only if this CPU is running the space being
    // replaced (R1 / E5).
    let retired = match exec_image_commit(vm_process, image) {
        Ok(retired) => retired,
        // Only reachable if this process died under us; the image drops here
        // and the old space is still installed, so returning an error is safe.
        Err((_image, err)) => return Err(ExecError::from(err)),
    };

    // --- EPILOGUE: infallible ----------------------------------------------
    retired.retire();
    *stack_ptr_out = stack_top;
    *tls_tp_out = exec_info.tls_tp;
    slopos_fs::fileio_close_on_exec(table);
    Ok(())
}
```

#### 5.7.1 The two callers, and why the prologue is conditional

`do_exec` is not only the `execve` implementation. `spawn_program_with_attrs`
(`core/src/exec/mod.rs:226-306`) calls it at `:302` against a **pending child's** table, obtained
from `SpawnGuard::child_table()` (`:299`, `sched/src/task/pending_spawn.rs:20`). That child:

- has exactly one task, which has not been published (`publish_new_task` runs at `:410`, long
  after), so there is nothing to de-thread; and
- is not the address space the calling CPU is running, which is what R1's CR3 predicate handles.

Hence the guard: de-thread only when `Current`'s process handle equals the target's. On the
`execve` path that is trivially true. On the spawn path it is false, and skipping is correct
rather than merely harmless — an unconditional sweep would walk the *parent's* threads (the shell
spawning a command) and kill them.

`launch_init` reaches the spawn path with no `Current` at all (`core/src/exec/mod.rs:262-266`
documents the `None` case as "the kernel-only root"), which the `if let Some(caller)` covers.

`setup_user_stack` (`core/src/exec/mod.rs:502-596`) is rewritten to take `&ExecImage` instead of
`FdTable`, and its three writers (`write_to_user_stack`, `write_byte_to_user_stack`,
`write_u64_to_user_stack`, `:598-612`) become `exec_image_write_bytes` calls. The layout arithmetic
— SysV alignment, the auxv block, the argv/envp vectors — is unchanged, which matters because
`test_setup_user_stack_contract_layout` and `test_setup_user_stack_auxv_required_entries`
(`core/src/exec/tests.rs:417, 483`) pin it; those tests are updated to build an `ExecImage`
instead of a live process VM, and must continue to pass unchanged in their assertions.

### 5.8 Commit, in exact order

Inside `exec_image_commit`, and this ordering is load-bearing:

```
0.  let slot = find_slot_for_pid(process)?;                    // generation-checked
1.  let mut guard = PROCESS_VMS[slot].lock();
2.  if guard.process_id != process.id()
       || guard.generation != process.handle().generation() {
        drop(guard); return Err((image, ProcessGone));         // nothing changed
    }
2b. debug_assert!(process.get().map_or(0, |p| p.task_count()) <= 1, "E8");
3.  let old_space = core::mem::replace(&mut guard.vm_space, Some(image.vm_space))
        .expect("a live slot always has a vm_space");
    let old_map   = core::mem::replace(&mut guard.vma_map, image.vma_map);
    let old_mm_ctx = MmContextId::from_raw(old_space.mm_ctx_handle());
    // core::mem::replace only; no allocation, no fallible call.
4.  guard.code_start/data_start/heap_start/heap_end/heap_break/stack_start/stack_end
        <- image.layout   (seven scalar stores)
5.  drop(guard);                                               // lock released here
6.  if luf::current_cpu_active_mm_ctx() == old_mm_ctx.raw() {   // R1 / E5
        IrqDisabled::with(|_| new_space.activate_at_context_switch());
    }
7.  return Ok(RetiredVm { vm_space: old_space, vma_map: old_map,
                          mm_ctx: old_mm_ctx, key: slot_tlb_key(slot) });
```

And in `RetiredVm::retire`:

```
8.  tlb::flush_all_for_process(key);        // peers drop old translations
9.  for (start, end, region) in vma_map.iter() where !region.is_anonymous():
        unmap_region_range_dir(&mut vm_space, key, start, end);   // R3 / E9
10. vma_map.drain(|s, e, r| dec_removed_shared_mapcount(s, e, r));  // memfd mapcounts
11. drop(vma_map);                          // ChargeSlot::drop refunds the pages
12. drop(vm_space);                         // VmSpace::drop reclaims the anonymous tree
```

Three orderings are invariants, not optimisations:

- **Step 6 before step 12** (**E5**). On the `execve` path the CPU entering commit is running the
  *old* CR3. Dropping the old `VmSpace` while it is the live CR3 would free the PML4 frame under
  the running CPU. On the spawn path step 6 is skipped, and step 12 is still safe because no CPU
  ever loaded the retired space — the child was never dispatched.
- **Step 8 before step 9** (**E9**). `unmap_region_range_dir` releases refs; a peer must have
  dropped its cached translations first. This is the same order `munmap` uses.
- **Step 9 before step 12** (**E9**). `VmSpace::drop`'s walk is backing-blind
  (`slopos-ostd/src/mm/vm_space.rs:1173-1220`), so ring and shared-memfd leaves must be gone from
  the tree before it runs. Step 9 is what removes them.

Step 9 iterating `vma_map` and step 10 draining it are separate on purpose: `drain` is
metadata-only (`mm/src/vma_region.rs:491-500`) and cannot unmap, which is exactly the
`teardown_inner_mappings` misreading §1.3 records the ledger making.

`MmContextId::from_raw(vm_space.mm_ctx_handle())` is how `process_vm_get_mm_ctx_id` already reads
it (`mm/src/process_vm.rs:568`), so step 3 introduces no new accessor. Note that
`VmSpace::set_mm_ctx_handle` **panics on conflicting reassignment**
(`slopos-ostd/src/mm/vm_space.rs:410-425`) — which is precisely why exec must install a *new*
`VmSpace` with a fresh handle rather than re-stamp the old one; an in-place reset that tried to
rebind the context would panic the kernel.

The `TlbProcessKey` does not change (it is derived from the slot index,
`mm/src/process_vm.rs:291`), so `tlb::register_process_tlb` / `unregister_process_tlb` are **not**
called: the slot stays registered across the swap, and the CPU mask correctly still names every
CPU that ran the old image — which is exactly the set step 8 must shoot down. This is why the
shootdown must precede any mask reset; it is also why the design deliberately does *not* reuse the
slot-rebinding path.

`Handle<ProcessVm>` (slot + generation) is **unchanged across exec** by design: the slot and its
generation both stay, so every task's cached `process_vm_handle_raw()`
(`sched/src/scheduler.rs:315`) keeps resolving, and resolves to the *new* space. That is what makes
the swap invisible to the scheduler and to `mm/src/page_fault.rs:31`.

### 5.9 Invariants (name these in the code)

- **E1 — Detachment.** An `ExecImage` is reachable only through the `KBox` its builder owns. No
  entry exists in `PROCESS_VMS`, no CPU has it in CR3, no lock covers it.
- **E2 — Rollback by drop.** Dropping an `ExecImage` is a complete rollback: frames reclaimed by
  `VmSpace::drop`, page charge refunded by `VmaMap`'s `ChargeSlot::drop`, nothing to shoot down
  because no CPU ever cached a translation.

  This is sound **only because every region an `ExecImage` contains is anonymous**, which is what
  makes `VmSpace::drop`'s backing-blind walk the right tool here and the wrong one at retire (E9).
  The builder maps exactly three things — `seed_fresh_layout`'s code/data/stack plus the zero page,
  and the ELF's PT_LOAD segments — all `RegionBacking::Anonymous`. **If a future change gives the
  loader a non-anonymous mapping (a vDSO backed by a shared frame, a memfd-backed segment),
  `ExecImage` needs the same backing-aware teardown `RetiredVm` has, and E2 as stated becomes
  false.** Implement `Drop for ExecImage` explicitly rather than relying on the derived field
  drops, so that requirement has a place to live.
- **E3 — One point of no return.** `exec_image_commit` is the only function that changes what
  userland can address. Everything fallible precedes it; nothing fallible follows it.
- **E4 — Commit is O(1) and allocation-free.** Its critical section performs three
  `core::mem::replace`s and seven scalar stores.
- **E5 — No CPU runs a retired space.** A CPU whose CR3 names the space being replaced switches to
  the new one *before* commit returns; a CPU running anything else is left alone. The predicate is
  `luf::current_cpu_active_mm_ctx() == old_mm_ctx.raw()` (§5.3.1). Peers are covered by E8 for the
  `execve` path and by "never dispatched" for the spawn path. Asserted by test 10.
- **E6 — No user instruction in the window.** Between commit and the syscall return, the task
  never executes a user instruction, so the epilogue's ordering (grants, signal reset, register
  rewrite) is not observable by userland and needs no additional atomicity.
- **E7 — Handle stability.** Exec does not change `Handle<ProcessVm>`. Anything that caches a
  *CR3 physical address* rather than the handle is wrong; the scheduler re-resolves per dispatch
  (`sched/src/scheduler.rs:922`) and must keep doing so.
- **E8 — Single-threaded commit.** `process.task_count() <= 1` holds at commit. Established by
  `exec_dethread` on the `execve` path and by construction on the spawn path (the child has one
  unpublished task). Asserted as a `debug_assert!` at commit step 2b — not a hard check, because
  the sweep's residual race (§5.6) means a hostile process could otherwise turn a refused exec
  into a panic; the honest outcome there is `EAGAIN`, which the loop already produces.
- **E9 — Backing-aware retire.** Every non-anonymous region of a retired address space is unmapped
  through `unmap_region_range_dir` before `VmSpace::drop` walks the tree, because that walk is
  backing-blind. Ring frames keep their `Frame<RingMeta>` accounting and shared-memfd pages are
  mapcount-decremented rather than freed. Asserted by tests 4 and 11.
- **E10 — The image's `KArc<VmSpace>` is uniquely held.** From `exec_image_begin` until the
  `core::mem::replace` in commit, `strong_count == 1 && weak_count == 0`. Every mapping primitive
  depends on it (`user_mappings::vm_space_get_mut`, `mm/src/user_mappings.rs:84-98`) and would
  otherwise fail with `MapError::ConcurrentAccess`. Concretely: `exec_image_*` never clones the
  handle, never hands out a `&KArc`, and the image is not reachable from `PROCESS_VMS`, so
  `process_vm_get_vm_space` (`mm/src/process_vm.rs:445-454`, the tree's only other cloner) cannot
  see it.

### 5.10 Interaction with each subsystem

**TLB shootdown.** One `flush_all_for_process` at retire (step 8), replacing today's implicit
reliance on the LUF hook's per-page local `invlpg` (`mm/src/mmu/luf.rs:19-22`) — which invalidates
only on the *unmapping* CPU and explicitly "records that peers have **not** been told".
`flush_all_for_process` → `targeted_flush_request` (`mm/src/tlb.rs:730-778`) queues a
`FlushType::Full` to every CPU in the process's mask, IPIs them, and waits for acks. Frame-reuse
safety continues to come from `mm::mmu::quiesce`'s epoch rule (`mm/src/mmu/quiesce.rs:13-16`:
freed at E, safe at E+2), which the buddy allocator already enforces on the free path — unchanged.

**Correction (R2).** The first draft claimed the new `MmContextId` matters because "peers' ASID
slots for the old context are never re-selected (`select_cr3` keys on `ctx_id`)". `select_cr3` has
no callers (§1.5b), so that mechanism is not live. What the fresh `VmSpace` actually buys is
**a different PML4 physical address and a different `Pcid`**, so the CR3 value `VmSpace::activate`
writes after the swap shares no tag with the retired space — which matters precisely because
`activate` sets `NOFLUSH` under PCIDE (`slopos-ostd/src/mm/vm_space.rs:396-404`). Optional
follow-up, not required by this fix: call `asid::forget_context_local`
(`mm/src/mmu/asid.rs:282`) for the retired context, which is dead code today and would become
meaningful only once `select_cr3` is wired up.

**Quota accounting.** `exec_image_begin` calls `vma_map.bind_account(process.account())` before the
first mapping (mirroring `mm/src/process_vm.rs:1529` and its comment). Consequence: **between
begin and retire, the process is charged for two images.** Bounded by
`MAX_TOTAL_MAPPED_SIZE` (256 MiB, `mm/src/elf.rs:59`) plus `PROCESS_STACK_SIZE_BYTES` (1 MiB), and
at most one exec is in flight per task, per E8 at most one task per process. This is a real
behaviour change: a process near its per-process `pages` ceiling can now be refused an exec with
`ENOMEM` that today succeeds. That refusal is *correct* — the ceiling is on virtual address space
(`scripts/gates/quota/tests.txt` documents `pages` as the RLIMIT_AS quantity) and the process
momentarily holds two — but it must be measured, not assumed harmless: see §8 and §9.

**Lockdep ordering.** No new class. One edge removed (`PROCESS_VMS -> buddy`). Chain counts move
because the loader's chains disappear. Re-measure, do not hand-edit.

**Authority model.** No new call edge to a power primitive; `syscall_exec` stays `NoneSelf`
(`core/src/syscall/process_handlers.rs:356-360`). The grant application at `:458-474` and the
`task_restrict_caps` intersect (`slopos-ostd/src/task/ops.rs:257`) stay exactly where they are, in
the epilogue — permitted by E6. Positively: this fix *strengthens* the grant model, because the
escalation path in §2.2 (pre-plant executable pages, then exec a granted program) is closed.

**Signals and cleanup hooks.** `task_cleanup_for_exec` (`sched/src/task/task_cleanup_hooks.rs:50`)
and `task_reset_caught_handlers` stay in the epilogue, unchanged. The seat-revocation hook
(`boot/src/boot_drivers.rs:81`) keeps its documented exec behaviour. SlopRing fds are
`FdFlags::PROCESS_PRIVATE` (`ring/src/enter.rs:151`, `fs/src/fileio/mod.rs:284-287`) so they are
closed by close-on-exec; their *mappings* now die with the retired image rather than surviving,
which is the ring region's documented intent (`ring/src/enter.rs:145-146`) finally being true.

**Page faults.** `mm/src/page_fault.rs:31` resolves through the handle
(`unpack_process_vm_handle`) and so sees the new space immediately after commit. A fault taken on
a peer CPU between commit and shootdown resolves against the *new* VMA map — correct, because the
map is swapped under `PROCESS_VMS[slot]`, the same lock `process_vm_with_vm_space_by_handle`
(`mm/src/process_vm.rs:396+`) takes — and, finding no region, faults the peer. E8 says there is no
such peer *in this process* on the `execve` path; on the spawn path the child has never been
dispatched, so it cannot fault either.

**The scheduler's dispatch guard.** `sched/src/scheduler.rs:919-940` refuses to dispatch a task
whose handle resolves to `cr3_phys == 0` and terminates it. The swap never produces that state:
step 3 writes `Some(image.vm_space)` in the same critical section that takes the old one out, so
no observer under the lock ever sees `vm_space == None`. This is why step 3 is a `replace` and not
a `take` followed by a store.

## 6. Stack-frame budget (`check_stack_sizes.sh`, 2 KiB)

### 6.1 R5 — `ExecImage` is measured, and `KBox::try_init` is *not* used

The first draft asserted `KBox::try_init(ExecImage::init_for(...))` "per the in-place-init
discipline" without ever sizing the struct. That is cargo-culting a primitive whose entire purpose
is to keep a *large* `T` off the caller's frame. `ExecImage` is not large:

| Field | Type | Bytes | Basis |
|---|---|---|---|
| `vm_space` | `KArc<VmSpace>` | 8 | one pointer |
| `vma_map` | `VmaMap` | 8 + 4 + 8 + 12 + pad = **48** | `KBTreeMap<u64,(u64,VmaRegion)>` is a `BTreeMap` newtype (`slopos-ostd/src/mm/heap.rs:1546-1548`) = 24 B; `mapped_pages: u32`; `account: AccountId`; `ChargeSlot` is `AtomicU64` + `AtomicU32` + `PhantomData` = 16 B (`slopos-ostd/src/process/quota/token.rs:233-238`) |
| `mm_ctx` | `MmContextId` | 8 | `MmContextId(u64)` (`mm/src/mmu/cr3.rs:69`) |
| `layout` | `ProcessMemoryLayout` | 64 | eight `u64`s (`mm/src/memory_layout_defs.rs:196-205`) |
| | **total** | **≈ 136 B** | |

136 bytes is an ordinary move. `KBox::try_new(ExecImage { .. })` (`slopos-ostd/src/mm/heap.rs:344`)
is correct and the `#[derive(SlotFields)]` + `init_struct_with` machinery
(`slopos-ostd/src/mm/init.rs`) is **deliberately not used** — it would be ~60 lines of
field-by-field `write_field!` for a struct that fits in two cache lines. The tree's own guidance
agrees: `KBox::try_new`'s doc points at the in-place path only for large `T`
(`slopos-ostd/src/mm/heap.rs:342-343`), and the existing `try_init` callers are `Task`
(`sched/src/context_tests.rs:271`) and `VConsoleState`, whose comment cites a **"~3 KiB stack
frame"** (`drivers/src/tty/vconsole.rs:425-427`).

**The threshold at which this flips.** If a future field pushes `ExecImage` past ~512 B — an
inline segment table, a copy of the ELF header, an auxv staging buffer — switch to
`KBox::try_init`. Below that, the extra machinery costs more than it saves. Record the measurement
in this table rather than re-deriving it.

The `KBox` indirection is kept regardless of size, for a different reason: it makes the image a
single movable pointer through `do_exec`'s locals and into `exec_image_commit`'s by-value
parameter, so the rollback-on-drop path (E2) is one `Drop` and the caller's frame carries 8 bytes.

| Function | Frame content | Est. |

| `do_exec` | `KBox` ptr (8), `KVec<u8>` header (24), `ElfExecInfo` (9×u64 = 72), three out-param ptrs, `FdTable` | ~180 B |

  iterate `vma_map` directly or collect into a `KVec`, as `collect_overlapping_vmas`

## 7. Tests that pin the fix

**R7 — "fails on today's tree" restated precisely.** A test that names `ExecImage` cannot compile
against today's tree, so "it fails today" is not literally checkable for tests 1–6 and 10–11. The
honest formulation, and the one the implementation must satisfy, is the **staged** one, and it is
why §10's commit decomposition is ordered the way it is:

- Commits 1–2 add `seed_fresh_layout` and `ExecImage` **with the old exec path still live**. At
  that point tests 1–6, 10 and 11 compile and run against the new module, and the two that assert
  *end-to-end exec behaviour* (8, 9) still exercise the old path and **fail**. Land tests 8 and 9
  in commit 2, red, gated behind nothing — a failing `utest!` is a failing `just test`, so they
  must land in the same commit as the fix (commit 3) or be marked skip. **Choose: land 8 and 9 in
  commit 3.**
- Test 2 (`load_failure_leaves_old_image_intact`) is the one that would fail *if the design were
  implemented wrongly* — i.e. if someone built `ExecImage` but committed before the load. It is a
  regression test for the design, not for the old tree.
- Tests 8 and 9 are the ones that literally fail on today's tree, through the real `execve`
  syscall, with no new kernel API in the assertion. They are the finding's own repro. Verify them
  first: build the two userland binaries against the **unmodified** kernel, run them, watch them
  fail, and record the output in the commit message. That is the evidence the fix is a fix.

Kernel tests are `stest!`; the userland ones are `utest!`. Filtered runs that create files must

## 9. Residual risk this fix does **not** close

1. **A spinning sibling can deny an exec.** `exec_dethread` returns `EAGAIN` after 250 ms if a
   sibling never reaches a blocking primitive. This is the same residual `AGENTS.md` records for
   task-ownership I8 ("a kernel loop that reaches no blocking primitive at all: nothing can stop
   one"), surfaced at a new place. Denying is the safe direction, but a malicious thread can make
   `execve` unreliable for its own process. Not a confidentiality or integrity issue.

2. **Peak virtual-address-space charge doubles across the commit.** A process near its `pages`
   ceiling can be refused an exec it would previously have been granted. Correct behaviour, but a
   behaviour change; if it bites in practice the honest fix is a named `ExecOverlap` grace of one
   image, not a silently raised ceiling.

3. **Exec severs *this process's* mappings, not the underlying objects.** A memfd whose handle a
   peer process still holds keeps its pages; exec drops only this address space's references. That
   is correct POSIX behaviour and worth stating so nobody reads "exec is an address-space
   boundary" as "exec revokes shared memory".

4. **ASLR strength is unchanged.** Re-randomising per exec fixes *reuse* of one roll, but the roll
   is still 8 bits of stack and 12 bits of heap entropy (`mm/src/aslr.rs:19-22`), and `code_start`
   / `data_start` are not randomised at all — the image always lands at `0x40_0000`. A PIE loader
   and a wider entropy budget are separate work.

5. **The zero page at VA 0 is re-created.** `seed_fresh_layout` preserves today's behaviour
   (`mm/src/process_vm.rs:1617-1642`, "tolerate benign null accesses"), so a null dereference in
   the new image still silently reads a mapped page instead of faulting. Deliberately out of
   scope; the refactor makes removing it a one-place change, which is the point.

6. **The shootdown at retire is best-effort in the same sense it already is.** A wedged CPU makes
   `handle_tlb_result` log rather than block forever (`mm/src/tlb.rs:892`); frame-reuse safety
   falls back to the quiesce epochs. Unchanged from today, neither improved nor worsened.

7. **`Handle<ProcessVm>` stability is an invariant, not an enforced property (E7).** Nothing in
   the type system stops a future caller from caching a CR3 physical address across a syscall. A
   gate for that would be a `check_*` script scanning for stored `pml4_paddr` values; not proposed
   here.

8. **Exec still confers authority by path** (`core/src/exec/grants.rs:31-105`). Closing §2.2's
   memory channel does not make path-keyed grants sound; it only removes one way to abuse them.
   That is the residual `CVSS.md:29` already records, and this fix does not claim to close it.

9. **`alloc_pcid` still aliases after 4096 address spaces.** A fresh `Pcid` per exec is fresh only
   in the sense that the counter advanced; `alloc_pcid` masks a monotonic `AtomicU64` to 12 bits
   (`slopos-ostd/src/mm/vm_space.rs:222-225`) and its own `TODO(tech-debt)` at `:218-221` says a
   real ASID slot scheduler is missing. This fix removes exec from the set of operations that
   *reuse a PCID deliberately*; it does not fix the wraparound. That is SLOPOS-2026-0017's
   territory, and §1.5b's correction means the two findings overlap less than the first draft
   claimed.

10. **`select_cr3` and the per-CPU ASID pool remain dead code.** `mm/src/mmu/asid.rs:203` and
    `forget_context_local` (`:282`) have no callers. This fix does not wire them up, and a future
    change that does must re-examine §5.10's TLB reasoning — the reasoning here is written against
    the CR3 path that is actually live (`VmSpace::activate`), not the one that is built.

11. **The de-thread sweep has a clone race it does not close.** §5.6 states it: a sibling that
    calls `clone` between the sweep and the count check can keep `task_count` above 1. The design
    converts that into `EAGAIN` rather than a wrong commit, but it means a hostile process can
    make its own `execve` fail indefinitely. Same severity class as residual 1.

12. **E8 is a `debug_assert!`, not an enforced check.** §5.9 explains why (a hard assert would let
    the race in residual 11 panic the kernel). A release-build commit with two live tasks would
    swap the address space under a peer. The mitigation is that the only path to it is the clone
    race, and the only way to *reach* the clone race is from inside the process being exec'd.
